시스템 설계 면접에서는 모호한 문제를 면접관과 함께 풀어 간다. 필요한 기능과 규모를 질문으로 확인하고, 설계에서 내린 결정의 근거를 설명하며, 피드백을 반영하는 과정이 중요하다.

기술적으로 가능한 설계라도 비용과 복잡성이 지나치게 커질 수 있다. 요구사항에 맞는 선택을 하고 그에 따른 장단점을 논의해야 한다. 설계의 완성도와 함께 협업하는 태도, 질문하는 능력도 평가 대상이다.

## 1단계: 문제 이해와 설계 범위 확정

문제를 듣자마자 구조를 그리기 시작하면 요구사항과 다른 시스템을 만들 수 있다. 먼저 무엇을 설계해야 하는지 확인한다.

- 구체적으로 어떤 기능이 필요한가?
- 사용자 수와 예상 트래픽은 어느 정도인가?
- 앞으로 몇 달이나 1년 뒤에는 규모가 얼마나 커지는가?
- 사용할 기술 스택과 활용할 수 있는 기존 서비스는 무엇인가?

면접관이 답을 주는 경우도 있고, 직접 가정을 세우도록 하는 경우도 있다. 스스로 정한 조건은 기록하고 면접관과 확인한다.

예를 들어 뉴스 피드 시스템이라면 다음과 같이 범위를 정할 수 있다.

| 항목        | 합의한 조건                         |
| ----------- | ----------------------------------- |
| 지원 환경   | 웹과 모바일                         |
| 핵심 기능   | 게시물 작성과 뉴스 피드 조회        |
| 정렬 기준   | 최신 게시물이 먼저 나오는 시간 역순 |
| 친구 수     | 사용자당 최대 5,000명               |
| 규모        | 일간 활성 사용자 1,000만 명         |
| 게시물 형식 | 텍스트, 이미지, 영상                |

이처럼 기능과 규모를 먼저 합의하면 이후 설계에서 무엇을 우선해야 하는지 정할 수 있다.

## 2단계: 개략적인 설계안 제시와 합의

전체 구조의 첫 설계안을 제시하고 면접관의 의견을 구한다. 면접관을 함께 문제를 푸는 팀원으로 생각하고, 방향이 맞는지 확인하며 진행한다.

클라이언트, API, 웹 서버, 저장소, 캐시, CDN, 메시지 큐 등 필요한 구성요소와 연결 관계를 그린다. 구체적인 사용 사례를 따라가며 데이터가 어떻게 흐르는지, 빠진 상황은 없는지 살펴본다.

뉴스 피드 예제는 크게 두 흐름으로 나눌 수 있다.

| 흐름           | 처리할 일                                        |
| -------------- | ------------------------------------------------ |
| 피드 발행      | 게시물을 저장하고 친구들의 뉴스 피드에 반영한다. |
| 피드 생성·조회 | 친구들의 게시물을 최신순으로 모아 보여 준다.     |

필요하다면 설계가 예상 규모를 감당할 수 있는지 개략적으로 계산한다. 규모 추정이 필요한지 면접관에게 확인하고, 계산 과정과 가정을 소리 내어 설명한다.

API나 DB 스키마를 어느 정도까지 다룰지는 문제의 범위에 따라 달라진다. 큰 시스템의 전체 구성을 논의하는 단계인지, 상대적으로 좁은 기능을 설계하는 단계인지에 맞춰 구체화할 수준을 정한다.

## 3단계: 중요한 영역의 상세 설계

전체 구조에 합의했다면 면접관과 상세하게 살펴볼 영역의 우선순위를 정한다. 앞 단계에서 구성요소와 처리 흐름을 잡았다면, 이제는 선택한 핵심 영역의 동작을 구체화한다.

뉴스 피드라면 게시물을 친구들의 피드에 반영하는 과정과 사용자가 피드를 가져오는 과정을 더 깊게 설명할 수 있다. 발행 쪽에서는 친구 정보 조회, 메시지 큐와 작업 서버를 통한 전달을 살피고, 조회 쪽에서는 뉴스 피드 캐시와 사용자·게시물 정보를 가져오는 흐름을 살핀다.

문제에 따라 집중할 부분은 달라진다. 단축 URL 생성기라면 해시 함수, 채팅 시스템이라면 지연시간과 사용자의 온·오프라인 상태 표시가 중요할 수 있다. 성능을 중심으로 질문한다면 병목 구간과 자원 요구량을 설명한다.

시간도 함께 관리한다. 최신순으로 정렬하기로 한 뉴스 피드에서 순위 알고리즘을 길게 설명하는 것처럼, 합의한 범위와 관련이 적은 세부사항에 시간을 쓰지 않도록 한다.

## 4단계: 설계를 돌아보고 마무리

설계안을 제시한 뒤에도 논의는 이어진다. 면접관의 후속 질문에 답하고, 필요한 경우 다음 내용을 짚는다.

- **설계 요약**: 주요 구성과 처리 흐름을 짧게 되짚는다. 여러 해법을 논의했다면 최종 선택을 다시 정리한다.
- **병목과 개선점**: 현재 설계의 한계와 더 개선할 수 있는 부분을 찾는다.
- **장애 상황**: 서버 오류나 네트워크 장애가 나면 어떻게 동작하는지 설명한다.
- **운영**: 로그와 메트릭을 어떻게 수집하고 모니터링할지, 시스템을 어떻게 배포할지 논의한다.
- **규모 확장**: 사용자와 트래픽이 더 늘었을 때 대응할 방법을 살핀다.

설계가 완벽하다고 방어하기보다 개선할 점을 찾고 선택의 근거를 설명한다. 시간이 남으면 필요하지만 다루지 못한 세부사항도 제안할 수 있다.

## 시간 배분

45분 면접을 기준으로 각 단계에 쓸 시간을 대략 잡으면 다음과 같다.

| 단계                       | 권장 시간 |
| -------------------------- | --------- |
| 문제 이해와 설계 범위 확정 | 3~10분    |
| 개략 설계안 제시와 합의    | 10~15분   |
| 상세 설계                  | 10~25분   |
| 마무리                     | 3~5분     |

각 단계의 시간은 문제의 범위와 면접관의 관심사에 따라 달라진다. 전체 면접 시간 안에서 중요한 영역에 시간을 더 쓰고, 마지막 논의를 위한 시간도 남긴다.

진행하는 동안 생각의 흐름을 말로 설명하고 면접관의 의견을 자주 구한다. 막히면 힌트를 요청한다. 혼자 세운 가정을 당연하게 취급하거나 침묵 속에서 설계를 끝내기보다, 조건과 선택을 계속 확인하며 대화를 이어 가는 편이 좋다.
