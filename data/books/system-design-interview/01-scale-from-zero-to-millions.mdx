처음부터 수백만 사용자를 위한 시스템을 만들지는 않는다. 서버 한 대에서 시작해 사용자가 늘면서 생기는 부하와 장애 문제를 해결해 나간다. 이 장은 그 과정에서 웹 계층과 데이터 계층의 구조가 어떻게 달라지는지 보여 준다.

## 서버 한 대에서 시작하기

처음에는 웹 애플리케이션, 데이터베이스, 캐시를 모두 한 서버에서 실행한다. 사용자가 도메인에 접속하면 DNS에서 IP 주소를 얻고, 해당 주소로 HTTP 요청을 보낸다. 웹 서버는 요청을 처리한 뒤 HTML이나 JSON으로 응답한다.

사용자가 늘면 웹 서버와 데이터베이스를 분리한다. 웹 요청을 처리하는 계층과 데이터를 저장하는 계층을 나누면 각각 필요한 만큼 확장할 수 있다.

데이터베이스는 데이터의 형태와 접근 방식에 따라 고른다. 관계형 DB는 테이블로 데이터를 표현하고 SQL로 여러 테이블을 조인할 수 있다. 책은 관계형 DB를 우선 검토하되, 다음 조건에서는 NoSQL도 고려하도록 설명한다.

- 아주 낮은 응답 지연이 필요하다.
- 비정형 데이터를 다룬다.
- 데이터를 직렬화하고 역직렬화하는 정도면 충분하다.
- 아주 많은 데이터를 저장해야 한다.

## 서버의 성능을 높일까, 대수를 늘릴까

| 방법                 | 확장하는 대상            | 특징                             |
| -------------------- | ------------------------ | -------------------------------- |
| 수직 확장(Scale Up)  | 한 서버의 CPU, 메모리 등 | 단순하지만 하드웨어 한계가 있다. |
| 수평 확장(Scale Out) | 서버의 수                | 여러 서버로 부하를 나눈다.       |

트래픽이 적을 때는 수직 확장이 간단한 선택이다. 다만 자원을 무한히 늘릴 수는 없고, 서버 한 대에 장애가 나면 서비스도 중단된다. 서버의 사양을 높이는 것만으로는 장애에 대비할 수 없다.

수평 확장에서는 여러 웹 서버 앞에 **로드밸런서**를 둔다. 사용자는 로드밸런서의 공개 IP로 접속하고, 로드밸런서는 사설 IP로 웹 서버에 요청을 전달한다. 정상인 서버들로 요청을 나누고, 트래픽이 늘면 서버를 추가해 부하를 분산한다.

## 데이터베이스의 읽기와 쓰기 나누기

웹 서버를 늘려도 데이터베이스가 한 대라면 데이터 계층에는 여전히 부하와 장애 문제가 남는다. 책에서는 주 데이터베이스의 데이터를 부 데이터베이스로 복제하는 구성을 소개한다.

- **주 DB**: 데이터 추가, 수정, 삭제 등 쓰기를 처리한다.
- **부 DB**: 주 DB의 사본을 받아 읽기를 처리한다.

읽기 요청이 많은 서비스에서는 여러 부 DB로 조회를 나눌 수 있다. 데이터 사본을 다른 서버나 지역에 두면 일부 서버에 장애가 나도 서비스를 이어가는 데 도움이 된다.

![사용자가 로드밸런서에 접속하면 요청을 웹 서버 두 대로 분산한다. 두 웹 서버 모두 주 DB에 쓰고 부 DB에서 읽는다. 복제 방향은 주 DB에서 부 DB로 향한다.](/static/images/books/system-design-interview/web-and-database.svg)

부 DB에 장애가 나면 다른 부 DB가 읽기를 맡거나, 일시적으로 주 DB가 읽기까지 처리할 수 있다. 주 DB에 장애가 나면 부 DB를 새로운 주 DB로 승격하는 방식으로 대응한다.

다만 **부 DB의 데이터가 최신 상태가 아닐 수 있다.** 책도 이 때문에 실제 운영 환경의 복구가 더 복잡하다고 설명한다. 복제본이 있다는 것과 최신 데이터까지 보장된다는 것은 구분해서 봐야 한다.

## 자주 읽는 데이터는 캐시에 두기

캐시는 자주 조회하는 데이터나 계산 비용이 큰 결과를 메모리에 보관한다. 같은 데이터를 다시 요청할 때 DB를 매번 읽지 않아도 되므로 응답 시간이 줄고 DB의 부하도 낮아진다. 캐시 계층을 따로 확장할 수도 있다.

책에서 설명하는 조회 흐름은 다음과 같다.

1. 웹 서버가 캐시에 데이터가 있는지 확인한다.
2. 있으면 그 값을 반환한다.
3. 없으면 DB에서 읽어 캐시에 저장한 뒤 반환한다.

갱신은 드물고 조회는 잦은 데이터에 적합하다. 다만 이 장에서 다루는 메모리 캐시는 휘발성이 있으므로, 중요한 데이터의 영구 보관은 지속성 저장소가 맡아야 한다.

| 고려할 점        | 확인할 내용                                                           |
| ---------------- | --------------------------------------------------------------------- |
| 만료 시간(TTL)   | 너무 짧으면 DB를 자주 읽고, 너무 길면 오래된 데이터를 반환할 수 있다. |
| 일관성           | DB의 원본과 캐시의 사본이 달라질 수 있다.                             |
| 장애             | 캐시 한 대에 의존하면 단일 장애 지점(SPOF)이 될 수 있다.              |
| 용량과 방출 정책 | 메모리가 찼을 때 어떤 데이터를 내보낼지 정한다.                       |

방출 정책에는 가장 오래 사용하지 않은 데이터를 제거하는 **LRU**, 사용 빈도가 가장 낮은 데이터를 제거하는 **LFU**, 먼저 들어온 데이터를 먼저 제거하는 **FIFO**가 있다.

## 정적 콘텐츠는 CDN으로 제공하기

CDN은 지리적으로 분산된 서버에서 정적 콘텐츠를 제공하는 네트워크다. 이미지, 영상, CSS, JavaScript 등을 사용자와 가까운 서버에서 전달해 로딩 시간을 줄인다.

![캐시와 CDN의 역할 비교. 웹 서버는 데이터 캐시를 확인하고, 캐시에 없으면 DB에서 조회해 캐시에 저장한다. 사용자는 정적 파일을 CDN에 요청하며, CDN에 파일이 없으면 원본 서버에서 가져와 보관한다.](/static/images/books/system-design-interview/cache-and-cdn.svg)

CDN에 파일이 없으면 원본 서버에서 가져온다. 가져온 파일은 TTL 동안 캐시에 보관하고, 이후 요청에는 캐시된 파일을 반환한다. 정적 파일은 CDN에서, 애플리케이션 요청은 웹 서버에서 처리하도록 경로가 나뉜다.

CDN을 사용할 때는 전송 비용, 만료 시간, 장애 시 원본 서버에서 가져올 방법을 고려한다. 만료 전 파일을 바꿔야 한다면 CDN의 무효화 API를 사용하거나, `image.png?v=2`처럼 URL에 버전을 붙이는 방법이 있다.

## 웹 서버에서 상태 분리하기

세션을 특정 웹 서버에 저장하면 같은 사용자의 요청을 계속 그 서버로 보내야 한다. 로드밸런서의 고정 세션(sticky session)으로 처리할 수 있지만, 서버를 추가하거나 제거하기가 까다로워지고 장애 대응도 복잡해진다.

세션 같은 상태 정보를 **공유 저장소**로 옮기면 어느 웹 서버든 요청을 처리할 수 있다. 이것이 이 장에서 말하는 무상태 웹 계층이다. 상태를 없애는 것이 아니라, 개별 웹 서버가 보관하지 않도록 바꾸는 것이다.

![상태를 웹 서버 안에 두면 사용자의 요청을 같은 서버로 보내야 한다. 공유 저장소로 옮기면 웹 서버 1과 2가 같은 상태 정보에 접근할 수 있어 어느 서버로든 요청을 보낼 수 있다.](/static/images/books/system-design-interview/stateless-web.svg)

공유 저장소로는 관계형 DB, Redis나 Memcached 같은 캐시 시스템, NoSQL 등을 사용할 수 있다. 책의 예시는 확장이 간편하다는 이유로 NoSQL을 선택한다. 웹 계층에서 상태를 분리하면 트래픽에 따라 웹 서버를 자동으로 추가하거나 제거하기도 쉬워진다.

## 여러 데이터 센터로 확장하기

여러 지역의 사용자를 지원하고 한 지역의 장애에도 대비하려면 데이터 센터를 여러 곳에 둘 수 있다. 책에서는 **geoDNS**로 사용자 위치에 따라 도메인을 서로 다른 IP 주소로 변환해 적절한 데이터 센터로 안내한다.

한 데이터 센터에 장애가 나면 정상인 곳으로 트래픽을 우회한다. 이 구성을 운영하려면 세 가지를 함께 해결해야 한다.

- **트래픽 우회**: 사용자를 적절한 데이터 센터로 보내고 장애에 대응한다.
- **데이터 동기화**: 다른 데이터 센터로 연결돼도 필요한 데이터를 사용할 수 있게 한다.
- **테스트와 배포**: 여러 위치에서 동작을 확인하고 동일한 서비스를 배포한다.

## 오래 걸리는 작업은 메시지 큐로 분리하기

메시지 큐는 소비자가 꺼낼 때까지 메시지를 보관한다. 책에서는 이 내구성과 비동기 통신을 주요 특성으로 설명한다. 생산자가 메시지를 넣으면 소비자가 꺼내 작업을 수행한다. 두 서비스가 서로의 작업 완료를 직접 기다리지 않으므로 결합을 느슨하게 만들 수 있다.

책에서는 사진 보정을 예로 든다. 웹 서버는 보정 작업을 큐에 넣고, 별도의 작업 프로세스가 가져가 처리한다. 작업이 쌓이면 작업 프로세스를 더 추가하고, 큐가 대부분 비어 있다면 수를 줄일 수 있다.

생산자와 소비자를 각각 확장할 수 있다는 점이 핵심이다. 소비자가 잠시 중단돼도 생산자는 메시지를 넣을 수 있고, 생산자가 중단된 동안에도 소비자는 이미 보관된 메시지를 처리할 수 있다.

## 로그, 메트릭, 자동화로 운영하기

서버가 많아지면 문제를 찾고 현재 상태를 파악할 도구도 필요하다.

- **로그**: 오류 로그를 모아 검색하고 문제를 추적한다.
- **메트릭**: CPU·메모리·디스크 I/O, DB·캐시의 성능, 일별 활성 사용자·수익·재방문 같은 지표를 살핀다.
- **자동화**: 지속적 통합(CI)으로 변경 사항을 검증하고, 빌드·테스트·배포의 반복 작업을 줄인다.

웹 서버와 DB를 늘리는 것뿐 아니라, 늘어난 시스템을 운영할 방법도 함께 갖춰야 한다.

## 데이터가 더 늘면 샤딩하기

DB도 수직 확장할 수 있지만 하드웨어와 비용의 한계가 있고, 한 서버에 의존하는 위험도 남는다. **샤딩**은 데이터를 여러 데이터베이스에 나눠 저장해 수평으로 확장하는 방법이다.

복제가 같은 데이터의 사본을 두는 방식이라면, 샤딩은 데이터를 나누는 방식이다. 책의 예시에서는 같은 스키마를 쓰는 네 샤드에 사용자 데이터를 나누고, `user_id % 4`의 결과로 저장할 샤드를 정한다.

![사용자 ID를 4로 나눈 나머지에 따라 샤드를 고른다. 샤드 0에는 ID 0, 4, 8, 12가, 샤드 1에는 1, 5, 9, 13이 저장된다. 샤드 2와 3도 같은 규칙으로 서로 다른 데이터를 보관한다.](/static/images/books/system-design-interview/sharding.svg)

샤딩 키는 데이터가 고르게 나뉘도록 골라야 한다. 도입 후에는 새로운 문제도 생긴다.

- **재샤딩**: 데이터가 너무 많아지거나 샤드 간 분포가 불균형해지면 데이터를 다시 배치해야 한다.
- **핫스폿**: 인기 사용자처럼 특정 데이터에 요청이 몰리면 한 샤드만 과부하에 걸릴 수 있다.
- **조인과 비정규화**: 여러 샤드에 걸친 조인이 어려워져, 한 테이블에서 조회할 수 있도록 데이터를 비정규화하는 방법을 고려한다.

책은 관계형 DB가 꼭 필요하지 않은 기능을 NoSQL로 옮겨 부하를 줄이는 방법도 소개한다. 규모 확장은 여기서 끝나지 않는다. 부하를 관찰하며 각 계층을 독립적으로 확장하고, 다중화와 모니터링·자동화를 보완하는 과정을 반복한다.

## 보충 설명: 캐시 전략의 이름

책에서는 앞에서 정리한 캐시 조회 흐름을 **읽기 주도형 캐시**(read-through)라고 부른다. 한편 [Microsoft의 Cache-Aside 패턴 문서](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside)는 애플리케이션이 캐시 미스 시 DB를 조회하고 캐시를 채우는 방식을 **Cache-Aside**로 설명한다. 다른 자료와 비교할 때는 명칭뿐 아니라 DB 조회와 캐시 저장을 누가 수행하는지도 확인하면 좋다.
