시스템을 설계할 때는 초당 몇 건의 요청을 처리해야 하는지, 데이터를 얼마나 저장해야 하는지부터 가늠해야 한다. 개략적인 규모 추정은 가정과 대략적인 성능 수치를 바탕으로 필요한 용량을 계산하고, 설계가 요구사항을 감당할 수 있을지 판단하는 방법이다.

## 데이터 단위와 2의 제곱수

1바이트는 8비트이며, ASCII 문자 하나는 1바이트를 차지한다. 용량을 계산할 때는 먼저 단위를 맞춘다.

2의 제곱수는 다음과 같이 근사해서 기억할 수 있다.

| 바이트 수 | 근사값            | 대략적인 용량 |
| --------- | ----------------- | ------------- |
| $2^{10}$  | 약 1천 바이트     | 1 KB          |
| $2^{20}$  | 약 1백만 바이트   | 1 MB          |
| $2^{30}$  | 약 10억 바이트    | 1 GB          |
| $2^{40}$  | 약 1조 바이트     | 1 TB          |
| $2^{50}$  | 약 1,000조 바이트 | 1 PB          |

정확한 값은 $2^{10} = 1,024$다. 규모를 빠르게 가늠할 때는 이를 약 1,000으로 놓고 계산한다.

## 응답 지연의 차이

연산마다 걸리는 시간은 크게 다르다. 메모리 접근과 디스크 탐색, 데이터 센터 사이의 통신을 비슷한 비용으로 생각하면 성능을 잘못 추정할 수 있다.

아래는 책에서 2020년을 기준으로 소개한 근사값 중 일부다. 실제 시간은 하드웨어와 실행 환경에 따라 달라진다.

| 작업                                 | 응답 지연 |
| ------------------------------------ | --------- |
| L1 캐시 참조                         | 약 1 ns   |
| 주 메모리 참조                       | 약 100 ns |
| SSD의 임의 위치 데이터 읽기          | 약 16 μs  |
| 같은 데이터 센터 안에서 패킷 왕복    | 약 500 μs |
| 디스크 탐색                          | 약 2 ms   |
| 캘리포니아와 네덜란드 사이 패킷 왕복 | 약 150 ms |

시간 단위도 함께 익혀 둔다.

```text
1 μs = 1,000 ns
1 ms = 1,000 μs
1초  = 1,000 ms
```

메모리는 디스크보다 빠르고, 디스크 탐색은 비용이 크다. 단순한 압축 알고리즘은 빠르게 동작하므로 인터넷으로 데이터를 보내기 전에 압축하는 방법도 고려한다. 데이터 센터가 여러 지역에 나뉘어 있다면 지역 사이의 통신 시간도 계산에 넣어야 한다.

## 가용률과 장애 시간

가용성은 시스템이 오랜 시간 중단 없이 운영될 수 있는 능력이다. 이를 백분율로 나타낸 값이 가용률이며, 100%라면 관측한 기간에 중단이 없었다는 뜻이다.

SLA(Service Level Agreement)는 서비스 제공자와 고객 사이의 합의다. 서비스의 가용시간 같은 제공 수준을 명시한다.

가용률을 장애 시간으로 바꿔 보면 목표의 차이가 더 분명해진다.

| 가용률   | 연간 장애 시간 |
| -------- | -------------- |
| 99%      | 약 3.65일      |
| 99.9%    | 약 8.8시간     |
| 99.99%   | 약 52.6분      |
| 99.999%  | 약 5.3분       |
| 99.9999% | 약 31.6초      |

9가 하나 더 붙을 때마다 허용되는 장애 시간은 10분의 1로 줄어든다.

## 트위터의 QPS와 저장량 추정

실제 트위터의 통계가 아닌 연습용 가정으로 계산한다.

### 가정

| 항목                                     | 값     |
| ---------------------------------------- | ------ |
| 월간 활성 사용자(MAU)                    | 3억 명 |
| 매일 사용하는 사용자 비율                | 50%    |
| 사용자 한 명의 하루 평균 트윗 수         | 2건    |
| 미디어를 포함한 트윗의 비율              | 10%    |
| 미디어를 포함한 트윗 한 건의 미디어 크기 | 1 MB   |
| 데이터 보관 기간                         | 5년    |

### 평균 QPS와 최대 QPS

QPS(Queries Per Second)는 초당 처리하는 질의 수다. 이 예제에서는 트윗 작성 요청을 기준으로 계산한다.

일간 활성 사용자(DAU)는 월간 활성 사용자의 50%이므로 1.5억 명이다. 각 사용자가 하루에 트윗을 2건씩 올리면 하루 작성량은 3억 건이다.

```text
DAU = 3억 명 × 50% = 1.5억 명
하루 트윗 수 = 1.5억 명 × 2건 = 3억 건

평균 QPS = 3억 건 ÷ (24 × 3,600초)
         ≈ 3,500건/초
```

최대 QPS는 이 예제에서 평균의 2배로 가정해 약 7,000건/초로 잡는다.

### 미디어 저장량

하루 트윗 3억 건 중 10%에 미디어가 붙는다. 미디어 크기를 건당 1 MB로 놓으면 하루에 필요한 미디어 저장 공간은 약 30 TB다.

```text
하루 미디어 저장량 = 3억 건 × 10% × 1 MB
                   = 30 TB/일

5년 미디어 저장량 = 30 TB/일 × 365일 × 5
                  = 54,750 TB
                  ≈ 55 PB
```

이 계산에서는 1 TB = 1,000,000 MB, 1 PB = 1,000 TB로 환산했다. 약 55 PB는 미디어를 보관하는 데 필요한 용량이다.

## 추정할 때 남겨야 할 것

개략적인 규모 추정에서는 계산 결과만큼 가정을 세우고 계산을 이어 가는 과정이 중요하다.

- **근사값으로 계산한다.** 복잡한 수를 그대로 계산하기보다 적절히 반올림해 규모를 빠르게 파악한다.
- **가정을 적어 둔다.** 활성 사용자 비율, 요청 빈도, 데이터 크기, 보관 기간처럼 결과를 좌우하는 조건을 남긴다.
- **숫자에 단위를 붙인다.** 5라고만 쓰면 5 KB인지 5 MB인지 알 수 없다. 요청량도 하루 몇 건인지 초당 몇 건인지 구분한다.

QPS, 최대 QPS, 저장량, 캐시 용량, 서버 수 등을 같은 방식으로 추정할 수 있다. 가정과 단위가 명확하면 조건이 바뀌어도 어느 부분을 다시 계산해야 하는지 알 수 있다.

## 보충 설명: KB와 KiB

단위를 정확히 구분하면 1 KB는 1,000바이트이고 1 KiB는 1,024바이트다. MB와 MiB, GB와 GiB도 같은 구분을 따른다. ([NIST 단위 안내](https://physics.nist.gov/cuu/Units/binary.html)) 앞의 2의 제곱수 표는 규모를 가늠하기 위한 근사표이며, 저장량을 계산할 때는 어느 기준을 쓸지 정해 두는 편이 좋다.
