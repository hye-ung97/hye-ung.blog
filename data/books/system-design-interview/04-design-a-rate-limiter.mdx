한 사용자가 게시글 작성 API를 짧은 시간에 수천 번 호출한다면, 그 요청을 모두 처리해도 될까? 서버가 견디더라도 다른 사용자의 요청이 밀릴 수 있다. 외부 서비스를 호출하는 API라면 비용도 늘어난다.

**처리율 제한 장치**(rate limiter)는 정해진 기준에 따라 일정 시간 동안 허용할 요청량을 통제한다. 사용자별로 초당 게시글 작성 횟수를 제한하거나, 같은 IP에서 하루에 만들 수 있는 계정 수를 제한하는 식이다. 한도를 넘은 요청은 API 서버로 전달하지 않고 거절할 수 있다.

이를 구현하려면 누구의 요청을 제한할지부터 정해야 한다. 사용량을 어디에 보관하고, 서버가 여러 대일 때 어떻게 같은 한도를 적용할지도 함께 살펴본다.

## 무엇을 보호하고 무엇을 제한할까

처리율 제한을 두는 목적은 크게 세 가지다.

- **자원 보호**: DoS 공격이나 과도한 요청에 따른 CPU, 메모리, 연결 등의 자원 고갈을 완화한다.
- **비용 통제**: 서버의 처리량과 호출마다 과금되는 외부 API의 사용량을 조절한다.
- **과부하 방지**: 봇이나 잘못 구현한 클라이언트가 반복해서 보내는 요청을 걸러 낸다.

여기서는 서버 측 API의 요청을 제한하는 시스템을 설계한다. 구현에 앞서 정할 조건은 다음과 같다.

| 정할 것       | 예시                                                     |
| ------------- | -------------------------------------------------------- |
| 제한 대상     | 사용자 ID, IP 주소, 기기, API, 서비스 전체               |
| 시간과 허용량 | 사용자별 초당 2회, IP별 하루 10회                        |
| 규칙의 유연성 | API마다 서로 다른 규칙을 적용할 수 있는가                |
| 배치          | 애플리케이션 내부에 둘 것인가, 별도 미들웨어로 둘 것인가 |
| 규모          | 여러 서버와 프로세스가 같은 제한을 공유해야 하는가       |
| 초과 요청     | 즉시 거절할 것인가, 나중에 처리해도 되는가               |

제한 기능은 정한 한도를 정확하게 적용해야 한다. 다만 모든 요청이 검사를 거치는 만큼 응답이 지나치게 느려져서는 안 된다. 상태를 저장하는 데 쓰는 메모리도 적어야 하고, 서버가 여러 대여도 같은 사용량을 기준으로 판단해야 한다. 요청을 막았다면 이유를 알려 주고, 제한 장치에 장애가 났을 때 서비스가 어떻게 동작할지도 정한다.

## 제한 장치는 어디에 둘까

클라이언트에서도 요청 속도를 조절할 수 있다. 하지만 모든 클라이언트가 제한을 지킨다고 보장할 수는 없다. 요청을 변조할 수도 있으므로, 서버를 보호하려면 요청을 받는 쪽에서 한도를 검사해야 한다.

서버 측에서는 API 서버 안에 제한 로직을 넣거나, API 서버 앞의 미들웨어에 둘 수 있다. 이미 인증과 IP 허용 목록 등을 처리하는 API 게이트웨이가 있다면 그곳의 제한 기능을 활용하는 방법도 있다.

![처리율 제한 장치의 두 가지 배치. 위쪽은 API 서버 내부에 제한 로직을 두고, 아래쪽은 API 서버 앞의 별도 미들웨어에서 요청을 검사한다.](/static/images/books/system-design-interview/ch04/placement.svg)

초당 2회만 허용하는 미들웨어에 같은 초 동안 요청 3개가 들어온다고 하자. 앞선 두 요청은 API 서버로 전달하고, 세 번째 요청은 차단한 뒤 클라이언트에 429 응답을 돌려준다.

![초당 2회 한도에서 세 요청을 처리하는 흐름. 요청 1과 2는 API 서버로 전달한다. 요청 3은 제한 미들웨어에서 차단하고 429 Too Many Requests를 클라이언트로 반환한다.](/static/images/books/system-design-interview/ch04/request-flow.svg)

어디에 둘지는 지금 쓰는 기술과 운영 여건에 따라 달라진다. 직접 구현하면 알고리즘을 자유롭게 고를 수 있지만 개발과 운영도 맡아야 한다. 기존 게이트웨이에 공통 기능을 모으려면 원하는 알고리즘과 규칙을 지원하는지 먼저 확인한다. 직접 만들 인력이 부족할 때는 관리형 게이트웨이를 고려할 수 있다.

## 다섯 가지 알고리즘

같은 ‘분당 100회’라는 설정도 알고리즘에 따라 동작이 달라진다. 잠깐 몰리는 요청을 바로 받아줄지, 큐에 두고 일정한 속도로 처리할지, 최근 1분의 요청 수를 엄격히 셀지에 따라 선택이 달라진다.

### 토큰 버킷: 남겨 둔 허용량으로 요청 집중을 받아들인다

정해진 용량의 버킷에 토큰을 일정한 속도로 채운다. 요청 하나를 허용할 때 토큰 하나를 꺼낸다. 토큰이 없으면 요청을 거절하고, 버킷이 가득 차면 새로 공급된 토큰은 버린다.

설정값은 **버킷 용량**과 **토큰 공급률**이다. 용량은 모아 둘 수 있는 최대 허용량이고, 공급률은 시간이 지나면서 허용량이 회복되는 속도다.

아래 그림은 용량이 4이고 초당 토큰 2개를 공급하는 버킷이다. 이미 토큰이 4개 있으면 추가로 공급된 토큰은 버린다.

그림 아래에서는 토큰이 3개 남은 상태에서 요청 5개가 들어온다. 추가 보충 전에 토큰을 하나씩 소비하며 3개를 전달하고, 토큰을 얻지 못한 나머지 2개는 버린다.

![토큰 공급과 요청 처리의 분기. 용량 4인 버킷에 초당 2개를 공급하며, 가득 차면 추가 토큰을 버린다. 아래 예시는 사용 가능한 토큰 3개로 입력 요청 5개를 검사해 3개를 전달하고 2개를 버리는 흐름이다. 전달할 때 요청마다 토큰 1개를 소비한다.](/static/images/books/system-design-interview/ch04/buckets.svg)

이번에는 **용량 4인 버킷에 매분 한 번 토큰 4개를 한꺼번에 보충**하는 별도 설정으로 시간에 따른 변화를 살펴보자. `1:00:00`에 토큰 4개로 시작해 요청 하나를 허용하면 3개가 남는다. `1:00:05`에 요청 3개가 오면 모두 허용하고 토큰을 전부 소비한다. 다음 보충 시점 전까지는 토큰이 추가되지 않으므로 `1:00:20`의 요청은 거절하고, `1:01:00`에 토큰 4개를 한꺼번에 보충한다.

![토큰 버킷의 네 가지 상태 변화. 용량 4인 버킷에 매분 한 번 토큰 4개를 한꺼번에 보충한다. 1:00:00에는 요청 1개를 허용해 4개에서 3개가 된다. 1:00:05에는 요청 3개를 모두 허용해 0개가 된다. 1:00:20의 요청은 거절하고, 1:01:00에는 토큰 4개를 한꺼번에 보충한다.](/static/images/books/system-design-interview/ch04/token-bucket-states.svg)

토큰이 남아 있으면 짧은 시간에 몰리는 요청, 즉 **버스트**(burst)를 받아들일 수 있다. 구현이 비교적 단순하고 저장할 상태도 작다. 다만 같은 공급률이라도 버킷 용량에 따라 받아줄 수 있는 버스트의 크기가 달라지므로 두 값을 함께 조정해야 한다.

버킷을 몇 개 둘지도 제한 기준에 달려 있다.

- 사용자마다 API별 한도를 적용한다면 `(사용자 ID, API)`마다 버킷을 둔다.
- IP별 한도라면 IP마다 버킷을 둔다.
- 서비스 전체의 처리량을 제한한다면 모든 요청이 공통 버킷을 사용한다.

### 누출 버킷: 큐에 담고 일정한 속도로 내보낸다

누출 버킷(leaky bucket)은 요청을 FIFO 큐에 넣고 일정한 속도로 꺼내 처리하는 방식으로 구현할 수 있다. 먼저 들어온 요청부터 처리하며, 큐가 가득 차면 새 요청을 거절한다.

설정값은 **큐 용량**과 **배출 속도**다. 큐 용량은 대기시킬 수 있는 요청 수를, 배출 속도는 단위 시간에 꺼낼 요청 수를 정한다.

그림에서는 입력 요청 5개 중 3개가 큐를 거쳐 전달된다. 나머지 2개는 도착했을 때 큐가 가득 차 있어 버려진다. 이 숫자는 해당 요청 묶음의 처리 결과이며, 큐의 최대 용량이나 초당 처리율은 별도로 정한다.

![누출 버킷의 요청 처리 분기. 입력 요청 5개 중 큐에 들어간 3개는 일정한 속도로 시스템에 전달하고, 큐가 가득 찼을 때 도착한 2개는 버린다. 5개·3개·2개는 요청 묶음 예시의 개수이며 큐 용량이나 초당 처리율을 나타내지 않는다.](/static/images/books/system-design-interview/ch04/leaky-bucket.svg)

토큰 버킷은 쌓아 둔 허용량을 바로 쓸 수 있다. 누출 버킷은 요청을 대기시켜 일정한 속도로 내보낸다. 요청을 받는 시스템이 안정적인 속도로 작업을 처리해야 할 때 적합하다.

큐 크기를 제한해 메모리 사용량을 통제할 수 있지만, 요청이 몰리면 대기 시간이 길어진다. 먼저 들어온 요청이 큐에 쌓여 있는 동안 새 요청은 거절될 수 있다. 큐 용량과 배출 속도를 함께 조정해야 하는 이유다.

### 고정 윈도 카운터: 고정된 시간 구간마다 센다

시간을 1초나 1분 같은 고정 구간으로 나누고, 각 구간에 카운터를 둔다. 요청이 오면 해당 구간의 사용량을 확인하고, 한도까지 허용한다. 다음 구간이 열리면 새로운 카운터로 시작한다.

초당 3회가 한도이고, 다섯 초 동안 각각 3개, 6개, 4개, 2개, 5개 요청이 들어오는 경우를 보자. 각 초에 최대 3개만 허용하므로 차단되는 요청은 순서대로 0개, 3개, 1개, 0개, 2개다. 이전 초에 거절된 요청이 있어도 새 초의 카운터는 새로 시작한다.

![초당 3회 한도에서의 고정 윈도 동작. 1:00:00부터 각 초에 3개, 6개, 4개, 2개, 5개 요청이 도착한다. 허용 수는 3개, 3개, 3개, 2개, 3개이며 나머지는 차단한다.](/static/images/books/system-design-interview/ch04/fixed-window-counter.svg)

이해하기 쉽고 메모리도 적게 사용한다. 정각마다 허용량을 새로 부여하는 정책에도 잘 맞는다. 문제는 **구간의 경계**다.

이번에는 분당 5회가 한도라고 하자. `2:00:00~2:01:00`에 5개, `2:01:00~2:02:00`에 5개를 허용한다. 앞 구간의 뒤쪽과 다음 구간의 앞쪽에 요청이 몰리면, `2:00:30~2:01:30`의 1분 안에 10개가 모두 들어갈 수 있다. 각 고정 구간에서는 규칙을 지켰지만, 경계를 가로지르는 1분에는 한도의 두 배를 처리한 셈이다.

![분당 5회 한도의 경계 집중 문제. 인접한 두 고정 구간에 각각 5개 요청을 허용한다. 요청 묶음은 시간순으로 3개, 2개, 1개, 4개이며, 2:00:30부터 2:01:30까지의 1분에 10개가 모두 포함된다.](/static/images/books/system-design-interview/ch04/fixed-window.svg)

따라서 ‘고정된 각 1분에 5회’와 ‘어느 시점에서 보더라도 최근 1분에 5회’는 다른 조건이다. 후자가 필요하다면 이동 윈도 방식을 검토한다.

### 이동 윈도 로그: 최근 구간의 요청 시각을 보관한다

요청마다 도착 시각을 기록하고, 현재 시점에서 최근 일정 시간에 들어온 기록을 센다. 시각순으로 정리할 수 있는 Redis 정렬 집합(sorted set) 같은 자료구조를 사용할 수 있다.

여기서 설명하는 방식은 다음 순서로 판단한다.

1. 현재 윈도보다 오래된 기록을 제거한다.
2. 새 요청의 시각을 로그에 추가한다.
3. 로그 크기가 한도 이하이면 허용하고, 초과하면 거절한다.

**거절한 요청의 기록도 남긴다.** 한도를 넘겼다는 이유로 방금 추가한 기록을 되돌리지는 않는다.

최근 1분에 2회를 허용하는 예를 보자. 요청이 들어올 때마다 오래된 기록을 지우고 새 요청 시각을 넣은 결과는 다음과 같다.

| 도착 시각 | 만료 기록을 지우고 새 요청을 넣은 로그 | 결과               |
| --------- | -------------------------------------- | ------------------ |
| `1:00:01` | `[1:00:01]`                            | 허용               |
| `1:00:30` | `[1:00:01, 1:00:30]`                   | 허용               |
| `1:00:50` | `[1:00:01, 1:00:30, 1:00:50]`          | 거절, 새 기록 유지 |
| `1:01:40` | `[1:00:50, 1:01:40]`                   | 허용               |

`1:01:40` 시점에는 `1:00:40`보다 오래된 `1:00:01`, `1:00:30` 기록을 제거한다. 앞서 거절한 `1:00:50` 기록은 아직 최근 1분 안에 있으므로 남아 있다. 새 요청을 추가한 뒤 로그가 2개이므로 요청을 허용한다.

![이동 윈도 로그의 네 단계. 1:00:01과 1:00:30 요청은 허용한다. 1:00:50 요청은 거절하되 시각을 기록한다. 1:01:40에는 오래된 두 기록을 지우고 1:00:50과 새 시각만 남아 요청을 허용한다.](/static/images/books/system-design-interview/ch04/sliding-log.svg)

실제 요청 시각을 확인하므로 고정 구간의 경계에 영향을 받지 않고 최근 구간의 요청 수를 정확히 셀 수 있다. 대신 요청마다 시각을 보관해야 한다. 거절한 요청까지 기록하므로 트래픽이 많을수록 메모리 부담이 커진다.

### 이동 윈도 카운터: 이전 구간을 가중해서 추정한다

요청 시각을 모두 저장하는 대신 현재 구간과 직전 구간의 카운터를 이용한다. 직전 구간의 요청이 고르게 들어왔다고 가정하고, 최근 윈도에 걸치는 비율만큼 반영한다.

```text
추정 요청 수
  = 현재 구간의 요청 수
  + 직전 구간의 요청 수 × 직전 구간이 최근 윈도와 겹치는 비율
```

현재 1분 구간의 30%가 지났다면, 최근 1분은 직전 구간의 70%와 현재 구간의 30%를 포함한다. 직전 구간에 5회, 현재 구간에 3회가 있었다면 추정치는 다음과 같다.

```text
3 + 5 × 0.7 = 6.5
```

![이동 윈도 카운터의 요청 분포와 가중 계산. 직전 1분에 5개, 현재 1분에 3개 요청이 있다. 현재 구간의 30퍼센트가 지나 직전 구간의 70퍼센트를 반영한다. 한도는 분당 7회이며 추정치 6.5를 내림한 6을 기준으로 다음 요청 하나를 허용한다.](/static/images/books/system-design-interview/ch04/sliding-counter.svg)

한도를 분당 7회로 두고, 이 예에서는 **신규 요청을 넣기 전 추정치를 내림한 뒤 한도와 비교**한다. `6.5`를 내림한 값은 6이므로 새 요청을 허용하고 현재 카운터를 4로 늘린다. 같은 시각에 다음 요청이 오면 `4 + 5 × 0.7 = 7.5`이고, 내림한 값이 7이므로 거절한다.

요청별 시각을 저장하지 않아 메모리를 적게 쓰면서도 고정 윈도의 경계 문제를 줄일 수 있다. 다만 직전 구간의 어느 시점에 요청이 몰렸는지는 알 수 없다. 요청이 고르게 들어왔다고 가정한 추정치이므로 실제 개수와는 차이가 날 수 있다.

### 알고리즘을 고르는 기준

| 알고리즘         | 관리하는 상태          | 적합한 조건                      | 주의할 점                        |
| ---------------- | ---------------------- | -------------------------------- | -------------------------------- |
| 토큰 버킷        | 남은 토큰과 보충 정보  | 잠깐의 요청 집중을 허용한다      | 용량과 공급률을 조정해야 한다    |
| 누출 버킷        | 대기 요청 큐           | 일정한 출력 속도가 필요하다      | 대기 시간과 큐 포화가 생긴다     |
| 고정 윈도 카운터 | 구간별 요청 수         | 단순한 구간별 한도가 필요하다    | 경계에서 요청이 집중될 수 있다   |
| 이동 윈도 로그   | 요청별 도착 시각       | 최근 구간을 정확히 판단한다      | 요청 수에 따라 메모리를 사용한다 |
| 이동 윈도 카운터 | 현재·직전 구간 요청 수 | 적은 상태로 경계 집중을 완화한다 | 추정 오차가 있다                 |

## 기본 구조: 미들웨어와 공유 저장소

사용자별 한도를 적용하려면 사용자마다 사용량을 따로 세어야 한다. 같은 사용자라도 API별 한도가 다르다면 사용자와 API의 조합으로 상태를 나눈다.

모든 요청이 이 상태를 확인하므로 조회가 느리면 API 응답도 늦어진다. 여기서는 메모리에서 빠르게 조회하고 만료시간도 지정할 수 있는 Redis에 상태를 둔다. 카운터는 `INCR`로 늘리고, 시간이 지나면 필요 없어지는 키는 `EXPIRE`로 만료시킬 수 있다.

저장하는 정보는 알고리즘에 따라 다르다. 고정 윈도는 카운터를, 이동 윈도 로그는 요청 시각의 집합을 관리한다. 토큰 버킷에는 남은 토큰 수와 보충 시점을 판단할 정보가 필요하다.

![Redis를 사용하는 기본 처리율 제한 구조. 클라이언트는 제한 미들웨어에 요청한다. 미들웨어는 Redis의 요청 수와 시각을 조회하고 갱신하며, 허용된 요청을 API 서버로 전달한다.](/static/images/books/system-design-interview/ch04/basic-architecture.svg)

요청 하나가 들어왔을 때의 흐름을 따라가 보자.

1. 제한 미들웨어가 요청을 받는다.
2. 요청에 적용할 규칙과 제한 대상을 찾는다.
3. Redis의 상태를 기준으로 허용 여부를 판단하고 상태를 갱신한다.
4. 허용된 요청은 API 서버로 전달한다.
5. 초과 요청에는 `429 Too Many Requests`를 반환한다.

실제 구현에서는 한도를 검사한 뒤 상태를 갱신하기 전에 다른 요청이 끼어들 수 있다. 이 흐름을 여러 명령으로 나누어 실행할 때 생기는 문제는 분산 환경을 살펴볼 때 다시 다룬다.

## 상세 설계: 규칙과 요청 상태를 나눈다

규칙은 ‘얼마나 허용할 것인가’를 정하고, 요청 상태는 ‘지금까지 얼마나 사용했는가’를 나타낸다. 자주 갱신되는 사용량과 시각 정보는 Redis에 두고, 규칙은 작업 프로세스가 설정 파일에서 읽어 캐시에 반영한다. 운영 중 규칙이 바뀌어도 이 캐시를 갱신하면 된다. 미들웨어는 요청마다 디스크에 접근하지 않고 캐시에서 규칙을 가져온다.

![규칙 관리와 초과 요청의 상세 처리 흐름. 작업 프로세스가 규칙 파일을 읽어 캐시에 반영한다. 제한 미들웨어는 규칙과 Redis 상태로 판단해 허용 요청을 API 서버로 전달한다. 한도를 초과하면 클라이언트에 429를 반환하고, 같은 초과 요청은 옵션 1에서 버리거나 옵션 2에서 메시지 큐에 보관한다.](/static/images/books/system-design-interview/ch04/architecture.svg)

한도를 넘었다는 사실은 클라이언트에 **429 응답으로 알린다.** 서버에서는 같은 초과 요청을 그대로 버리거나, 처리 시점이 늦어져도 되는 작업이라면 큐에 보관해 나중에 처리할 수 있다. 그림의 두 옵션은 이 선택을 나타낸다. 큐에 보관할 때의 접수와 재시도 방식은 보충에서 살펴본다.

### 제한 규칙 표현하기

설정 파일에는 요청의 종류, 시간 단위, 허용 횟수를 적는다. 다음 규칙은 마케팅 메시지 전송을 하루 5회로 제한한다.

```yaml
domain: messaging
descriptors:
  - key: message_type
    value: marketing
    rate_limit:
      unit: day
      requests_per_unit: 5
```

인증 요청에는 별도 규칙을 적용할 수 있다.

```yaml
domain: authentication
descriptors:
  - key: action
    value: sign_in
    rate_limit:
      unit: minute
      requests_per_unit: 5
```

설정만으로는 사용자별 한도인지 서비스 전체의 한도인지까지 정해지지 않는다. 같은 규칙을 누구에게 적용할지에 맞춰 사용량 상태를 나누는 기준도 정해야 한다.

### 초과 요청과 응답 정보

`429 Too Many Requests`를 받은 클라이언트는 언제 다시 요청할 수 있는지 알아야 한다. 응답 헤더에는 한도와 남은 허용량, 재시도까지 기다릴 시간을 담을 수 있다.

| 정보            | 클라이언트가 알 수 있는 것                  |
| --------------- | ------------------------------------------- |
| 요청 한도       | 해당 정책에서 허용하는 요청량               |
| 남은 허용량     | 현재 판단 기준에서 추가로 사용할 수 있는 양 |
| 재시도 대기시간 | 다시 요청하기 전에 기다릴 시간              |

## 분산 환경에서 풀어야 할 두 문제

제한 미들웨어가 여러 대라면 요청이 어느 서버로 들어오든 같은 사용량을 확인해야 한다. 동시에 여러 요청이 그 값을 바꾸는 상황도 생긴다. 따라서 **상태를 공유하는 방법**과 **동시에 갱신해도 안전하게 만드는 방법**을 함께 설계해야 한다.

### 경쟁 조건: 두 요청이 같은 값을 읽으면

Redis의 카운터가 3인 상태에서 두 요청이 각각 값을 읽고 1을 더한 결과를 저장한다고 하자.

| 순서 | 요청 A       | 요청 B       | 저장된 값 |
| ---- | ------------ | ------------ | --------- |
| 시작 |              |              | 3         |
| 1    | 3을 읽는다   |              | 3         |
| 2    |              | 3을 읽는다   | 3         |
| 3    | 4를 저장한다 |              | 4         |
| 4    |              | 4를 저장한다 | 4         |

두 요청을 처리했으므로 값은 5여야 하지만 실제로 저장된 값은 4다. 이렇게 사용량을 적게 집계하면 한도를 넘는 요청도 통과시킬 수 있다.

![카운터 갱신의 경쟁 조건. 초기 값 3을 요청 A와 요청 B가 각각 읽는다. A가 4를 저장한 뒤 B도 4를 저장하므로 최종 값은 4다. 두 요청이 모두 반영됐다면 5여야 한다.](/static/images/books/system-design-interview/ch04/race-condition.svg)

이 구간을 락으로 보호할 수 있지만 경쟁이 많으면 성능 부담이 생긴다. Redis의 Lua 스크립트를 사용하면 **상태 조회, 한도 검사, 상태 갱신을 원자적으로 실행**할 수 있다. 다른 요청이 검사와 갱신 사이에 끼어들지 못하게 하는 것이다.

정렬 집합은 요청 시각을 보관하고 만료된 기록을 찾는 데 유용하다. 하지만 자료구조를 정렬 집합으로 골랐다는 이유만으로 여러 명령을 묶은 검사와 갱신 전체가 원자적으로 실행되지는 않는다.

### 상태 공유: 요청이 다른 서버로 가더라도

각 제한 미들웨어가 로컬 카운터만 관리하면 같은 사용자의 사용량이 서버마다 나뉜다. 다음 요청이 다른 서버로 가면 그 서버는 이전 요청에서 쓴 사용량을 알지 못한다.

![요청을 받는 제한 장치가 바뀌는 경우. 처음에는 클라이언트 1이 제한 장치 1로, 클라이언트 2가 제한 장치 2로 보낸다. 다음 요청에서는 연결이 서로 바뀔 수 있어 각 장치의 로컬 상태만으로 전체 사용량을 알 수 없다.](/static/images/books/system-design-interview/ch04/distributed-local.svg)

같은 사용자의 요청을 항상 같은 서버로 보내는 고정 세션(sticky session)으로 대응할 수 있다. 하지만 서버 증설과 장애 대응에서 유연성이 떨어진다.

여러 미들웨어가 Redis의 공통 상태를 사용하면 어느 서버로 요청이 들어와도 같은 사용량을 확인할 수 있다. 공통 저장소는 상태를 공유하는 문제를 풀고, 원자적 실행은 동시에 갱신하는 문제를 푼다. 두 가지가 함께 필요하다.

![여러 제한 장치의 공유 저장소. 클라이언트 1은 제한 장치 1을, 클라이언트 2는 제한 장치 2를 거치지만 두 장치는 같은 Redis의 사용량 상태를 공유한다.](/static/images/books/system-design-interview/ch04/distributed-sharing.svg)

## 성능과 운영

### 가까운 곳에서 판단하고 동기화 비용을 고려한다

매번 멀리 떨어진 데이터센터까지 가서 제한 여부를 판단하면 네트워크 지연이 커진다. 사용자와 가까운 에지에서 요청을 처리하면 이 지연을 줄일 수 있다.

![사용자와 가까운 에지로 요청을 전달한다. 여러 지역에 에지 서버가 분산되어 있다. 사용자에서 가까운 에지로 향하는 경로를 강조해 통신 지연을 줄이는 방식을 보여 준다.](/static/images/books/system-design-interview/ch04/edge-routing.svg)

여러 제한 장치의 상태를 동기화할 때는 최종 일관성(eventual consistency)도 고려할 수 있다. 모든 지점에 갱신을 즉시 반영하지 않고, 시간이 지나면서 상태가 일치하도록 하는 방식이다. 엄격한 전역 한도가 필요할 때 생기는 문제는 보충에서 다룬다.

### 규칙과 알고리즘이 실제 트래픽에 맞는지 본다

배포 후에는 요청을 제대로 막는지뿐 아니라 **정상 요청까지 지나치게 막고 있지 않은지** 살펴야 한다. 규칙이 너무 빡빡하면 사용자가 필요한 작업을 하지 못할 수 있다.

이벤트나 할인 행사처럼 요청이 잠깐 몰릴 때는 평소에 쓰던 방식이 맞지 않을 수 있다. 평균 요청량을 조절하면서 일시적인 집중을 받아들여야 한다면 토큰 버킷을 검토한다. 실제 트래픽을 보며 한도와 알고리즘을 조정하는 과정이 필요하다.

### 제한의 강도와 적용 계층

경성(hard) 제한은 정한 한도를 넘는 요청을 허용하지 않고, 연성(soft) 제한은 짧은 시간의 초과를 허용할 수 있다. 잠깐의 초과를 허용해도 되는지부터 요구사항에서 정해 둔다.

HTTP 요청을 다루는 애플리케이션 계층뿐 아니라 IP 주소를 기준으로 네트워크 계층에서도 제한할 수 있다. 같은 ‘트래픽 제한’이라도 어느 계층에서 무엇을 셀지는 다르다.

클라이언트는 캐시로 불필요한 API 호출을 줄이고, 호출을 짧은 시간에 몰아 보내지 않도록 조절한다. 제한 응답을 받으면 예외를 처리하고 충분한 대기시간을 둔 뒤 재시도해야 한다.

## 보충: 구현 전에 더 정할 것

### 제한 키와 집계 정책

사용자별 로그인 한도라면 `사용자 ID + 로그인 API`, IP별 계정 생성 한도라면 `IP + 계정 생성 API`처럼 같은 허용량을 공유할 범위를 정한다. 사용자별 한도와 서비스 전체 한도를 함께 두는 경우에는 두 규칙을 모두 만족해야 한다.

IP만 기준으로 삼으면 같은 네트워크의 여러 사용자가 한도를 나눠 쓸 수 있다. 프록시 뒤에서는 어떤 경로로 전달된 IP 정보를 신뢰할지도 정해야 한다. 클라이언트가 임의로 지정한 값을 그대로 제한 키로 사용하면 기준을 바꿔 가며 요청할 수 있다.

무엇을 집계할지도 정해야 한다. 앞의 이동 윈도 로그처럼 거절한 요청까지 기록하면 반복되는 재시도가 이후 판단에도 영향을 준다. 허용한 요청만 기록할 때와 동작이 달라지는 이유다. 토큰 버킷도 일정 주기마다 한꺼번에 채울지, 경과 시간에 비례해 보충할지 정해야 한다.

### 원자적 검사와 만료를 묶는 코드

`INCR` 한 번이 원자적이라는 사실만으로 ‘한도를 검사하고 증가시킨다’는 전체 작업이 보호되지는 않는다. 증가와 최초 만료 설정을 별도 호출로 나누면, 그 사이 장애로 만료 설정을 빠뜨릴 수도 있다. [Redis의 INCR 문서](https://redis.io/docs/latest/commands/incr/)도 처리율 제한 예제에서 이런 경쟁 조건과 Lua를 이용한 해결을 설명한다.

다음은 고정 윈도 카운터를 한 키에서 처리하는 Lua 예시다. 키는 사용자와 API 같은 제한 대상을 나타내고, 해시에는 구간 번호와 사용량을 저장한다. 시간은 Redis에서 읽어 고정 구간을 계산한다.

```lua
-- KEYS[1]: 제한 대상의 키. 예: rl:user:42:sign-in
-- ARGV[1]: 구간별 한도, ARGV[2]: 구간 길이(ms)
-- 반환: {허용 여부(1/0), 남은 허용량, 구간 종료까지 남은 ms}
local key = KEYS[1]
local limit = tonumber(ARGV[1])
local windowMs = tonumber(ARGV[2])
local clock = redis.call('TIME')
local now = tonumber(clock[1]) * 1000 + math.floor(tonumber(clock[2]) / 1000)
local window = math.floor(now / windowMs)
local ttl = (window + 1) * windowMs - now

local state = redis.call('HMGET', key, 'window', 'count')
local count = 0
if tonumber(state[1]) == window then
  count = tonumber(state[2]) or 0
end

if count >= limit then
  return {0, 0, ttl}
end

count = count + 1
redis.call('HSET', key, 'window', window, 'count', count)
redis.call('PEXPIRE', key, ttl)
return {1, limit - count, ttl}
```

한도와 구간 길이는 검증된 양의 정수라는 전제다. 거절한 요청은 사용량을 증가시키지 않는다. 같은 구간에서 키가 없어지지 않는 한 사용량은 한도까지만 증가하고, 구간이 끝나면 키도 만료된다. 고정 윈도 방식이므로 구간 경계의 요청 집중 문제는 그대로 남는다.

Redis는 Lua 스크립트를 원자적으로 실행하는 동안 다른 작업을 막는다. 따라서 스크립트에는 짧은 검사와 갱신만 담아야 한다. 이 보장은 같은 Redis 안에서 실행되는 작업에 적용된다. 장애 후 데이터 유실이나 여러 지역 사이의 전역 한도까지 보장하지는 않는다. ([Redis Lua 문서](https://redis.io/docs/latest/develop/programmability/eval-intro/))

### 429 응답과 재시도 시간을 구분한다

`429` 응답에 재시도 시점을 안내하려면 `Retry-After`를 사용할 수 있다. 값은 HTTP 날짜나 대기할 초 단위 정수로 표현한다. ([429 응답 규격](https://www.rfc-editor.org/rfc/rfc6585.html#section-4), [Retry-After 규격](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3))

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 12
X-RateLimit-Limit: 5
X-RateLimit-Remaining: 0
```

이 예시에서 `Retry-After: 12`는 재시도 전에 12초를 기다리라는 뜻이다. `X-RateLimit-*`는 서비스가 의미를 정해 제공하는 사용자 정의 헤더이므로 클라이언트와 헤더의 의미를 합의한다. 남은 허용량이 어떤 구간과 정책을 기준으로 하는지도 분명해야 한다.

큐에 접수한 작업과 429로 거절한 요청은 구분해야 한다. 서버가 이미 큐에 넣은 작업을 클라이언트가 거절된 것으로 이해하고 다시 보내면 중복 처리될 수 있다. 클라이언트가 접수 여부를 알 수 있도록 응답을 정하고, 같은 작업을 식별할 방법도 API 계약에 포함해야 한다.

### 저장소 장애와 전역 한도

Redis에 접근할 수 없을 때의 행동은 미리 정해야 한다.

| 선택                      | 동작                              | 감수할 점                                    |
| ------------------------- | --------------------------------- | -------------------------------------------- |
| 장애 중 통과(fail-open)   | 제한 판단에 실패해도 API로 보낸다 | 보호하려던 서버와 비용의 한도를 넘을 수 있다 |
| 장애 중 차단(fail-closed) | 판단할 수 없는 요청을 막는다      | 정상 사용자의 요청도 실패할 수 있다          |
| 임시 로컬 제한            | 미들웨어별 작은 한도로 처리한다   | 서버 전체의 합산 한도는 정확하지 않다        |

판단 자체가 실패한 경우와 사용자가 실제로 한도를 초과한 경우는 다르다. 저장소 장애를 모두 429로 응답하면 원인을 잘못 알리게 된다.

여러 지역이 각자 요청을 허용한 뒤 사용량을 합치면, 동기화 전에는 서로 얼마나 썼는지 알 수 없다. 그동안 전역 한도를 넘길 수 있으므로 최종 일관성을 선택할 때는 허용할 초과량도 정해야 한다. 엄격한 전역 한도가 필요하다면 공유된 판단 지점이나 지역별 할당량 같은 방식을 추가로 설계한다.

운영할 때는 규칙별 허용·거절 건수와 함께 판단 지연, Redis 오류, 상태 저장에 쓰는 메모리, 큐 대기시간을 살핀다. 거절 비율만 높다고 해서 정상 요청을 잘못 막는다고 단정할 수는 없다. 어떤 사용자와 API에서 거절이 늘었는지 확인하며 조정한다.

## 설계 정리

제한 대상과 시간 단위를 정한 뒤에는 순간적인 요청 집중을 얼마나 허용할지에 맞춰 알고리즘을 고른다. 서버를 여러 대로 늘릴 때는 사용량을 공유하는 것과 동시에 갱신해도 안전하게 만드는 것을 함께 해결해야 한다. 초과 요청의 처리와 재시도 안내까지 정했다면, 실제 트래픽에서 정상 요청이 불필요하게 막히지 않는지 확인하며 규칙을 조정한다.
