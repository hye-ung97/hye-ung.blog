같은 데이터를 여러 장비에 두는 이유는 세 가지다. 사용자와 가까운 곳에서 응답해 지연 시간을 줄이고, 일부가 죽어도 서비스를 이어 가고, 읽기 요청을 여러 장비로 나눠 처리량을 늘린다. 어려운 부분은 데이터가 바뀔 때다.

## 리더와 팔로워

가장 흔한 방식은 쓰기를 리더 한 곳에서만 받는 것이다. 팔로워는 리더의 복제 로그를 받아 같은 순서로 적용하고, 읽기는 리더와 팔로워 모두에서 처리한다.

동기 복제는 팔로워가 받았다고 답할 때까지 쓰기를 끝내지 않는다. 데이터는 안전하지만 팔로워 하나가 느려지면 쓰기 전체가 멈춘다. 그래서 보통은 팔로워 하나만 동기로 두고 나머지는 비동기로 둔다.

## 복제 로그 구현

리더가 실행한 SQL 문을 그대로 보내면 `NOW()`나 `RAND()`처럼 실행할 때마다 결과가 달라지는 함수가 문제를 일으킨다. 저장 엔진의 쓰기 전 로그를 보내면 엔진 버전에 묶이고, 행 단위의 논리적 로그를 보내면 둘 다 피할 수 있다.

## 복제 지연 문제

비동기 팔로워는 리더보다 조금씩 뒤처진다. 평소에는 1초도 안 되지만 부하가 몰리면 몇 분까지 벌어지고, 그 사이 사용자는 이상한 화면을 본다. 책은 이 문제를 세 가지 읽기 보장으로 정리한다.

| 읽기 보장           | 막아 주는 문제                    |
| ------------------- | --------------------------------- |
| 자신이 쓴 내용 읽기 | 방금 쓴 글이 안 보인다            |
| 단조 읽기           | 새로고침하면 과거 데이터가 보인다 |
| 일관된 순서로 읽기  | 답이 질문보다 먼저 보인다         |

## 다중 리더 복제

데이터센터마다 리더를 두면 쓰기도 가까운 곳에서 처리할 수 있다. 대가는 쓰기 충돌이다. 두 리더가 같은 레코드를 동시에 바꾸면 어느 쪽을 남길지 정해야 하고, 마지막 쓰기 승리처럼 단순한 규칙은 조용히 데이터를 잃는다.

## 리더 없는 복제

다이나모 계열은 리더 없이 여러 노드에 동시에 쓰고 동시에 읽는다. 노드 n개 중 w개에 쓰고 r개에서 읽을 때 w + r > n이면, 읽은 노드 중 적어도 하나는 최신 값을 갖고 있다. 오래된 값은 읽기 복구와 안티 엔트로피로 따라잡는다.
