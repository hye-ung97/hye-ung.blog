데이터베이스는 결국 두 가지 일을 한다. 데이터를 받으면 저장하고, 나중에 요청하면 돌려준다. 3장은 이 두 일을 디스크 위에서 어떻게 빠르게 하는지를 저장 엔진 두 계열로 나눠 보여 준다.

## 로그와 해시 색인

가장 단순한 저장소는 파일 끝에 덧붙이기만 하는 로그다. 쓰기는 순차 쓰기라 빠르지만, 읽기는 파일 전체를 훑어야 한다. 그래서 색인이 필요하고, 가장 단순한 색인은 키마다 바이트 오프셋을 기억하는 해시 맵이다.

```python
# 쓰기는 파일 끝에 덧붙이기만 하고, 해시 맵에 키별 바이트 오프셋을 기록한다
index = {}

def db_set(key, value):
    with open('database', 'ab') as f:
        index[key] = f.seek(0, 2)  # 파일 끝 오프셋
        f.write(f'{key},{value}\n'.encode())

def db_get(key):
    with open('database', 'rb') as f:
        f.seek(index[key])
        return f.readline().decode().split(',', 1)[1].rstrip('\n')
```

로그는 계속 자라므로 일정 크기마다 세그먼트를 닫고, 같은 키의 오래된 값을 버리는 컴팩션으로 세그먼트를 합친다. 다만 해시 맵은 메모리에 다 들어가야 하고, 범위 질의에 쓸 수 없다.

## SS테이블과 LSM 트리

세그먼트 안의 키를 정렬해 두면 SS테이블이 된다. 쓰기는 먼저 메모리의 정렬된 트리(멤테이블)에 넣고, 커지면 디스크에 SS테이블로 내린다. 읽기는 멤테이블, 최신 세그먼트, 그다음 세그먼트 순으로 찾는다.

정렬 덕분에 색인은 몇 킬로바이트마다 키 하나만 기억해도 되고, 병합은 정렬된 파일을 합치는 일이 된다. 없는 키를 찾느라 모든 세그먼트를 뒤지지 않도록 블룸 필터를 함께 쓴다.

## B 트리

B 트리는 데이터를 고정 크기 페이지로 나누고, 페이지들이 서로를 가리키는 트리를 만든다. 값을 바꿀 때 로그처럼 덧붙이지 않고 그 페이지를 제자리에서 덮어쓴다.

덮어쓰는 도중에 서버가 죽으면 페이지가 깨질 수 있어서, 변경 내용을 먼저 쓰기 전 로그(WAL)에 남긴다. 분기 계수가 수백이라 깊이 서너 단계면 수억 개의 키를 담는다.

## 어느 쪽을 고를까

LSM 트리는 쓰기 처리량이 높고 압축률이 좋지만, 백그라운드 컴팩션이 디스크 대역폭을 나눠 쓰면서 응답 시간의 꼬리를 늘릴 수 있다. B 트리는 키가 정확히 한 곳에만 있어서 범위 잠금으로 트랜잭션 격리를 구현하기 쉽다.

결국 책의 결론은 실제 작업 부하로 측정해 보라는 것이다. 쓰기가 많은 로그 수집과 읽기가 많은 주문 조회는 같은 답을 갖지 않는다.
