타입스크립트는 기존 자바스크립트 코드에 타입을 조금씩 추가할 수 있다. 이 과정에서 `any`가 필요할 수 있지만, 한 곳에서 사용한 `any`가 다른 코드의 검사까지 느슨하게 만들지 않도록 경계를 정해야 한다.

## any는 가능한 한 좁은 범위에서

값 하나를 전달하기 위해 단언이 필요하다면 변수 전체나 함수의 반환 타입까지 `any`로 바꾸지 않는다. 필요한 표현식에만 제한하고, 다음 단계에는 구체적인 타입을 전달한다.

특히 외부 데이터를 읽는 함수의 반환 타입을 확인한다. 내부에서 다룬 `any`가 반환값으로 추론되면 호출하는 코드도 타입 정보를 잃을 수 있다. 반환 타입을 명시해 의도하지 않은 변화가 생기는지 검사할 수 있다.

다만 반환 타입을 적는 것만으로 `any`의 실제 값이 검증되지는 않는다. 잘못된 값도 구체적인 타입에 할당할 수 있다는 것이 `any`의 위험이다.

## 알고 있는 구조는 타입에 남기기

배열이라는 것을 안다면 `any`보다 `any[]`가 표현하는 정보가 많다. 문자열 키를 가진 객체라면 인덱스 시그니처로 구조를 표현할 수 있다.

```typescript
type UncheckedFields = { [key: string]: any }
type UnknownFields = Record<string, unknown>
```

값을 확인한 뒤 사용할 수 있다면 `unknown`을 선택한다. `any`는 속성 접근과 호출을 허용하지만, `unknown`은 먼저 검사하거나 타입을 좁혀야 한다.

```typescript
function readTitle(fields: Record<string, unknown>): string | undefined {
  const title = fields.title
  return typeof title === 'string' ? title : undefined
}
```

`object`는 원시값을 제외한 값을 표현한다. 특정 키와 값의 타입을 알려주지는 않으므로, 문자열 키로 임의의 속성을 읽을 수 있는 사전 타입과는 구분한다.

## any의 진화 이해하기

암시적인 `any`와 명시적으로 선언한 `any`는 일부 추론에서 다르게 동작한다. `noImplicitAny`와 `strictNullChecks`를 켠 환경에서 다음 빈 배열은 값을 추가하는 흐름에 따라 타입이 추론된다.

```typescript
function collectValues() {
  const values = []
  values.push(1)
  values.push('완료')
  return values // (number | string)[]
}
```

이것은 `const values: any[] = []`처럼 타입을 직접 `any[]`로 선언한 경우와 다르다. 명시적인 `any[]`는 값을 추가해도 해당 타입을 유지한다.

초기값이 `null`인 지역 변수도 이후 할당에 따라 추론될 수 있다. 반대로 타입이 결정되기 전에 읽거나, 콜백 안의 변경에 기대어 반환 타입을 추론하려 하면 암시적 `any` 오류가 발생할 수 있다. 세부 조건은 [원저자의 ‘Evolving any’ 글](https://effectivetypescript.com/2020/03/09/evolving-any/)에 정리돼 있다.

의도가 명확한 배열에는 `number[]`처럼 타입을 적거나, `map()`의 결과에서 타입을 추론하게 하면 흐름을 이해하기 쉽다.
