타입을 변수에 붙이는 이름으로만 보면 할당 가능 여부가 헷갈린다. 어떤 값을 허용하는 집합인지 생각하면 유니온과 타입 확장을 이해하기 쉬워진다.

## 타입은 값의 집합

```typescript
type Environment = 'development' | 'production'
type Production = 'production'
```

`Environment`는 두 문자열을 허용하고, `Production`은 그중 하나만 허용한다. `Production`의 값은 `Environment`에 할당할 수 있다. 값의 집합이 더 좁기 때문이다.

유니온은 두 타입이 허용하는 값을 합친다. 인터섹션은 양쪽 타입의 조건을 모두 만족하는 값을 나타낸다. 객체 타입의 인터섹션에 속성이 더 많이 보이더라도, 허용하는 값의 조건은 더 엄격해진다.

타입 매개변수의 `extends`도 ‘이 타입에 할당 가능한 타입’이라는 제약으로 읽을 수 있다.

## 타입 공간과 값 공간

같은 이름이나 연산자라도 타입을 설명하는 자리와 실행되는 코드에서 의미가 다를 수 있다.

```typescript
const settings = { retries: 3 }

type Settings = typeof settings
const runtimeType = typeof settings // 'object'
```

타입 공간의 `typeof settings`는 값의 타입을 가져온다. 값 공간의 `typeof settings`는 자바스크립트 연산자로 실행돼 문자열을 반환한다.

`type`과 `interface`는 타입 공간에만 존재한다. 반면 클래스는 타입과 런타임 값 양쪽에서 사용할 수 있다.

## 타입 단언보다 타입 선언

```typescript
interface User {
  name: string
}

const user: User = { name: '혜웅' }
```

타입 선언은 할당하는 값이 선언한 타입을 만족하는지 검사한다. 객체를 만드는 곳에서 속성을 빠뜨리거나 잘못 적었는지 확인할 수 있다.

타입 단언은 개발자가 알고 있는 정보를 타입 체커에 전달한다. 필요한 상황이 있지만, 타입을 단언했다고 값이 검증되는 것은 아니다. 단언에도 타입 간의 관계에 따른 제약이 있으므로, 모든 오류를 무조건 무시하는 문법으로 이해해서는 안 된다. ([공식 문서](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#type-assertions))

## 함수 표현식에 타입 적용하기

매개변수부터 반환값까지 하나의 함수 타입으로 정의하면 여러 구현에 같은 계약을 적용할 수 있다.

```typescript
type FormatId = (id: number) => string

const formatUserId: FormatId = (id) => `user-${id}`
const formatOrderId: FormatId = (id) => `order-${id}`
```

각 함수에 매개변수와 반환 타입을 반복하지 않아도 된다. 같은 역할을 하는 함수가 여러 개 있을 때 유용하다.

## 타입과 인터페이스의 차이

객체의 형태는 `type`과 `interface`로 모두 표현할 수 있다. 인터페이스는 `extends`로 확장하고, 타입 별칭은 인터섹션으로 조건을 합칠 수 있다.

```typescript
type State = { name: string; capital: string }

interface StateWithPopulation extends State {
  population: number
}

type StateWithArea = StateWithPopulation & { area: number }
```

객체 타입을 다룰 때 기능이 겹치지만 모든 쓰임이 같은 것은 아니다. 유니온 타입은 타입 별칭으로 표현할 수 있고, 인터페이스에는 선언 병합이 있다. 목적과 프로젝트의 기존 스타일에 맞춰 선택한다.

## 타입 연산과 제너릭으로 반복 줄이기

이미 정의한 타입에서 필요한 부분을 가져오면 같은 속성을 여러 곳에서 관리할 필요가 줄어든다.

```typescript
interface Product {
  id: number
  name: string
  price: number
}

type ProductSummary = Pick<Product, 'id' | 'name'>
```

타입에도 DRY 원칙을 적용할 수 있다. 다만 모양이 같다는 이유만으로 서로 다른 의미의 타입을 억지로 묶을 필요는 없다.

## 변경하지 않는 매개변수는 readonly

```typescript
function sum(values: readonly number[]): number {
  return values.reduce((total, value) => total + value, 0)
}
```

이 함수가 받은 배열을 변경하지 않는다는 의도를 타입으로 표현한다. 함수 안에서 `push()` 같은 변경 작업을 하면 타입 오류가 발생한다.

`readonly`는 런타임에 값을 동결하지 않고, 중첩된 값까지 모두 불변으로 만들지도 않는다. 읽기 전용 타입으로 바라보더라도 다른 참조를 통해 값이 바뀔 수 있다. ([공식 문서](https://www.typescriptlang.org/docs/handbook/2/objects.html#readonly-properties))
