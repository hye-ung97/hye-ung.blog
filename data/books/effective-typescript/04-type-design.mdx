좋은 타입은 값의 구조뿐 아니라 가능한 상태와 의미를 전달한다. 어떤 값을 허용하고 어떤 값을 제외할지 결정하는 일이 타입 설계의 출발점이다.

## 유효한 상태만 표현하기

로딩 여부, 데이터, 오류를 서로 독립적인 속성으로 두면 모순된 조합도 표현할 수 있다. 로딩 중인데 성공 데이터와 오류가 동시에 존재하는 식이다.

상태마다 필요한 값을 나누면 이런 조합을 줄일 수 있다.

```typescript
type LoadState<T> =
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; message: string }

function describeState(state: LoadState<string>): string {
  switch (state.status) {
    case 'loading':
      return '불러오는 중'
    case 'success':
      return state.data
    case 'error':
      return state.message
  }
}
```

`status`를 확인하면 각 상태에 맞는 속성만 사용할 수 있다. 성공 상태에 데이터가 없거나, 로딩 상태에 오류 메시지를 넣는 실수를 타입 검사로 찾을 수 있다. 이런 형태를 판별 유니온이라고 한다. ([공식 문서](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#discriminated-unions))

## 입력은 너그럽게, 출력은 구체적으로

함수는 호출자가 제공할 수 있는 입력의 범위와, 반환값에 대해 보장할 내용을 구분해야 한다.

```typescript
interface DateInput {
  year: number
  month?: number
  day?: number
}

interface FullDate {
  year: number
  month: number
  day: number
}

function fillDate(input: DateInput): FullDate {
  return {
    year: input.year,
    month: input.month ?? 1,
    day: input.day ?? 1,
  }
}
```

호출할 때는 일부 값을 생략할 수 있지만, 반환값을 사용할 때는 모든 속성이 있다고 가정할 수 있다. 이 예제는 누락된 값을 채우는 동작만 보여준다. 월과 일의 유효 범위까지 검증하려면 별도의 처리가 필요하다.

## string보다 더 구체적인 타입

허용하는 문자열이 정해져 있다면 `string`으로 모든 문자열을 받아들일 필요가 없다.

```typescript
type PaymentStatus = 'pending' | 'paid' | 'cancelled'
```

값의 범위를 좁히면 오타를 발견하기 쉽고, 사용할 수 있는 값도 코드에서 확인할 수 있다.

객체의 속성 이름을 받아야 한다면 `keyof`로 실제 키의 범위를 표현할 수 있다.

```typescript
function getProperty<T, K extends keyof T>(value: T, key: K): T[K] {
  return value[key]
}

const product = { name: '책', price: 25000 }
const price = getProperty(product, 'price') // number
```

키의 타입과 반환값의 타입을 연결하면, 속성 이름을 검사하는 것과 값의 타입을 유지하는 것을 함께 할 수 있다.

## 예시 데이터보다 API와 명세를 기준으로

응답 예시 하나에는 실제로 가능한 모든 경우가 들어 있지 않다. 한 번 받은 데이터만 보고 타입을 만들면 선택적인 필드, `null`, 오류 응답 등을 놓칠 수 있다.

API 명세에서 필수 여부와 값의 범위를 확인하고 타입을 만든다. 명세에 맞는 타입을 선언해도 네트워크에서 받은 값이 자동으로 검증되지는 않으므로, 필요한 경우 실행 시점의 검증도 추가한다.

## 해당 분야의 용어로 이름 짓기

이름은 값이 어떤 의미를 갖는지 전달해야 한다. 단순히 `Data`나 `Info`라고 부르는 것보다 `Invoice`, `PaymentStatus`처럼 해당 분야에서 사용하는 용어를 쓰면 이해하기 쉽다.

타입, 속성, 변수의 이름이 같은 의미를 일관되게 가리키도록 한다. 코드 안에서 새로운 용어를 만들기 전에 이미 쓰는 도메인 용어가 있는지 확인한다.

## 상표 기법으로 의미 구분하기

서로 다른 의미의 값이 같은 기본 타입으로 표현될 때, 구조적 타이핑만으로는 둘을 구분하기 어려울 수 있다. 상표 기법은 타입에 구분용 표식을 더한다.

```typescript
declare const absolutePathBrand: unique symbol
type AbsolutePath = string & { readonly [absolutePathBrand]: true }

function toAbsolutePath(value: string): AbsolutePath {
  if (!value.startsWith('/')) {
    throw new Error('POSIX 절대 경로가 필요합니다.')
  }

  return value as AbsolutePath
}
```

이 예제는 `/`로 시작하는 POSIX 경로 문자열을 대상으로 한다. 운영체제별 경로나 경로의 실제 존재 여부까지 검사하는 함수는 아니다.

**상표 자체가 실행 시점의 검증을 대신하지는 않는다.** 조건을 검사하는 함수에서 값을 만든 뒤, 타입 표식으로 그 결과를 전달한다. 아무 문자열이나 단언해 버리면 이 보장이 깨진다.
