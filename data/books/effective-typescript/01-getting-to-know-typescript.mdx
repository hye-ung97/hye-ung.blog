타입스크립트는 자바스크립트 코드에 타입 정보를 더하고, 실행 전에 코드의 오류를 찾는 도구다. 타입 검사가 통과했는지와 실행 중에 올바르게 동작하는지는 구분해서 생각해야 한다.

## 타입스크립트와 자바스크립트의 관계

타입스크립트는 자바스크립트 문법에 타입을 선언하는 문법 등을 추가한다. 타입 구문이 없는 자바스크립트 코드에도 타입 추론을 적용할 수 있다.

```typescript
const price = 1000
const quantity = 3
const total = price * quantity
```

위 코드에는 타입을 직접 적지 않았지만, 타입스크립트는 각 값이 숫자라는 것을 추론한다. 필요한 곳에 타입을 선언하면 함수가 무엇을 받고 무엇을 반환하는지 더 분명하게 전달할 수 있다.

```typescript
function calculateTotal(price: number, quantity: number): number {
  return price * quantity
}
```

타입 시스템은 자바스크립트의 동작을 모델링한다. 다만 실행 전에 모든 오류를 찾아주는 것은 아니다. 외부에서 들어오는 데이터나 실행 시점의 상태는 별도로 확인해야 한다.

## 타입스크립트 설정 이해하기

같은 코드라도 컴파일러 설정에 따라 검사 결과가 달라진다.

| 설정               | 확인하는 내용                                                               |
| ------------------ | --------------------------------------------------------------------------- |
| `noImplicitAny`    | 타입을 추론하지 못해 암시적인 `any`가 생기는 경우를 검사한다.               |
| `strictNullChecks` | `null`과 `undefined`를 별도의 타입으로 취급해, 값이 없을 가능성을 검사한다. |

`noImplicitAny`를 켠다고 모든 변수에 타입을 직접 적어야 하는 것은 아니다. 추론할 수 있는 타입은 그대로 추론한다. 타입을 알아낼 수 없는 함수 매개변수 등이 검사의 대상이 된다. ([공식 문서](https://www.typescriptlang.org/tsconfig/#noImplicitAny))

`strictNullChecks`를 켜면 DOM 요소를 찾거나 배열에서 값을 검색할 때 결과가 없을 가능성을 처리해야 한다. 그 과정에서 실행 중에 발생할 수 있는 오류를 미리 발견할 수 있다.

## 타입 검사와 코드 생성, 런타임 구분하기

타입 선언과 타입 단언은 자바스크립트로 변환할 때 제거된다. 타입을 선언했다고 실행 시점에 값이 검사되거나 변환되는 것은 아니다.

```typescript
const input: unknown = '42'
const count = input as number

console.log(typeof count) // 'string'
```

`as number`는 타입 체커가 값을 바라보는 방식을 바꾼다. 문자열을 숫자로 바꾸지는 않는다. 변환이 필요하다면 `Number()` 같은 실제 연산을 사용하고, 유효한 값인지도 확인해야 한다.

타입 오류가 있어도 자바스크립트가 생성될 수 있다. 오류가 있을 때 출력을 막을지는 [`noEmitOnError`](https://www.typescriptlang.org/tsconfig/#noEmitOnError) 같은 설정에 달려 있다. 타입 검사와 코드 생성은 서로 다른 작업이다.

`interface`는 타입으로만 존재한다. `class`는 타입으로 사용할 수 있고, 실행 시점에도 생성자 값으로 존재한다. `instanceof`로 확인할 수 있는 대상은 이런 런타임 값이다. 타입 단언의 동작은 [공식 문서](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#type-assertions)에서 확인할 수 있다.

## any 타입 지양하기

`any`는 해당 값을 다룰 때 타입 검사를 크게 느슨하게 만든다.

- 잘못된 속성 접근이나 함수 호출을 놓치기 쉽다.
- 자동 완성과 리팩터링에 필요한 타입 정보가 사라진다.
- 다른 변수나 함수의 반환값으로 퍼지면 타입 검사의 범위도 줄어든다.

타입스크립트를 점진적으로 도입할 때 `any`가 필요할 수는 있다. 그래도 사용 범위를 좁히고, 값의 구조를 알고 있다면 구체적인 타입을 선언한다. 아직 모르는 값은 `unknown`으로 받은 뒤 확인하는 방법도 있다.
