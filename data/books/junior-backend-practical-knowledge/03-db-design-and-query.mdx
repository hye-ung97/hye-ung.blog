[2장](/books/junior-backend-practical-knowledge/02-service-performance)에서는 응답 시간과 처리량을 측정하고 병목을 찾는 방법을 살펴봤다. DB 쿼리가 병목이라면 어떤 인덱스를 사용하는지, 얼마나 많은 데이터를 읽는지부터 확인한다.

이번 장은 조회 패턴에 맞춰 인덱스를 설계하고, 쿼리가 읽는 데이터의 양을 줄이는 방법을 다룬다. 아래 SQL은 MySQL을 기준으로 작성했다.

## 조회 패턴을 고려한 인덱스 설계

### 풀 스캔

풀 스캔은 테이블의 모든 행을 읽으면서 조건에 맞는 데이터를 찾는 방식이다. 조회 조건에 사용할 인덱스가 없으면 풀 스캔이 발생할 수 있다. 인덱스가 있어도 DB가 전체 테이블을 읽는 편이 더 빠르다고 판단하면 풀 스캔을 선택한다.

데이터가 적고 요청도 드물다면 풀 스캔이 큰 문제가 되지 않을 수 있다. 반면 게시글이 수백만 건인 커뮤니티에서 카테고리별 목록을 조회할 때마다 전체 테이블을 읽으면 부하가 커진다.

테이블을 설계할 때는 자주 사용하는 조회 조건, 정렬 순서, 예상 데이터양을 함께 본다. 인덱스를 추가한 뒤에는 `EXPLAIN`으로 실행 계획을 확인하고 실제 실행 시간도 비교한다.

### 단일 인덱스와 복합 인덱스

사용자의 활동 기록을 조회한다고 가정해 보자. `userId`만 포함한 단일 인덱스는 특정 사용자의 기록을 찾는 데 사용할 수 있다. 여기에 날짜 조건을 자주 사용한다면 `(userId, activityDate)` 복합 인덱스를 고려한다.

```sql
CREATE INDEX idx_activity_user_date
ON activityLog (userId, activityDate);

SELECT activityDate, activityType
FROM activityLog
WHERE userId = 100
  AND activityDate >= '2024-07-01'
  AND activityDate < '2024-08-01';
```

사용자당 기록이 몇 건뿐이라면 `userId` 인덱스로 찾은 뒤 날짜를 확인해도 충분할 수 있다. 사용자 한 명의 기록이 많아지면 날짜까지 인덱스에서 좁히는 편이 유리하다.

![단일 인덱스와 복합 인덱스의 조회 범위. userId만 있는 인덱스는 사용자 100의 활동 기록을 찾은 뒤 날짜 조건을 확인한다. userId와 activityDate로 구성된 복합 인덱스는 사용자 100의 기록 중 7월 범위를 찾는다. 설명을 위한 예이며 실제 읽는 행 수는 실행 계획에 따라 달라진다.](/static/images/books/junior-backend-practical-knowledge/index-range.png)

복합 인덱스는 칼럼 순서도 중요하다. `(userId, activityDate)`는 `userId` 조건이나 `userId`와 날짜를 함께 사용하는 조회에 맞는다. 날짜만으로 조회하는 쿼리까지 같은 효과를 낸다고 볼 수는 없다. ([MySQL 복합 인덱스 문서](https://dev.mysql.com/doc/refman/8.4/en/multiple-column-indexes.html))

### 선택도와 데이터 분포

선택도는 칼럼의 값이 얼마나 잘 구분되는지 판단하는 기준이다. 고유한 값의 비율이 높으면 대체로 인덱스로 조회 범위를 좁히기 좋다. 하지만 고유한 값의 개수만 보고 인덱스가 필요한지 결정할 수는 없다.

작업 큐의 `status`는 `READY`, `RUNNING`, `DONE`처럼 값의 종류가 적을 수 있다. 대부분이 `DONE`이고 처리할 `READY` 작업은 적다면, `READY`를 찾는 인덱스가 도움이 된다. 반대로 조회하려는 상태가 테이블 대부분을 차지하면 효과가 작을 수 있다.

칼럼의 고유한 값 수와 함께, 실제 조회 조건에 해당하는 행의 비율을 확인한다.

### 커버링 인덱스

커버링 인덱스는 쿼리에 필요한 칼럼을 모두 포함하는 인덱스다. 조건에 맞는 행을 찾고 결과를 반환하는 데 필요한 값이 인덱스 안에 있으면, 테이블 행을 추가로 읽는 작업을 줄일 수 있다.

다음 쿼리는 `(activityDate, activityType)` 인덱스가 있다고 가정한다.

```sql
CREATE INDEX idx_activity_date_type
ON activityLog (activityDate, activityType);

SELECT activityDate, activityType
FROM activityLog
WHERE activityDate = '2024-07-31'
  AND activityType = 'VISIT';
```

`WHERE`와 `SELECT`에 사용한 칼럼이 모두 인덱스에 포함돼 있다. 여기서 `SELECT *`로 바꾸면 인덱스에 없는 칼럼도 필요해져 같은 이점을 얻지 못할 수 있다.

커버링 인덱스를 사용해도 조건에 맞는 인덱스 항목은 읽어야 한다. 조회 대상이 많다면 인덱스만으로 처리하더라도 시간이 걸린다.

### 문자열 검색과 인덱스 비용

제목 중간에 특정 단어가 포함됐는지 찾는 조건은 다음과 같이 작성할 수 있다.

```sql
SELECT id, title
FROM article
WHERE title LIKE '%검색어%';
```

앞에 `%`가 있는 패턴은 일반적인 B-tree 인덱스로 검색 범위를 좁히기 어렵다. 데이터가 많다면 전문 검색 인덱스나 별도 검색 엔진을 검토한다. 전문 검색은 단어 분리 방식과 검색 규칙이 있으므로, 부분 문자열을 찾는 `LIKE`와 결과가 같은지도 확인해야 한다.

인덱스를 많이 만들수록 모든 쿼리가 빨라지는 것은 아니다. 데이터를 추가하거나 변경하거나 삭제할 때 관련 인덱스도 갱신해야 한다. 인덱스를 저장하는 디스크와 메모리도 필요하다. 자주 실행되는 쿼리에 효과가 있는 인덱스를 유지하고, 사용하지 않거나 중복되는 인덱스는 정리한다.

## 조회할 데이터 줄이기

### 페이지 번호 대신 마지막 ID로 조회하기

페이지 번호로 목록을 조회할 때는 `OFFSET`을 사용하는 경우가 많다.

```sql
SELECT id, title
FROM article
ORDER BY id DESC
LIMIT 20 OFFSET 100000;
```

이 쿼리는 앞의 100,000건을 건너뛴 뒤 20건을 반환한다. 뒤쪽 페이지로 갈수록 건너뛰는 데이터가 많아져 조회 비용이 커질 수 있다.

무한 스크롤처럼 다음 목록만 필요하다면 마지막으로 받은 ID를 기준으로 조회할 수 있다. `id`에 인덱스가 있고 ID 내림차순으로 정렬하는 경우의 예다.

```sql
SELECT id, title
FROM article
WHERE id < 50000
ORDER BY id DESC
LIMIT 20;
```

이전 응답의 마지막 ID가 `50000`이면 그보다 작은 ID부터 다음 목록을 읽는다. 특정 페이지로 바로 이동하기는 어렵지만, 큰 `OFFSET`을 처리하는 비용을 줄일 수 있다.

![OFFSET과 마지막 ID 기준 조회의 차이. OFFSET 방식은 앞의 100,000건을 건너뛴 뒤 20건을 반환한다. 마지막 ID 기준 방식은 ID 50000보다 작은 범위에서 20건을 읽는다. 두 쿼리가 동일한 페이지를 가리킨다는 뜻은 아니며 접근 방식의 차이를 보여주는 예다.](/static/images/books/junior-backend-practical-knowledge/keyset-pagination.png)

정렬 기준이 작성 시간이라면 ID만 커서로 사용해서는 안 된다. 같은 작성 시간을 가진 행의 순서를 정할 ID까지 포함해, 정렬 조건과 커서 조건을 맞춰야 한다.

### 시간 범위 제한하기

전체 이력을 조회하는 대신 최근 한 달이나 사용자가 선택한 기간만 조회하도록 범위를 제한할 수 있다.

```sql
SELECT activityDate, activityType
FROM activityLog
WHERE userId = 100
  AND activityDate >= '2024-07-01'
  AND activityDate < '2024-08-01';
```

날짜 범위를 인덱스로 찾는 쿼리라면, 조회 기간을 짧게 잡을수록 읽을 대상도 줄어든다. 최신 데이터에 조회가 집중되면 DB의 메모리 캐시를 재사용하기에도 유리하다.

오래된 기록도 조회해야 하는 기능이라면 기본 조회 기간은 짧게 두고, 사용자가 기간을 늘려 조회할 수 있게 한다.

### 전체 개수가 꼭 필요한지 확인하기

목록 20건을 읽는 쿼리와 전체 개수를 구하는 `COUNT(*)`는 읽는 데이터양이 다를 수 있다. 특히 조건에 맞는 정확한 개수를 구하려면 해당 범위의 행이나 인덱스 항목을 확인해야 한다.

커버링 인덱스가 있어도 많은 항목을 세는 비용은 남는다. 목록은 빠르게 나와도 전체 개수를 구하느라 응답이 늦어질 수 있다.

화면에 다음 목록이 있는지만 표시한다면 전체 개수 대신 21건을 조회한다. 20건을 응답하고, 한 건이 더 있었는지로 다음 목록의 존재 여부를 판단할 수 있다. 전체 개수가 꼭 필요하다면 집계 결과를 따로 저장하거나 캐시하는 방법을 검토한다. 이때 집계 값의 갱신 주기도 정해야 한다.

## DB 확장과 캐시

### 수직 확장과 조회 분산

쿼리와 인덱스를 개선해도 DB 자원이 부족할 수 있다. CPU, 메모리, 디스크 I/O 중 무엇이 부족한지 확인하고 장비를 확장한다.

조회 비중이 높다면 주 DB(primary)와 복제 DB(replica)를 구성해 조회를 분산할 수 있다. 변경 쿼리는 주 DB에서 실행하고, 지연된 데이터를 허용할 수 있는 조회는 복제 DB로 보낸다. 복제 DB를 추가하면 조회 처리량을 늘릴 수 있지만, 주 DB의 쓰기 처리량까지 같은 방식으로 늘어나는 것은 아니다.

### 복제 지연과 상태 변경

주 DB에서 커밋한 내용이 복제 DB에 반영되기까지는 시간이 걸릴 수 있다. 변경 내용을 전달하고 복제 DB에서 적용하는 동안 두 DB의 값이 달라진다.

재고가 1개인 상품의 주문이 완료돼 주 DB의 재고가 0개가 됐다고 가정해 보자. 복제 DB에 아직 반영되지 않았다면 다음 요청은 재고를 1개로 읽을 수 있다. 이 값을 기준으로 주문 가능 여부를 판단하면 잘못된 결정을 내릴 수 있다.

![복제 지연으로 생기는 조회 값의 차이. 주 DB에서는 주문을 커밋해 재고가 0개가 됐지만 복제 DB는 변경 적용 전이라 재고 1개를 반환한다. 변경 내용이 반영된 뒤에는 복제 DB도 재고 0개를 반환한다. 비동기 복제를 단순화한 그림이며 지연 시간은 고정된 값이 아니다.](/static/images/books/junior-backend-practical-knowledge/replication-lag.png)

상태를 변경할지 판단하는 조회는 변경 작업과 함께 주 DB에서 처리한다. 같은 주 DB를 사용하더라도 동시 요청이 들어올 수 있으므로, 필요한 잠금이나 조건부 갱신도 고려해야 한다.

주 DB에서 진행 중인 트랜잭션의 미커밋 변경을 복제 DB에서 읽을 수도 없다. 하나의 작업에서 사용하는 조회와 변경이 같은 트랜잭션에 참여하는지 확인한다. 변경 직후 자신의 결과를 다시 보는 화면도 복제 지연을 고려해야 한다.

### 별도 캐시 서버

반복해서 읽는 데이터를 캐시하면 DB로 들어가는 조회 요청을 줄일 수 있다. 캐시에 값이 없을 때 DB를 조회하고 결과를 저장하는 흐름과 캐시 종류는 [2장의 캐시 정리](/books/junior-backend-practical-knowledge/02-service-performance#서버-캐시)를 참고한다.

캐시를 추가할 때는 데이터가 바뀌면 언제 값을 지우거나 갱신할지 정한다. 캐시가 오래된 값을 반환할 수 있으므로, 재고나 결제 상태처럼 정확한 현재 값이 필요한 판단에 그대로 사용하지 않도록 주의한다.

## 운영 중 주의할 점

### 배치와 집계 쿼리

집계 쿼리는 결과가 몇 행이더라도 많은 데이터를 읽을 수 있다. 다음은 한 달의 접속 로그를 날짜별로 세는 예다.

```sql
SELECT DATE(al.accessDatetime) AS accessDate,
       COUNT(*) AS accessCount
FROM accessLog al
WHERE al.accessDatetime >= '2024-08-01 00:00:00'
  AND al.accessDatetime < '2024-09-01 00:00:00'
GROUP BY DATE(al.accessDatetime);
```

`accessDatetime`에 인덱스가 있어도 한 달치 로그가 많으면 실행 시간이 길어진다. 필요한 칼럼을 인덱스에 포함해 테이블 행을 읽는 비용을 줄이거나, 날짜 또는 ID 범위로 나눠 처리할 수 있다.

나눠 처리할 때는 각 구간의 경계를 맞춰 누락과 중복을 막아야 한다. 한 달의 합계는 일별 결과를 더할 수 있지만, 중복을 제거한 사용자 수처럼 단순히 더하면 안 되는 집계도 있다. 분할한 결과를 어떻게 합칠지 함께 정한다.

### 타입이 다른 칼럼 조인

조인하는 칼럼의 타입이 다르면 비교 과정에서 변환이 발생할 수 있다. 예를 들어 한 테이블의 사용자 ID는 정수이고 다른 테이블은 문자열이면, 예상한 인덱스 접근을 사용하지 못할 수 있다. MySQL은 문자열 칼럼과 숫자를 비교할 때 문자열 칼럼의 인덱스로 값을 빠르게 찾을 수 없다고 설명한다. ([MySQL 타입 변환 문서](https://dev.mysql.com/doc/refman/8.4/en/type-conversion.html))

같은 값을 나타내는 칼럼은 설계 단계부터 타입을 맞춘다. 문자열은 문자 집합과 콜레이션도 확인한다. 쿼리에서 인덱스 칼럼에 변환 함수를 붙이는 것으로 해결하려 하면 인덱스 사용에 영향을 줄 수 있으므로 실행 계획을 확인해야 한다.

### 테이블 변경

데이터가 많은 테이블의 구조를 변경하면 오래 걸리거나 다른 쿼리를 막을 수 있다. MySQL의 변경 방식은 버전, 스토리지 엔진, 변경 작업에 따라 다르다. 모든 변경이 새 테이블을 만들고 전체 데이터를 복사하는 것은 아니다.

| 방식      | 확인할 내용                                                                  |
| --------- | ---------------------------------------------------------------------------- |
| `INSTANT` | 지원되는 작업은 테이블 데이터를 다시 쓰지 않고 메타데이터 변경으로 처리한다. |
| `INPLACE` | 작업에 따라 테이블 재구성이 필요할 수 있고, 동시 쓰기 허용 여부도 다르다.    |
| `COPY`    | 새 테이블로 데이터를 복사하며, 복사 중 쓰기 작업이 제한된다.                 |

운영 DB에서 실행하기 전에 해당 변경이 어떤 방식으로 처리되는지, 잠금이 얼마나 필요한지 확인한다. 온라인 DDL도 잠금이 전혀 없다는 뜻은 아니다. 지원 작업과 제한은 [MySQL 온라인 DDL 문서](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl-operations.html)를 참고한다.

큰 테이블은 운영과 비슷한 데이터양으로 먼저 작업 시간을 확인한다. 서비스가 허용할 수 있는 중단 시간에 따라 점검 시간을 잡거나 온라인 변경 방법을 선택한다.

### 실패와 트랜잭션

주문 생성과 재고 차감처럼 함께 성공해야 하는 DB 변경은 하나의 트랜잭션으로 묶는다. 재고 차감이 실패했는데 주문만 남으면 데이터가 맞지 않게 된다.

Spring의 `@Transactional`은 트랜잭션이 적용된 메서드에서 `RuntimeException`이나 `Error`가 밖으로 전달되면 기본적으로 롤백한다. 체크 예외는 기본 설정에서 롤백하지 않으며, 필요하면 `rollbackFor` 등으로 규칙을 지정한다. ([Spring 롤백 규칙](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/rolling-back.html))

예외를 메서드 안에서 잡고 정상 반환하면 기대한 자동 롤백이 일어나지 않을 수 있다. 트랜잭션 경계와 예외 처리 방식을 같이 확인해야 한다.

DB 트랜잭션이 외부 결제나 메시지 전송까지 되돌려 주지는 않는다. DB 밖의 작업이 섞이면 실패 후 재시도와 보상 처리를 따로 설계한다.
