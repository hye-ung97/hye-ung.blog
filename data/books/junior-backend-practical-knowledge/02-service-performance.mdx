성능 문제를 찾으려면 현재 응답 시간과 처리량부터 알아야 한다. 트래픽이 많은 시간대의 값을 측정하고, 요청 처리 과정에서 어느 단계가 느린지 확인한다.

## 응답 시간과 처리량

### 응답 시간

응답 시간은 클라이언트가 요청을 시작한 뒤 응답을 받기까지 걸리는 시간이다. 전체 JSON 응답을 받는 시점을 기준으로 하면 연결, 대기, 서버 처리, 데이터 전송 시간이 모두 포함된다.

- TTFB(Time to First Byte): 응답의 첫 번째 바이트를 받을 때까지 걸리는 시간
- TTLB(Time to Last Byte): 응답의 마지막 바이트를 받을 때까지 걸리는 시간

![응답 시간과 TTFB, TTLB. 연결과 요청 전송, 대기, 서버 처리를 거쳐 첫 바이트를 받을 때까지가 TTFB다. 마지막 바이트까지 받는 TTLB에는 응답 전송 시간도 포함된다. API 요청을 단순화한 그림이며 각 구간의 길이는 실제 소요 시간과 다르다.](/static/images/books/junior-backend-practical-knowledge/response-time-v2.png)

파일 다운로드처럼 응답 데이터가 크거나 네트워크가 느리면 TTFB와 TTLB의 차이가 커진다. 서버 처리가 끝났어도 데이터를 받는 데 시간이 더 걸릴 수 있기 때문이다.

### 처리량

처리량은 단위 시간당 시스템이 처리하는 작업량이다.

| 지표                         | 의미                      |
| ---------------------------- | ------------------------- |
| TPS(Transactions Per Second) | 초당 처리하는 트랜잭션 수 |
| RPS(Requests Per Second)     | 초당 처리하는 요청 수     |

TPS와 RPS는 무엇을 한 건으로 집계하는지 확인해야 한다. 동시 요청 수와도 구분해야 한다. 처리량은 일정 시간 동안 처리한 양이고, 동시 요청 수는 특정 시점에 함께 처리 중인 요청의 수다.

요청 유입 속도가 처리 능력을 계속 넘어서면 대기가 늘어난다. 응답 시간이 길어지고, 타임아웃이나 오류가 발생할 수 있다.

현재 처리량과 응답 시간을 기준으로 목표를 정하고, 개선 전후의 결과를 비교한다.

## 병목 지점과 서버 확장

### 병목 지점

DB 쿼리, 외부 API 호출, 계산 등 요청을 처리하는 작업별로 실행 시간을 측정한다. 느릴 것 같은 코드를 짐작할 수는 있지만, 실제로 시간이 오래 걸리는지 확인해야 한다.

모니터링 도구를 사용하고, 도구가 없다면 주요 작업의 실행 시간을 로그로 남긴다.

### 수직 확장과 수평 확장

| 구분                 | 방법                                       | 확인할 내용                                              |
| -------------------- | ------------------------------------------ | -------------------------------------------------------- |
| 수직 확장(Scale Up)  | CPU, 메모리, 디스크 등 서버 자원을 늘린다. | 해당 자원이 부족한지 확인한다.                           |
| 수평 확장(Scale Out) | 서버 수를 늘려 요청을 분산한다.            | DB와 외부 API가 늘어난 요청을 감당할 수 있는지 확인한다. |

서버 확장으로 부하를 낮추면 문제를 해결할 시간을 벌 수 있다. 다만 DB나 외부 API가 이미 병목이라면 애플리케이션 서버를 늘려도 효과가 작다. 늘어난 서버가 더 많은 요청을 보내면서 연동 대상의 부하가 커질 수도 있다.

## DB 커넥션 풀

DB 연결을 매번 생성하고 종료하면 그만큼 응답 시간이 늘어난다. 커넥션 풀은 연결을 보관했다가 재사용한다.

애플리케이션은 DB 작업이 필요할 때 풀에서 커넥션을 빌리고, 작업이 끝나면 반환한다. 사용할 수 있는 커넥션이 없으면 반환될 때까지 기다린다.

### 커넥션 풀 크기

풀 크기를 늘리면 커넥션을 기다리는 시간을 줄일 수 있다. 하지만 DB가 이미 포화 상태라면 연결을 늘려도 처리량이 나아지지 않을 수 있다.

목표 처리량, 커넥션을 점유하는 시간, DB가 감당할 수 있는 동시 작업량을 보고 풀 크기를 정한다. 트래픽이 갑자기 증가하는 서비스에서는 필요한 연결을 미리 준비해 두는 방법도 생각할 수 있다.

서버를 수평 확장할 때는 전체 커넥션 수도 계산해야 한다. 서버마다 풀이 있으므로 서버 수가 늘면 DB에 연결할 수 있는 최대 커넥션 수도 늘어난다.

![서버 수와 DB 커넥션 수. 최대 풀 크기가 각각 10인 서버 세 대가 하나의 DB에 연결된다. 전체 커넥션 수는 최대 30개다. 서버 수에 따른 연결 수를 계산하기 위한 예다.](/static/images/books/junior-backend-practical-knowledge/pool-connections-v2.png)

### 대기 시간과 연결 수명

| 설정                  | 의미                                               |
| --------------------- | -------------------------------------------------- |
| 커넥션 획득 대기 시간 | 사용할 수 있는 커넥션을 기다리는 최대 시간         |
| 최대 유휴 시간        | 사용하지 않는 커넥션을 풀에 유지하는 시간          |
| 유효성 검사           | 커넥션을 정상적으로 사용할 수 있는지 확인하는 절차 |
| 최대 유지 시간        | 생성된 커넥션을 유지하는 최대 수명                 |

커넥션을 오래 기다리면 응답도 늦어진다. 대기 중인 요청이 서버 자원을 계속 차지하므로, 서비스의 응답 시간 목표에 맞춰 대기 시간을 제한한다.

연결 수명과 검사 설정은 DB와 네트워크의 연결 종료 정책에 맞춘다. 세부 동작은 커넥션 풀마다 다르다. 예를 들어 [HikariCP](https://github.com/brettwooldridge/HikariCP)는 최대 유지 시간이 지나도 사용 중인 커넥션을 바로 끊지 않고, 반환된 뒤 제거한다.

### 보충: Node.js와 Spring Boot

책 내용과 별개로 두 환경에서 커넥션 풀을 어떻게 사용하는지 찾아봤다. Node.js는 MySQL 드라이버인 [mysql2](https://sidorares.github.io/node-mysql2/docs), Spring Boot는 JDBC와 HikariCP를 사용하는 경우를 기준으로 비교했다.

Node.js에서는 DB 드라이버가 제공하는 풀을 생성해 사용한다. Spring Boot는 `spring-boot-starter-jdbc`나 `spring-boot-starter-data-jpa`를 사용하면 HikariCP 의존성이 포함되고, 일반적인 자동 설정에서 HikariCP 기반의 `DataSource`를 구성한다. ([Spring Boot 공식 문서](https://docs.spring.io/spring-boot/reference/data/sql.html))

| 구분           | Node.js (mysql2)                                                                         | Spring Boot (JDBC/HikariCP)                                                      |
| -------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 풀 생성        | `mysql.createPool()`로 생성해 공유한다.                                                  | 자동 설정으로 구성된 `DataSource`를 사용한다.                                    |
| 최대 커넥션 수 | `connectionLimit`으로 설정한다.                                                          | `maximum-pool-size`로 설정한다.                                                  |
| 커넥션 생성    | 필요할 때 한도 안에서 연결을 만든다.                                                     | `minimum-idle`을 기준으로 유휴 연결을 유지한다.                                  |
| 커넥션 반환    | `pool.query()`와 `pool.execute()`는 자동 반환한다. 직접 빌렸다면 `release()`로 반환한다. | `JdbcTemplate` 등이 연결을 관리한다. 직접 빌린 풀의 연결은 `close()`로 반환한다. |

Spring Boot의 HikariCP 설정은 `spring.datasource.hikari` 아래에 둔다. 예를 들어 최대 커넥션 수는 `spring.datasource.hikari.maximum-pool-size`로 지정한다. 세부 설정은 [HikariCP 문서](https://github.com/brettwooldridge/HikariCP), Spring의 연결 관리는 [JdbcTemplate 관련 문서](https://docs.spring.io/spring-framework/reference/data-access/jdbc/connections.html)를 참고했다.

Node.js도 여러 커넥션으로 DB 요청을 동시에 보낼 수 있다. 풀을 프로세스마다 하나씩 만드는 구성이라면, 같은 서버에서 프로세스를 여러 개 실행할 때도 전체 커넥션 수가 늘어난다. 요청마다 풀을 새로 만들지 않고, 생성한 풀을 재사용해야 한다.

## 서버 캐시

캐시는 자주 조회하는 데이터나 계산 결과를 저장해 반복 작업을 줄인다. DB 조회 결과, 복잡한 계산 결과, 외부 API 응답 등을 보관할 수 있다.

캐시에 값이 있으면 바로 사용한다. 없으면 원본 데이터를 조회하고, 결과를 캐시에 저장한 뒤 사용한다.

![캐시 조회 흐름. HIT는 캐시에 값이 있는 경우로, 캐시를 확인한 뒤 바로 응답한다. MISS는 값이 없는 경우로, DB에서 조회한 결과를 캐시에 저장한 뒤 응답한다.](/static/images/books/junior-backend-practical-knowledge/cache-aside-v2.png)

### 적중률과 삭제 규칙

캐시 적중률은 전체 조회 중 캐시에서 데이터를 찾은 비율이다.

```text
캐시 적중률 = 캐시에서 데이터를 찾은 횟수 / 전체 캐시 조회 횟수
```

적중률이 높아지면 DB나 외부 시스템을 호출하는 횟수가 줄어든다. 응답 시간을 줄이고 처리량을 높이는 데 도움이 된다.

캐시 공간은 제한적이므로 어떤 데이터를 남기고 지울지 정해야 한다.

- LRU(Least Recently Used): 가장 오랫동안 사용하지 않은 데이터를 제거한다.
- LFU(Least Frequently Used): 사용 빈도가 가장 낮은 데이터를 제거한다.
- FIFO(First In, First Out): 가장 먼저 저장한 데이터를 제거한다.

유효 시간(TTL)을 설정해 일정 시간이 지난 데이터를 만료시키는 방법도 함께 사용한다.

### 로컬 캐시와 리모트 캐시

| 구분                | 로컬 캐시                       | 리모트 캐시                               |
| ------------------- | ------------------------------- | ----------------------------------------- |
| 저장 위치           | 애플리케이션 프로세스의 메모리  | 별도의 캐시 서버                          |
| 접근 방식           | 메모리에 직접 접근              | 네트워크 통신                             |
| 장점                | 빠른 접근, 단순한 구조          | 여러 서버에서 공유 가능, 용량 확장에 유리 |
| 단점                | 메모리 제한, 서버별 데이터 차이 | 통신 지연, 별도 운영 필요                 |
| 애플리케이션 재시작 | 캐시 데이터가 사라진다.         | 캐시 서버가 유지되면 데이터도 남는다.     |

데이터가 적고 변경 빈도가 낮다면 로컬 캐시를 사용할 수 있다. 여러 서버에서 같은 캐시를 공유하거나 큰 용량이 필요하다면 리모트 캐시를 고려한다.

### 사전 적재와 무효화

트래픽이 특정 시점에 몰린다면 자주 조회할 데이터를 캐시에 미리 넣어 초기 부하를 줄일 수 있다.

캐시를 언제 지우거나 갱신할지는 오래된 값을 얼마나 허용할 수 있는지에 따라 정한다. 가격이나 게시글처럼 최신 값이 필요한 데이터는 변경 시 캐시도 삭제하거나 갱신한다. 일정 시간 동안 이전 값을 허용할 수 있다면 TTL을 사용할 수 있다.

여러 서버가 로컬 캐시를 쓴다면 각 서버의 캐시를 함께 갱신할 방법도 필요하다.

## 메모리 사용과 데이터 전송

### 가비지 컬렉션

가비지 컬렉터(GC)는 더 이상 사용하지 않는 객체의 메모리를 회수한다. Java에서는 GC의 일부 단계에서 애플리케이션 스레드가 일시 중단된다. 이를 Stop-the-World(STW)라고 한다.

중단 시간과 동작 방식은 GC 종류에 따라 다르다. [G1 GC](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html)는 일부 작업을 애플리케이션 실행과 동시에 수행한다.

불필요한 객체 생성이나 큰 메모리 할당은 GC 부담을 늘릴 수 있다. 메모리 사용량뿐 아니라 GC 빈도와 중단 시간도 확인한다.

파일 다운로드처럼 큰 데이터를 처리할 때는 스트림을 사용해 전체 파일을 한꺼번에 메모리에 올리지 않도록 한다.

### 응답 데이터 압축

응답 데이터의 크기를 줄이면 전송 시간을 줄일 수 있다. JSON, HTML, CSS 같은 텍스트 데이터는 gzip 등으로 압축해 전송한다.

압축 효과는 데이터에 따라 다르다. 이미 압축된 이미지나 파일은 다시 압축해도 효과가 작을 수 있다. 압축에 드는 CPU 비용도 확인해야 한다. ([MDN HTTP 압축](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Compression))

서버에 압축을 설정했더라도 프록시 등 중간 장비를 거친 최종 응답이 실제로 압축됐는지 확인한다. 전송량을 줄이면 네트워크 비용도 줄일 수 있다.

### 정적 자원

동적 자원은 요청 시점이나 조건에 따라 응답이 달라지는 데이터다. 제품 목록 HTML이나 제품 상세 JSON이 여기에 해당한다.

정적 자원은 파일이 변경되기 전까지 같은 내용을 제공한다. 이미지, JavaScript, CSS가 대표적이다. 정적 자원이 차지하는 전송량도 함께 확인한다.
