[3장](/books/junior-backend-practical-knowledge/03-db-design-and-query)에서는 DB 설계와 쿼리 성능을 살펴봤다. 쿼리가 빨라도 요청 처리 중 호출하는 외부 API가 느려지면 전체 응답 시간은 길어진다. 이때 대기 중인 요청이 스레드나 DB 커넥션까지 오래 점유하면 다른 기능도 영향을 받는다.

이번 장은 외부 호출의 대기와 재시도를 제한하고, 장애가 다른 기능으로 번지는 영향을 줄이는 방법을 다룬다. 책을 읽고 정리한 내용을 바탕으로 재구성했으며, 공식 문서를 참고해 추가로 살펴본 내용은 **보충**으로 구분했다.

## 타임아웃

### 느린 응답과 스레드 풀

A 서비스가 B 서비스를 동기 방식으로 호출한다고 가정한다. A 서비스의 톰캣 요청 처리 스레드는 200개이고, 요청 하나가 스레드 하나를 점유한다. B 서비스에는 문제가 생겨 응답에 60초 넘게 걸리고 있다.

타임아웃이 없다면 다음과 같은 일이 생긴다.

| 시점 | 들어온 요청 | A 서비스의 상태                                      |
| ---- | ----------- | ---------------------------------------------------- |
| 0초  | 100개       | 스레드 100개가 B 서비스의 응답을 기다린다.           |
| 10초 | 100개       | 스레드 200개가 모두 B 서비스의 응답을 기다린다.      |
| 20초 | 100개       | 사용할 스레드가 없어 새 요청을 바로 처리하지 못한다. |

세 번째로 들어온 요청이 B 서비스를 사용하지 않는 기능이라면 어떨까? 같은 스레드 풀을 쓰면 이 요청도 기다려야 한다. B 서비스의 문제가 A 서비스의 다른 기능까지 막는 것이다.

사용자가 기다리다 새로고침하면 부하가 더 커질 수 있다. 브라우저에서 이전 요청을 중단해도 서버의 작업이 바로 취소되는 것은 아니다. 앞선 요청을 처리하는 중에 새 요청까지 들어오게 된다.

### 타임아웃을 설정하면

이번에는 외부 호출의 전체 대기를 5초로 제한한다. 0초에 들어온 100개 요청은 5초 안에 응답을 받지 못하면 타임아웃으로 끝난다. A 서비스는 실패 응답을 보내고 스레드를 반환하므로, 10초에 다음 요청이 들어오면 이 스레드를 다시 사용할 수 있다.

![타임아웃에 따른 스레드 점유 차이. 동기 방식으로 10초마다 요청 100개를 받는 예다. 타임아웃이 없으면 20초 시점에 앞선 요청들이 스레드 200개를 점유한다. 전체 호출을 5초로 제한하면 각 요청 묶음이 종료된 뒤 스레드를 재사용할 수 있다. 외부 서버의 작업까지 중단된다는 뜻은 아니다.](/static/images/books/junior-backend-practical-knowledge/timeout-thread-occupancy.png)

타임아웃은 B 서비스의 장애를 해결해 주지는 않는다. 대신 A 서비스가 자원을 붙잡고 기다리는 시간을 줄인다. 다만 B 서비스에서는 작업이 계속될 수 있으므로, 타임아웃 응답을 받았다고 외부 처리까지 취소됐다고 보면 안 된다.

### 연결 타임아웃과 읽기 타임아웃

| 구분                              | 제한하는 시간                                 |
| --------------------------------- | --------------------------------------------- |
| 연결 타임아웃(Connection timeout) | 대상 서버와 연결을 맺기까지 기다리는 시간     |
| 읽기 타임아웃(Read timeout)       | 연결 후 응답 데이터를 읽기 위해 기다리는 시간 |

연결을 맺었더라도 상대 서버가 응답을 보내지 않으면 대기는 계속된다. 연결 타임아웃과 함께 읽기 타임아웃도 설정해야 한다.

### 보충: 읽기 타임아웃과 전체 호출 시간

앞의 5초는 예시이며, 전체 외부 호출의 대기가 5초 안에 끝난다고 가정한 값이다. 실제 설정값은 외부 서비스의 응답 시간 분포와 우리 서비스가 허용하는 응답 시간을 보고 정한다.

읽기 타임아웃의 정확한 범위는 HTTP 클라이언트마다 다르다. 각 읽기 사이의 대기 시간을 제한하는 설정이라면, 데이터가 조금씩 계속 들어올 때 전체 호출 시간은 설정값보다 길어질 수 있다. 커넥션 풀 대기, DNS 조회, TLS 연결까지 어떤 시간 제한이 적용되는지도 다를 수 있다.

따라서 읽기 타임아웃 5초와 전체 호출 제한 5초를 같은 설정으로 보면 안 된다. ([AWS의 타임아웃 설명](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/))

## 재시도

### 재시도 여부

일시적인 네트워크 오류는 같은 요청을 다시 보내면 해결될 수 있다. 다만 실패 원인과 중복 실행의 영향을 구분해야 한다.

| 상황                 | 재시도할 때의 판단 기준                         |
| -------------------- | ----------------------------------------------- |
| 단순 조회            | 반복 실행해도 데이터를 변경하지 않는가?         |
| 연결 타임아웃        | 요청을 보내기 전 연결 단계에서 실패했는가?      |
| 상태를 변경하는 요청 | 같은 요청을 반복해도 중복 변경이 생기지 않는가? |

포인트 내역 조회는 다시 호출해도 잔액이 바뀌지 않는다. 반면 포인트 차감에서 읽기 타임아웃이 발생하면 판단이 어렵다. 이미 차감을 끝냈는데 응답만 전달되지 않았을 수 있기 때문이다. 이 상태에서 같은 요청을 보내면 포인트가 두 번 차감될 수 있다.

변경 요청을 재시도하려면 멱등성이 필요하다. 멱등성은 같은 연산을 여러 번 적용해도 한 번 적용했을 때와 결과가 같은 성질이다. API가 이 동작을 보장하는지에 따라 재시도 가능 여부가 달라진다.

같은 API라도 실패 원인에 따라 판단이 달라진다. 콘텐츠 ID를 비워서 좋아요 API를 호출하면 입력 검증에서 실패할 것이다. 이때 값을 고치지 않고 같은 요청을 다시 보내도 문제는 해결되지 않는다.

### 재시도 횟수와 간격

재시도에는 횟수와 간격을 정한다. 횟수를 늘릴수록 사용자의 대기 시간과 외부 서비스의 부하가 함께 늘어난다. 여러 번 실패했다면 일시적인 오류가 아닌 다른 원인이 있을 수 있으므로 정해진 횟수에서 멈춘다.

여러 차례 재시도할 때는 간격을 점진적으로 늘릴 수 있다. 첫 번째 재시도는 1초 뒤, 두 번째는 2초 뒤에 하는 식이다. 바로 반복해서 호출하는 것보다 연동 서비스에 가해지는 부하를 줄일 수 있다.

### 재시도 폭풍

연동 서비스가 과부하로 느려졌다면 재시도가 상황을 악화시킬 수 있다. 처리할 요청이 쌓인 상태에서 재시도 요청까지 몰리기 때문이다. 이를 재시도 폭풍(Retry storm)이라고 한다.

재시도는 일시적인 실패를 회복하는 데 유용하지만, 과부하로 실패하는 서비스에는 요청을 더 쌓는 결과가 될 수 있다.

### 보충: 멱등성 키

변경 요청에 작업을 구분하는 멱등성 키를 보내는 방법이 있다. 주문의 포인트 차감 요청에 같은 키를 사용하고, 포인트 서비스가 이미 처리한 키라면 중복 차감 없이 기존 결과를 반환하도록 만드는 식이다.

재시도할 때 키를 새로 만들면 별개의 작업으로 처리될 수 있다. 같은 작업에는 같은 키를 사용하고, 상대 서비스에서도 동시 요청을 포함해 중복 실행을 막아야 한다. 키를 보내는 것만으로 멱등성이 보장되는 것은 아니다. ([AWS의 멱등 API 설명](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/))

HTTP 메서드가 가진 멱등성은 [HTTP 메서드와 멱등성](/blog/http-method-idempotency)에서 따로 정리했다.

### 보충: 지수 백오프와 지터

재시도 사이에 대기 시간을 두는 방법을 백오프(Backoff)라고 한다. 대기 시간을 200ms, 400ms, 800ms처럼 배수로 늘리면 지수 백오프(Exponential backoff)다. 계속 늘어나지 않도록 대기 시간에 상한도 둔다.

간격을 늘리는 것만으로 요청이 고르게 분산되지는 않는다. 요청 100개가 동시에 실패한 뒤 모두 200ms를 기다리면, 200ms 후에 다시 100개가 몰릴 수 있다. 다음 간격을 400ms로 늘려도 같은 일이 반복된다.

지터(Jitter)는 대기 시간에 무작위성을 넣어 재시도 시점을 흩어 놓는다. 다음은 각 시도의 대기 시간을 0부터 백오프 상한 사이에서 무작위로 정하는 Full Jitter 방식의 예다.

| 재시도  | 지터 없는 지수 백오프 | Full Jitter 적용             |
| ------- | --------------------- | ---------------------------- |
| 첫 번째 | 200ms 대기            | 0~200ms 사이에서 무작위 선택 |
| 두 번째 | 400ms 대기            | 0~400ms 사이에서 무작위 선택 |
| 세 번째 | 800ms 대기            | 0~800ms 사이에서 무작위 선택 |

지터는 재시도 시점을 분산하는 방법이다. 재시도 횟수와 전체 대기 시간의 제한도 함께 필요하다. ([AWS의 지수 백오프와 지터 설명](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/))

### 보충: 전체 대기 시간과 여러 계층의 재시도

재시도 정책을 정할 때는 최초 호출과 각 재시도, 그 사이의 대기 시간을 더해 본다. 각 호출의 전체 시간을 1초로 제한한다면 다음 예시는 다른 처리 시간을 제외하고도 최대 3.6초가 걸린다.

```text
최초 호출 1초 + 대기 0.2초 + 재시도 1초 + 대기 0.4초 + 재시도 1초
= 최대 3.6초
```

우리 API가 3초 안에 응답해야 한다면 이 정책은 맞지 않는다. 남은 시간 안에 다음 시도를 끝낼 수 있어야 한다.

여러 계층에서 각각 재시도하면 최종 호출 횟수는 곱해진다. A가 B를 최대 세 번 호출하고 B가 매번 C를 최대 세 번 호출하면, A의 요청 하나가 C의 호출을 최대 아홉 번 만들 수 있다. 재시도를 담당할 계층을 정하고 HTTP 클라이언트나 SDK의 기본 재시도도 포함해 계산한다. ([AWS의 재시도 설명](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/))

## 동시 요청 제한과 벌크헤드

B 서비스가 안정적으로 감당할 수 있는 동시 요청 수는 100개라고 가정한다. 선착순 이벤트로 들어온 요청 300개를 그대로 전달하면 B 서비스에 대기가 쌓이고, 응답을 기다리는 A 서비스도 함께 느려질 수 있다.

이때 A 서비스에서 B 서비스로 보내는 동시 요청을 100개까지로 제한할 수 있다. 한도에 도달하면 추가 요청은 B 서비스로 보내지 않고 바로 실패 응답을 반환한다. 일시적으로 요청을 수용하기 어려운 상황에는 `503 Service Unavailable` 상태 코드를 사용할 수 있다.

이처럼 구성 요소를 격리해 한쪽의 장애가 다른 쪽에 미치는 영향을 줄이는 설계가 벌크헤드(Bulkhead) 패턴이다.

### 보충: 호출 한도의 적용 범위

호출 한도는 상대 서비스의 처리 능력과 우리 서비스의 자원을 함께 보고 정한다. 특정 연동이 요청 처리 스레드를 모두 사용하면 다른 기능도 멈출 수 있다. 외부 서비스별 세마포어를 두거나 별도의 스레드 풀을 사용하는 방법이 있다.

바로 실패시키는 대신 큐에서 기다리게 할 수도 있다. 이 경우 큐의 크기와 대기 시간에도 한도가 필요하다. ([Resilience4j Bulkhead 문서](https://resilience4j.readme.io/docs/bulkhead))

한도가 인스턴스별로 적용되는지도 중요하다. A 서비스의 인스턴스 다섯 대가 각각 100개를 허용하면 B 서비스에는 최대 500개가 전달될 수 있다. 다른 호출자의 트래픽까지 더해지므로, 한 인스턴스의 설정값만으로 전체 호출량을 판단할 수 없다.

## 서킷 브레이커

서킷 브레이커(Circuit breaker)는 최근 호출 결과를 보고 장애로 판단한 대상의 호출을 차단한다. 차단 중에는 외부 응답을 기다리지 않고 바로 실패를 반환하며, 이후 일부 요청으로 복구 여부를 확인한다.

누전 차단기에 비유할 수 있다. 과전류가 흐르면 차단기가 전기를 끊는 것처럼, 외부 호출에 오류가 일정 기준 이상 발생하면 호출을 차단한다.

### 닫힘, 열림, 반 열림

1. **닫힘(Closed)**: 외부 호출을 허용한다. 오류가 발생하면 최근 일정 시간 또는 일정 호출 수를 기준으로 오류 비율을 집계하고, 기준에 도달하면 열림으로 전환한다.
2. **열림(Open)**: 외부 호출을 수행하지 않고 바로 실패 응답을 반환한다. 지정한 시간이 지나면 반 열림에서 복구 여부를 확인한다.
3. **반 열림(Half-open)**: 일부 요청만 허용한다. 복구 기준을 충족하면 닫힘으로 돌아가고, 그렇지 않으면 다시 열림으로 돌아간다.

![서킷 브레이커의 상태 전환. 닫힘에서는 정상 호출을 허용한다. 실패율이 임계치에 도달하면 열림으로 전환해 호출을 차단한다. 대기 시간이 지나면 반 열림에서 제한된 요청으로 복구를 확인한다. 복구 기준을 충족하면 닫힘으로 돌아가고, 실패하면 다시 열림으로 돌아간다. 그림 아래의 최소 호출 수에 관한 내용은 이어지는 보충에서 다룬다.](/static/images/books/junior-backend-practical-knowledge/circuit-breaker-states.png)

열림 상태에서는 외부 서비스에 요청을 보내지 않으므로 과부하에서 벗어날 기회가 생긴다. 우리 서비스도 불필요한 대기에 자원을 쓰지 않는다. 문제가 있는 기능을 실행하지 않고 바로 실패로 처리하는 이런 방식을 빠른 실패(Fail fast)라고 한다.

### 보충: 서킷 브레이커의 설정

오류 비율을 계산하려면 관찰 구간 외에 최소 호출 수도 정해야 한다. 한 건을 호출해 실패했다고 바로 실패율 100%로 판단해 차단하지 않도록 하기 위해서다. 연결 오류를 장애로 집계할지, 입력 검증 오류는 제외할지 등 오류 분류도 필요하다. 라이브러리에 따라 느린 호출의 비율을 기준으로 차단할 수도 있다.

서킷 브레이커가 닫혀 있는 동안에는 호출이 실행된다. 이미 실행 중인 호출의 시간이나 동시 요청 수를 서킷 브레이커 자체가 제한해 주는 것은 아니다. 따라서 각 호출의 대기는 타임아웃으로, 동시에 점유할 자원은 벌크헤드로 제한한다. ([Resilience4j CircuitBreaker 문서](https://resilience4j.readme.io/docs/circuitbreaker))

## 외부 연동과 DB 트랜잭션

### 외부 호출 실패와 트랜잭션 롤백

주문을 DB에 저장하고 외부 포인트 서비스에서 포인트를 차감한다고 가정한다. DB 트랜잭션 안에서 포인트 호출이 실패하면 주문 저장을 롤백할 수 있다. 다만 읽기 타임아웃이라면 실제로는 포인트가 차감됐을 수 있다. 우리 DB의 롤백이 외부 서비스의 변경까지 되돌려 주지는 않는다.

이때는 두 시스템의 데이터를 정기적으로 대조하고 보정하는 방법을 사용할 수 있다. 예를 들어 하루에 한 번 전날 주문 내역과 포인트 사용 내역을 비교하고, 맞지 않는 건을 수동 또는 자동으로 처리한다.

연동 서비스가 처리 결과를 알려주는 API를 제공한다면 성공 여부를 조회할 수도 있다. DB 트랜잭션을 끝내기 전에 읽기 타임아웃이 발생한 경우, 결과 확인 API로 성공이 확인되면 트랜잭션을 이어가고 실패가 확인되면 롤백하는 방식이다.

이미 DB를 롤백한 뒤라면 기존 트랜잭션을 이어갈 수는 없다. 이때는 조회한 결과를 바탕으로 별도의 보정 처리를 해야 한다.

### 외부 호출 성공 후 DB 반영이 실패한 경우

포인트 차감에는 성공했지만, 이후 주문 저장이나 DB 커밋에 실패할 수도 있다. DB를 롤백해도 외부 서비스에서 차감한 포인트는 돌아오지 않는다.

이 경우에는 포인트 차감을 취소하는 API를 호출해 앞선 변경을 되돌려야 한다. 다만 취소 API가 없거나 취소 호출도 실패할 수 있으므로, 데이터 일관성이 중요한 기능에는 정기 대조와 보정 절차가 필요하다.

### DB 커넥션을 점유하는 시간

DB 커넥션을 획득한 상태에서 외부 API를 호출하면, 쿼리를 실행하지 않는 동안에도 커넥션을 점유할 수 있다.

```text
커넥션 획득
  → DB 쿼리 0.1초
  → 외부 API 호출 4.8초
  → DB 쿼리 0.1초
커밋 후 커넥션 반환
```

쿼리 실행 시간은 총 0.2초지만 커넥션 점유 시간은 약 5초다. 외부 호출이 느려질수록 커넥션 반환도 늦어진다. 이런 요청이 쌓이면 다른 기능도 DB 커넥션을 기다리게 된다.

DB 연동과 분리할 수 있다면 외부 호출을 커넥션 사용 전이나 후에 실행하는 방법을 고려할 수 있다. 다만 DB 커밋 이후 외부 호출이 실패하면 이미 반영된 변경을 롤백할 수 없다. 데이터를 되돌리는 보상 트랜잭션이나 업무에 맞는 후보정이 필요하다.

### 보충: 결과 확인과 보상 처리

결과 확인 API가 아직 처리 중이라고 응답하거나, 조회 자체가 다시 타임아웃이 날 수도 있다. 결과를 모르는 상태와 실패가 확인된 상태를 구분해 두어야 한다. 같은 DB 트랜잭션을 유지한 채 결과를 오래 기다리면 앞서 살펴본 커넥션 점유 문제도 생긴다.

나중에 다시 확인할 작업을 기록한다면, 원래 트랜잭션이 롤백될 때 그 기록도 함께 사라지지 않도록 해야 한다.

DB를 커밋한 뒤 외부 호출을 실행하는 방식에서는 커밋 직후 프로세스가 종료되면 호출이 누락될 수 있다. DB 변경과 함께 후속 작업을 기록하고 별도 처리기가 실행하는 방식으로 누락에 대비할 수 있다. 이때도 중복 실행에 대한 처리는 필요하다.

취소나 보상 역시 별도의 작업이므로 실패할 수 있다. 재처리할 수 있도록 작업을 남기고, 같은 보상이 두 번 실행되더라도 문제가 없게 해야 한다. ([Microsoft의 보상 트랜잭션 설명](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction))
