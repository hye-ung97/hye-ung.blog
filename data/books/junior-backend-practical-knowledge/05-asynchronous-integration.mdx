로그인한 사용자에게 포인트를 지급한다고 해 보자. 포인트 서비스의 응답이 느리면 로그인도 함께 늦어진다. 포인트 지급에 실패했다고 로그인까지 실패하게 해야 할까?

포인트가 조금 늦게 지급돼도 괜찮고, 실패한 지급은 나중에 다시 처리할 수 있다면 로그인 응답이 포인트 지급을 기다릴 필요는 없다. 이처럼 다음 작업에 외부 연동 결과가 당장 필요하지 않을 때 비동기 연동을 고려할 수 있다.

## 동기로 기다려야 하는 작업인가

동기 방식에서는 호출한 작업이 끝나야 다음 작업으로 넘어간다. 외부 서비스를 동기로 호출하면 그 서비스의 응답 시간과 실패가 현재 요청에 영향을 준다.

비동기 방식은 외부 연동이 끝날 때까지 기다리지 않고 다음 작업을 진행한다. 다만 모든 외부 호출을 비동기로 바꿀 수 있는 것은 아니다. 다음 작업이 연동 결과를 필요로 하는지부터 확인해야 한다.

비동기로 연동할 수 있는 작업의 예는 다음과 같다.

| 먼저 처리하는 작업 | 비동기로 연동할 작업          |
| ------------------ | ----------------------------- |
| 주문 생성          | 판매자에게 푸시 알림 발송     |
| 학습 완료          | 학생에게 포인트 지급          |
| 콘텐츠 등록        | 검색 서비스에 콘텐츠 반영     |
| 인증 번호 요청     | SMS 서비스로 인증 메시지 발송 |

이런 작업은 연동에 약간의 시차를 허용할 수 있다. 실패했을 때 다시 시도하거나 수동으로 처리할 수 있는 작업도 있고, 용도에 따라 실패를 무시할 수 있는 작업도 있다.

포인트 지급에 실패해도 로그인을 허용할 수 있는지, 검색에 조금 늦게 노출돼도 되는지처럼 기능별로 판단해야 한다. 비동기로 실행할 방법을 고르기 전에 이 조건부터 정한다.

## 별도 스레드로 실행하기

가장 간단한 방법은 외부 연동을 별도 스레드에서 실행하는 것이다. 요청을 처리하는 스레드는 외부 작업의 완료를 기다리지 않고 응답할 수 있다.

작업마다 새 스레드를 만들 수도 있지만 스레드는 자체적으로 메모리를 사용한다. 스레드 풀을 사용하면 작업을 실행할 스레드를 일정 개수로 유지하고 재사용할 수 있다.

Java에서는 스레드 풀을 이용할 수 있고, Spring은 `@Async`로 비동기 실행 기능을 제공한다. 비동기로 실행하는 메서드는 `sendPushAsync()`처럼 이름에도 실행 방식을 드러내면 호출부를 읽을 때 이해하기 쉽다.

### 오류는 비동기 작업 안에서 처리한다

비동기 메서드를 호출하는 부분만 `try-catch`로 감싸도 별도 스레드에서 발생한 예외는 잡히지 않는다. 호출부는 이미 다음 작업으로 넘어갔을 수 있다. 외부 연동을 실행하는 쪽에서 재시도하거나 실패 내역을 남겨야 한다.

트랜잭션도 주의해야 한다. 책에는 트랜잭션 처리 중 호출한 메서드가 비동기로 실행돼, 그 안에서 예외가 발생했는데도 호출부의 트랜잭션은 커밋된 사례가 나온다. 비동기 작업의 실패가 원래 요청의 롤백으로 이어질 것이라고 기대하면 안 된다.

## 메시징으로 시스템 연결하기

서로 다른 시스템을 비동기로 연결할 때는 메시징 시스템을 사용할 수 있다. 생산자는 전달할 데이터를 메시지로 보내고, 소비자는 메시징 시스템에서 받은 메시지로 작업을 처리한다.

중간에 메시징 시스템을 두면 메시지를 보관하는 버퍼 역할을 할 수 있다. 생산자의 트래픽이 갑자기 증가해도 소비자는 자신의 처리 능력에 맞춰 메시지를 가져와 처리한다. 직접 호출할 때보다 두 시스템의 처리 속도를 분리하기 좋다.

![메시징 시스템을 통한 소비자 확장. 생산자인 시스템 A가 메시지를 발행하면 메시징 시스템이 시스템 B와 시스템 C에 전달한다. 새 소비자를 연결해 연동 대상을 늘린다.](/static/images/books/junior-backend-practical-knowledge/async-messaging-v3.png)

연동 대상이 늘어날 때도 이점이 있다. 이미 발행하는 메시지를 다른 시스템에서도 사용할 수 있다면 생산자에 직접 호출 코드를 추가하는 대신 새로운 소비자를 연결할 수 있다.

그렇다고 소비자의 상태가 생산자와 완전히 무관해지는 것은 아니다. 소비가 계속 느려지면 메시지가 쌓이고, 저장 공간이나 큐의 한도에 도달하면 생산자도 메시지를 넣지 못할 수 있다. 메시지 소비 속도와 적체를 함께 모니터링해야 한다.

### Kafka, RabbitMQ, Redis Pub/Sub

| 기술          | 주요 특징                                                                                                   | 선택할 때 볼 점                                                                                     |
| ------------- | ----------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Kafka         | 메시지를 파일에 보관하고 소비자가 읽어 가는 풀 모델이다. 파티션 단위로 순서를 유지한다.                     | 높은 처리량, 수평 확장, 메시지 재처리가 필요한지 확인한다. 토픽 전체의 순서를 보장하는 것은 아니다. |
| RabbitMQ      | 브로커가 소비자에게 메시지를 전달하는 푸시 모델을 지원한다. 전달 확인과 다양한 라우팅·연동 방식을 제공한다. | 큐의 저장 방식, 전달 확인, AMQP·STOMP 같은 연동 요구를 살핀다.                                      |
| Redis Pub/Sub | 메모리 기반으로 동작하며 구조가 단순하다. 기본 Pub/Sub은 메시지를 영구 보관하지 않는다.                     | 구독자가 없거나 메시지를 받지 못했을 때 유실을 허용할 수 있는지 확인한다.                           |

처리량 수치만으로 기술을 고르기보다는 재처리, 유실 허용 여부, 순서 보장이 필요한 범위를 먼저 정한다. 운영하는 조직이 해당 기술을 유지보수할 수 있는지도 고려한다.

> **보충 내용 · 저장과 순서 보장의 범위**
>
> Kafka가 파일에 저장한다는 이유만으로 모든 장애에서 유실을 막는 것은 아니다. 복제와 `acks`, `min.insync.replicas` 같은 설정도 함께 봐야 한다. RabbitMQ도 큐에서 꺼내는 순서와 여러 소비자가 처리를 끝내는 순서를 구분해야 하며, 재전달이나 우선순위가 실제 전달 순서에 영향을 줄 수 있다. ([Kafka 설계 문서](https://kafka.apache.org/41/design/design/), [RabbitMQ 큐 문서](https://www.rabbitmq.com/docs/queues#message-ordering))

## 생산자: 메시지 유실과 DB 변경을 함께 살핀다

메시지를 보내는 과정에서는 타임아웃이나 네트워크 오류가 발생할 수 있다. 전송 실패를 어떻게 다룰지는 메시지의 용도에 따라 달라진다.

| 처리 방식      | 고려할 점                                                           |
| -------------- | ------------------------------------------------------------------- |
| 무시           | 유실을 허용할 수 있는 메시지인지 판단한다.                          |
| 재시도         | 일시적인 오류를 해결할 수 있지만 같은 메시지가 중복 전송될 수 있다. |
| 실패 로그 기록 | 나중에 다시 처리할 수 있도록 메시지 데이터와 실패 원인을 남긴다.    |

생산자가 타임아웃을 겪었다고 해서 브로커가 메시지를 받지 못했다고 단정할 수는 없다. 브로커가 메시지를 받았지만 응답이 생산자에게 도착하지 않았을 수도 있다. 이때 재전송하면 같은 메시지가 두 번 전달된다. 재시도할 때도 유지되는 고유한 메시지 ID가 중복을 판단하는 데 도움이 된다.

### DB 커밋 전에 보내면 생기는 문제

주문 정보를 DB에 저장하는 트랜잭션 안에서 주문 완료 메시지를 보냈다고 해 보자. 메시지를 전송한 뒤 다른 DB 작업이 실패하면 주문은 롤백되지만, 알림 서비스는 이미 받은 메시지로 주문 완료 푸시를 보낼 수 있다.

사용자는 주문 실패 화면을 봤는데 주문 완료 알림을 받게 된다. 이런 불일치를 피하려면 DB 트랜잭션이 커밋된 뒤 메시지를 보내야 한다.

다만 커밋 후 전송만으로 메시지 유실까지 해결되지는 않는다. DB 변경을 완료하는 일과 메시지 전송을 완료하는 일은 여전히 별개다. 이 문제는 뒤에서 살펴볼 트랜잭션 아웃박스 패턴으로 대응할 수 있다.

## 소비자: 중복 처리와 지연에 대응한다

소비자가 같은 작업을 두 번 처리하는 경로는 크게 두 가지다.

- 생산자가 같은 메시지를 두 번 이상 전송한다.
- 소비자가 처리 중 오류를 겪어 메시지를 다시 수신한다.

### 고유 ID로 이미 처리한 메시지 확인하기

첫 번째 경우에는 메시지의 고유 ID로 처리 이력을 확인할 수 있다. 이미 처리한 ID라면 다시 실행하지 않고 넘어간다. 생산자도 같은 메시지를 재전송할 때 ID를 바꾸지 않아야 한다.

처리한 ID는 DB 테이블이나 메모리의 집합으로 관리할 수 있다. 메모리에 저장한다면 계속 쌓이지 않도록 보관 범위도 제한해야 한다.

### 외부 API의 중복 실행은 멱등성으로 다룬다

소비자가 포인트 지급 API를 호출한 뒤 읽기 타임아웃을 겪었다고 해 보자. 소비자는 실패로 판단했지만 포인트 서비스에서는 지급이 끝났을 수 있다. 메시지를 다시 받아 API를 호출하면 포인트가 두 번 지급될 수 있다.

이 경우에는 메시지 처리 이력만 확인하는 것으로 충분하지 않을 수 있다. 외부 API가 같은 요청을 여러 번 받아도 지급 결과가 바뀌지 않도록 멱등성을 갖춰야 한다.

소비 속도도 함께 확인한다. 메시지는 정상적으로 전달되고 있어도 대기가 길어지면 사용자는 포인트가 지급되지 않았거나 검색에 반영되지 않았다고 느낄 수 있다.

## 이벤트와 커맨드를 구분한다

메시지는 크게 이벤트와 커맨드로 나눌 수 있다. 둘은 메시지가 담는 의미가 다르다.

| 구분   | 의미                         | 예                                                        |
| ------ | ---------------------------- | --------------------------------------------------------- |
| 이벤트 | 이미 발생한 사실을 알린다.   | 주문이 생성됨, 로그인이 실패함, 배송이 완료됨             |
| 커맨드 | 특정 작업의 실행을 요청한다. | 포인트 지급하기, 로그인 차단하기, 배송 완료 문자 발송하기 |

커맨드는 수행할 기능과 수신 대상이 정해져 있다. 포인트 지급 요청을 받은 포인트 서비스는 지급 작업을 실행한다.

이벤트는 발생한 사실을 전달하고, 그 사실에 어떻게 반응할지는 소비자가 정한다. 배송 완료 이벤트를 알림 서비스는 문자 발송에 사용하고, 주문 서비스는 주문 상태 변경에 사용할 수 있다. 새로 만드는 분석 서비스도 같은 이벤트를 받아 배송 완료 시점을 기록할 수 있다.

![배송 완료 이벤트와 여러 소비자. 배송 서비스가 배송 완료 사실을 발행하면 메시징 시스템이 알림 서비스와 주문 서비스에 전달한다. 알림 서비스는 문자를 발송하고 주문 서비스는 주문 상태를 변경한다. 이벤트에 어떻게 반응할지는 각 소비자가 정한다.](/static/images/books/junior-backend-practical-knowledge/async-event-consumers-v3.png)

### 시스템 간 상태 차이를 허용할 수 있는가

배송 서비스가 배송 완료로 바뀌어도 메시지가 주문 서비스에 반영되기 전에는 주문 쪽 상태가 배송 중일 수 있다. 비동기 연동에서는 이런 일시적인 불일치가 발생한다.

궁극적 일관성은 즉시 같은 상태를 갖는 대신 변경이 전달되고 반영된 뒤 일관성이 맞춰지는 특성이다. 해당 기능이 이런 시차를 허용할 수 있는지 확인해야 한다.

## 트랜잭션 아웃박스 패턴

DB 변경은 성공했는데 메시지를 보내지 못하는 문제에 대응하려면, 보낼 메시지 자체를 DB에 저장해 둘 수 있다. 트랜잭션 아웃박스 패턴은 업무 데이터 변경과 메시지 저장을 하나의 DB 트랜잭션으로 묶는다.

1. 주문 생성 등 업무 데이터를 변경한다.
2. 보낼 메시지를 아웃박스 테이블에 저장한다.
3. 두 작업을 함께 커밋한다.
4. 별도 중계 프로세스가 미발송 메시지를 조회해 브로커에 보낸다.
5. 전송에 성공하면 발송 완료로 표시한다.

![트랜잭션 아웃박스의 시퀀스 다이어그램. 업무 서비스가 하나의 DB 트랜잭션에서 업무 데이터를 변경하고 아웃박스에 메시지를 저장한 뒤 커밋한다. 커밋 후 메시지 중계가 DB에서 미발송 메시지를 조회해 메시징 시스템에 전송한다. 전송 성공을 확인한 중계가 DB에 발송 완료를 표시하며, 조회부터 완료 표시까지 주기적으로 반복한다.](/static/images/books/junior-backend-practical-knowledge/async-outbox-sequence.png)

트랜잭션이 롤백되면 업무 데이터와 메시지 데이터가 함께 롤백된다. 커밋한 메시지는 DB에 남아 있으므로 중계 프로세스가 나중에 전송할 수 있다.

아웃박스 테이블에는 다음과 같은 정보를 담을 수 있다.

| 정보                                    | 용도                                   |
| --------------------------------------- | -------------------------------------- |
| `id`, `messageId`                       | 저장 순서와 메시지 고유 식별자         |
| `messageType`, `payload`                | 메시지 종류와 전달할 데이터            |
| `status`                                | 발송 대기·완료·실패 상태               |
| `failCount`                             | 실패 횟수                              |
| `occurredAt`, `processedAt`, `failedAt` | 발생 시각, 처리 시각, 마지막 실패 시각 |

메시지 순서가 중요하다면 중간 메시지의 전송에 실패했을 때 발송을 멈추는 방법을 사용할 수 있다. 뒤의 메시지를 먼저 보내지 않고 실패한 메시지부터 다시 시도하는 식이다.

일시적인 오류일 수 있으므로 한 번 실패했다고 바로 최종 실패로 바꾸지는 않는다. 재시도 횟수나 운영 기준에 따라 실패 상태로 전환하고, 실패한 메시지는 별도로 확인해 후속 조치한다. 그대로 방치하면 시스템 간 데이터가 계속 어긋날 수 있다.

> **보충 내용 · 아웃박스에서도 중복 전송은 가능하다**
>
> 브로커에 전송한 직후, DB에 발송 완료를 기록하기 전에 중계 프로세스가 종료될 수 있다. 다시 실행하면 같은 메시지를 재전송할 수 있으므로 아웃박스를 사용해도 소비자의 중복 처리 대응은 필요하다. ([트랜잭션 아웃박스 패턴 원문](https://microservices.io/patterns/data/transactional-outbox.html))

## 배치 전송: 일정 간격으로 모아서 보낸다

연동 결과가 바로 필요하지 않다면 데이터를 모아 주기적으로 보내는 배치 방식도 사용할 수 있다. 전날 매출을 다음 날 전달하거나 배송 요청을 한 시간 간격으로 보내는 식이다.

파일을 이용한다면 보낼 데이터를 DB에서 조회하고, 합의한 형식의 파일로 만든 뒤 상대 시스템에 전송한다. 파일 대신 API로 데이터를 일괄 전송하거나, 읽기 전용 DB 접근으로 연동하는 방식도 있다.

### 파일 전송의 운영 규칙

파일 형식 외에도 누가 업로드하거나 다운로드할지, 언제까지 전달할지, 어떤 경로와 이름을 사용할지 정해야 한다. 소비자가 업무를 시작할 때 데이터가 필요한데 생산자가 그 이후에 전달하면 형식이 맞아도 연동은 실패한다.

소비자는 파일이 있는지 확인하고 데이터를 반영한 뒤 처리한 파일을 다른 폴더로 옮길 수 있다. 처리한 파일을 구분하면 같은 파일을 다시 처리하는 일을 줄이고, 보관한 파일로 재처리할 수도 있다.

자동 재시도와 수동 재실행 방법도 준비한다. 파일 생성이나 전송에 일시적인 오류가 날 수 있고, 자동 재시도 시간이 지난 뒤에야 파일이 도착할 수도 있기 때문이다.

책에는 보낼 데이터가 없는 날에도 빈 파일을 전달하도록 바꾼 사례가 나온다. 생산자는 데이터가 없어서 파일을 만들지 않았지만, 소비자는 파일이 오지 않은 이유를 알 수 없었다. 정상적으로 보낼 데이터가 없는 상태와 전송 실패를 구분할 규칙이 필요하다.

## CDC: DB 변경을 감지해 전달한다

CDC(Change Data Capture)는 DB의 데이터 변경을 추적해 다른 시스템으로 전달하는 방식이다. DB 변경 내역을 CDC 처리기가 받아 그대로 전달하거나 필요한 데이터로 변환한다.

회원 테이블의 이름 변경을 다른 DB에 동일하게 반영할 수도 있고, 주문 데이터에서 주문 ID와 상태만 추려 통지 시스템에 전달할 수도 있다. 중간에 메시징 시스템을 두면 여러 소비자에게 변경 데이터를 보낼 수 있다.

### 처리한 위치를 기록한다

CDC 처리기는 어디까지 읽고 처리했는지 기록해야 한다. MySQL에서는 바이너리 로그와 로그 위치를 이용할 수 있다. 처리 위치를 남기면 재시작 후 이어서 읽을 수 있다. 반대로 재시작 시점의 최신 로그부터 읽으면 중단된 동안의 변경을 놓칠 수 있다.

기존 시스템에 연동 코드를 추가하기 어려울 때도 CDC를 고려할 수 있다. 책에서는 신규 주문 시스템의 코드를 수정하는 부담을 줄이기 위해 DB 변경을 CDC로 읽고, Kafka를 거쳐 구주문 시스템과 콘텐츠 서비스에 전달한 사례를 소개한다.

### DB 변경만으로 업무 의미가 드러나는 것은 아니다

CDC로 암호 칼럼이 바뀌었다는 사실은 알 수 있다. 하지만 그 변경이 사용자의 직접 변경인지, 관리자의 초기화인지는 변경 데이터만으로 분명하지 않을 수 있다.

CDC로 전달하는 데이터 변경과 업무 이벤트는 구분해야 한다. 어떤 데이터를 바꿨는지와 어떤 일이 일어났는지는 항상 같은 설명이 아니다. 연동 대상이 필요한 의미를 변경 데이터에서 알 수 있는지 확인해야 한다.

## 적용 전에 정할 것

현재 요청이 연동 결과를 바로 필요로 하는지부터 판단한다. 비동기로 옮겨도 되는 작업이라면 허용할 수 있는 지연과 실패 처리 방법을 정하고, 그 조건에 맞춰 스레드·메시징·배치·CDC를 선택한다.
