요청을 더 많이 보냈는데 처리량은 늘지 않고 응답만 느려질 수 있다. 에러 응답까지 늘었다면, 초당 처리 건수 하나만 보고 성능이 좋다고 판단하기 어렵다.

성능 테스트는 정해진 부하에서 시스템의 응답 시간, 처리량, 안정성과 자원 사용량을 측정하는 작업이다. 서버가 감당할 수 있는 트래픽을 확인하고, 목표에 못 미치면 어디서 막히는지 찾아 개선한다. 도구를 실행하기 전에 **어떤 상황을 재현하고 무엇을 통과 기준으로 삼을지**부터 정해야 한다.

## 확인하려는 상황에 따라 테스트가 달라진다

| 종류                    | 확인하려는 것                                          | 부하를 주는 방식                      |
| ----------------------- | ------------------------------------------------------ | ------------------------------------- |
| 부하 테스트(load)       | 예상 트래픽에서 응답 시간과 처리량이 목표를 만족하는가 | 실제로 예상하는 수준의 부하를 준다.   |
| 스트레스 테스트(stress) | 예상 범위를 넘어섰을 때 어디까지 견디는가              | 부하를 높이며 시스템의 한계를 찾는다. |
| 지속 부하 테스트(soak)  | 오랫동안 요청을 처리해도 성능이 유지되는가             | 일정 수준의 부하를 장시간 유지한다.   |
| 스파이크 테스트(spike)  | 요청이 갑자기 몰리면 어떻게 반응하는가                 | 짧은 시간에 부하를 급격히 바꾼다.     |

평소 트래픽을 처리하는 능력과 이벤트 시작 직후 몰리는 요청을 견디는 능력은 다른 문제다. 짧은 테스트에서 괜찮아도 오래 실행하면 메모리 누수 때문에 성능이 떨어질 수 있다. 확인하려는 문제에 맞춰 부하의 크기뿐 아니라 증가 속도와 유지 시간도 바꿔야 한다.

## 부하를 늘려 포화점을 찾는다

낮은 부하에서 시작해 동시 사용자를 단계적으로 늘리면, 초기에는 처리량도 함께 증가한다. 하지만 어느 순간부터 부하를 더 주어도 처리량이 거의 늘지 않는다. 더 밀어붙이면 응답 시간이 길어지고 처리량이 오히려 떨어질 수 있다.

성능이 꺾이기 전의 한계 지점을 **포화점(saturation point)**이라고 한다. 포화점을 지나 성능이 저하되는 구간이 **버클존(buckle zone)**이다.

![부하 증가와 처리량의 변화. 부하가 늘면 처리량도 증가하지만 포화점 부근에서 증가 폭이 작아지고, 버클존에서는 부하를 더 주어도 처리량이 떨어질 수 있다. 실측값이 아닌 개념도다.](/static/images/books/junior-backend-practical-knowledge/appendix-a/load-types.svg)

포화점에서 목표한 성능을 충분히 넘겼다면 그 조건의 테스트를 마칠 수 있다. 목표보다 먼저 한계가 왔다면 병목을 찾아야 한다. 자주 호출되면서 응답도 느린 기능부터 살펴보면 범위를 좁히기 쉽다.

- DB 쿼리 실행 시간이 길지 않은가?
- 외부 서비스의 응답을 오래 기다리고 있지 않은가?
- 트래픽에 비해 커넥션 풀이 작아 연결을 기다리고 있지 않은가?

병목에 맞춰 쿼리를 개선하거나 서버를 확장하고, 캐시나 비동기 연동을 적용한 뒤 다시 측정한다. 응답 시간이 줄어들면 같은 자원으로 처리할 수 있는 요청이 늘어 포화점도 높아질 수 있다.

## 처리량과 응답 시간, 에러를 함께 본다

### 응답 시간은 평균 하나로 설명하기 어렵다

응답 시간은 평균, 최소, 최대, 중앙값과 95·99백분위 값을 함께 확인한다. 평균과 최대의 차이가 크다면 일부 요청만 유난히 느린 것인지, 많은 요청이 느려진 것인지 구분해야 한다.

예를 들어 최대 응답 시간은 크게 늘었는데 95·99백분위 값이 평균 근처에 있다면, 느린 요청이 소수에 집중됐을 가능성이 있다. 그렇다고 그 요청을 바로 무시해도 된다는 뜻은 아니다. 어떤 API와 실행 조건에서 늦어졌는지 확인할 단서로 삼는다.

중앙값과 평균의 차이도 본다. 둘의 차이가 크면 응답 시간의 분포가 한쪽으로 치우쳤을 수 있으므로 평균만으로 사용자가 겪는 지연을 설명하기 어렵다.

### 처리량은 테스트 구간에 따라 달라진다

처리량은 단위 시간에 처리한 작업 수다. 초당 트랜잭션 수인 TPS 같은 단위를 사용한다. 테스트하는 동안 부하가 바뀌면 처리량도 달라지므로 최대치뿐 아니라 평균과 최소치도 확인한다.

잠깐 높은 처리량을 기록한 것과 그 수준을 안정적으로 유지한 것은 구분해야 한다. 어느 부하 단계에서 어떤 응답 시간과 에러율을 보였는지 함께 기록한다.

### 에러가 늘면 처리량만으로 판단하지 않는다

에러율은 전체 요청 중 에러가 발생한 요청의 비율이다. 처리량이 높게 나오더라도 에러가 함께 늘었다면 시스템이 부하를 감당하지 못하고 있을 수 있다. 에러가 늘기 시작한 지점은 한계를 찾는 데 중요한 단서가 된다.

### CPU 사용률로 원인 분석의 범위를 좁힌다

부하를 주는 동안 테스트 대상 시스템의 CPU 사용률도 모니터링한다. DB나 외부 연동이 느린 경우가 많지만 CPU가 바빠서 처리하지 못하는 경우도 있다. 응답 시간과 처리량만 모으면 이런 차이를 알아보기 어렵다.

메모리 사용량도 함께 측정한다. 특히 지속 부하 테스트에서는 시간이 지날수록 사용량이 계속 늘거나 성능이 떨어지는지 살펴볼 수 있다.

## 실제 트래픽에 맞춰 테스트를 설계한다

### 먼저 목표와 트래픽 패턴을 정한다

무조건 높은 TPS를 목표로 잡으면 실제 운영과 관계없는 숫자를 쫓기 쉽다. 예상 사용자 수와 사용자가 요청을 보내는 빈도로 목표 부하를 잡는다. 내부 직원 수십 명이 쓰는 시스템과 대규모 온라인 서비스는 필요한 부하부터 다르다.

부하를 높이는 방식도 서비스에 맞춘다. 업무 시간 동안 비교적 고르게 쓰는 서비스인지, 특정 시각에 사용자가 몰리는 서비스인지 살핀다. 짧은 시간에 요청이 늘어나는 서비스라면 테스트도 빠르게 부하를 높여야 한다. 정해진 시각에 많은 요청이 한꺼번에 발생하는 업무라면 그 상황을 재현한다.

### 동시 사용자 수와 사용자 데이터를 함께 준비한다

동시 사용자 수만 늘리고 모든 요청에 같은 인증 토큰을 쓰면 실제보다 좋은 결과가 나올 수 있다. 같은 사용자의 데이터를 반복 조회하면서 DB나 캐시가 유리한 상태가 될 수 있기 때문이다.

사용자마다 조회하는 데이터가 다르다면 테스트에서도 여러 사용자가 각자의 데이터에 접근하도록 만든다. 부하 규모가 커지면 한 대의 부하 발생기로 충분한지도 확인하고, 필요하면 여러 장비로 나눈다.

### 기능별 요청 비율을 맞춘다

실제 서비스에서는 여러 API가 서로 다른 비율로 호출된다. 자주 쓰는 기능을 추리고 운영에서 호출되는 비율에 가깝게 요청을 섞는다.

한 API만 반복 호출하면 캐시 효과 등으로 성능이 과장될 수 있다. 개별 API의 성능을 측정할 때와 전체 서비스의 처리 능력을 확인할 때는 테스트 구성을 다르게 잡는다.

### 데이터 크기를 예상 규모에 맞춘다

운영에서 수백만 건을 저장할 예정인데 테스트 DB에는 몇만 건만 넣으면, 실제 데이터가 쌓였을 때의 성능을 확인하기 어렵다. 반대로 데이터가 거의 늘지 않는 기능에 불필요하게 많은 데이터를 넣으면 실제와 동떨어진 조건을 시험하게 된다.

데이터는 예상되는 규모에 맞춰 준비한다. 사용자 수뿐 아니라 DB에 쌓인 데이터의 양도 테스트 조건이다.

### 워밍업이 필요한 상태인지 확인한다

캐시가 비어 있는 첫 요청과 자주 조회하는 데이터가 채워진 뒤의 요청은 성능이 다를 수 있다. 캐시가 채워진 평상시 성능을 확인하려는 테스트라면 먼저 데이터를 어느 정도 채워 둔다.

부하를 조금씩 늘리면서 시스템을 안정화한 뒤 본격적으로 측정할 수도 있다. 반대로 빈 캐시에서 시작하는 상황을 확인하려는 목적이라면 그 상태에서 시작했다는 조건을 기록한다. **워밍업을 할지 여부도 확인하려는 상황에 달려 있다.**

## 성능 테스트 도구는 환경에 맞춰 고른다

| 도구                                                             | 작성·실행 방식과 특징                                                                                                   |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| [nGrinder](https://naver.github.io/ngrinder/)                    | Groovy·Jython으로 시나리오를 작성한다. 웹 UI를 제공하는 컨트롤러가 테스트를 관리하고 여러 에이전트가 부하를 발생시킨다. |
| [k6](https://grafana.com/docs/k6/latest/get-started/running-k6/) | JavaScript로 시나리오를 작성하고 CLI로 실행한다. CI/CD에 연결하기 쉽다.                                                 |
| [Locust](https://docs.locust.io/en/stable/what-is-locust.html)   | Python으로 테스트를 작성하고 웹 UI나 명령행에서 실행한다. 여러 장비에서 부하를 발생시킬 수 있다.                        |
| [Gatling](https://docs.gatling.io/)                              | 코드로 시나리오를 작성한다. JVM 환경에 익숙한 팀에서 검토할 수 있는 도구다.                                             |
| [JMeter](https://jmeter.apache.org/)                             | GUI와 CLI를 제공하며 HTTP 외에 DB·FTP·TCP 등 다양한 대상을 테스트할 수 있다.                                            |

nGrinder는 컨트롤러가 시나리오와 실행을 관리하고 에이전트가 요청을 보내는 구조다. 에이전트를 여러 장비에 배치해 큰 부하를 만들 수 있다.

k6는 콘솔에서 결과를 확인하고 외부 저장소나 모니터링 도구와 연결해 지표를 살펴볼 수 있다. 도구를 고를 때는 익숙한 언어, 실행 환경, 필요한 부하 규모와 결과 확인 방법을 함께 본다.

## 부하기가 측정 결과를 왜곡하지 않게 한다

### 테스트 대상과 부하기를 분리한다

부하를 발생시키는 프로그램도 CPU와 메모리를 사용한다. 같은 장비에서 서버와 부하기를 실행하면 자원을 나눠 쓰므로, 서버가 실제로 낼 수 있는 성능보다 낮게 측정될 수 있다.

테스트 대상과 부하기를 별도 장비로 나누고, 부하기의 성능도 확인한다. 부하기가 요청을 충분히 만들지 못하면 서버의 한계를 확인한 것이 아니라 부하기의 한계만 본 셈이다.

![성능 테스트 환경의 분리. 독립된 부하기가 테스트 대상 시스템으로 요청을 보내고, 외부 연동은 테스트용 대역으로 연결한다. 부하기와 대상 시스템의 지표를 함께 수집한다.](/static/images/books/junior-backend-practical-knowledge/appendix-a/test-topology.svg)

### 요청 제한과 풀 크기를 미리 확인한다

IP별 요청 제한이 걸려 있으면 부하기 한 대에서 보내는 요청이 제한에 걸릴 수 있다. 서버 스레드 풀이나 DB 커넥션 풀이 테스트하려는 부하에 비해 작은 경우에도 원하는 조건의 테스트가 어려워진다.

어떤 제한을 포함해 측정할지 정하고 설정을 확인한다. 처리 용량을 확인하려고 제한을 조정했다면 그 설정도 결과와 함께 남겨야 한다. 풀 크기를 크게 바꾸는 것만으로 병목 자체가 해결되는 것은 아니므로, 대기와 에러가 발생한 위치를 살핀다.

### 운영 네트워크와 외부 서비스에 영향을 주지 않게 한다

테스트 서버만 따로 두어도 운영 시스템과 같은 네트워크를 사용하면 대량 트래픽이 운영에 영향을 줄 수 있다. 네트워크가 포화되면 실제 서비스까지 느려지거나 멈출 수 있으므로 테스트 트래픽이 지나가는 경로도 확인한다.

외부 서비스 연동도 살핀다. 우리 시스템에 부하를 주는 과정에서 실제 외부 서비스에 대량 요청이 전달되면 그쪽에 장애를 일으킬 수 있다. 이런 연동은 테스트용 대역으로 교체한 뒤 진행한다.

### 운영 환경과 다른 조건을 기록한다

운영은 CPU 8코어와 메모리 16GB를 쓰는데 테스트는 2코어와 2GB를 쓴다면 운영에서의 성능을 그대로 확인하기 어렵다. 유효한 성능 지표를 얻으려면 가능한 한 운영과 비슷한 환경을 구성한다.

환경 차이가 있다면 서버 사양, 구성과 설정을 결과에 함께 남긴다. 숫자만 옮겨 놓으면 어떤 조건에서 얻은 결과인지 알 수 없다.

## 측정하고 고치는 과정을 반복한다

성능 테스트 한 번으로 작업이 끝나지는 않는다. 부하를 올리는 동안 지표를 관찰하고, 목표에 못 미치면 병목을 찾아 수정한 뒤 다시 실행한다.

![성능 개선의 반복 과정. 목표와 부하 조건을 정하고 테스트를 실행한 뒤 지표와 병목을 분석한다. 개선한 시스템을 같은 조건에서 다시 측정해 목표 달성 여부를 확인한다.](/static/images/books/junior-backend-practical-knowledge/appendix-a/iteration.svg)

테스트 실행 시간뿐 아니라 결과 분석, 코드 수정과 재실행에 쓸 시간도 확보해야 한다. 목표한 처리량이 나왔는지와 함께 응답 시간과 에러율이 허용 범위인지 확인해야 개선 여부를 판단할 수 있다.

## 보충

### p95와 p99를 통과 기준으로 표현하기

p95는 측정한 응답 시간 중 95%가 그 값 이하라는 뜻이다. p95가 400ms라면 나머지 약 5%는 더 느릴 수 있다. p99도 같은 방식으로 상위의 느린 요청을 살피는 데 사용한다.

“평균 응답 시간이 빠르다”보다 “정해진 부하에서 p95가 400ms 미만이고 HTTP 실패율은 1% 미만이다”처럼 조건을 구체적으로 잡으면 반복 실행 결과를 비교하기 쉽다. 다만 400ms와 1%는 설명을 위한 값이다. 실제 기준은 서비스 요구에 맞춰 정한다. [k6 Thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/)

다음은 워밍업을 마친 테스트 환경에서 인증 없는 상품 목록 API를 확인하는 최소 예제다. `catalog-load.js`로 저장하고 테스트 서버 주소를 전달해 실행한다.

```javascript
import http from 'k6/http'
import { sleep } from 'k6'

const baseUrl = __ENV.TEST_BASE_URL
if (!baseUrl) {
  throw new Error('TEST_BASE_URL을 지정해야 한다.')
}

export const options = {
  vus: 10,
  duration: '1m',
  thresholds: {
    http_req_duration: ['p(95)<400'],
    http_req_failed: ['rate<0.01'],
  },
}

export default function () {
  http.get(`${baseUrl}/api/products`)
  sleep(1)
}
```

```bash
k6 run -e TEST_BASE_URL=http://api.example.test:8080 catalog-load.js
```

`api.example.test`는 예시 주소이므로 별도 장비에 구성한 테스트 서버 주소로 바꾼다. 가상 사용자 10명이 응답을 받은 뒤 1초 쉬고 다시 요청한다. 동시 사용자 수가 10명이라는 설정이 초당 요청 10건을 보장하지는 않는다. 실제 요청 빈도는 응답 시간과 대기 시간의 영향을 받는다. [k6 실행과 가상 사용자](https://grafana.com/docs/k6/latest/get-started/running-k6/)

`http_req_duration`은 요청 전송·응답 대기·응답 수신 시간을 합한 값이며 최초 DNS 조회나 연결 수립 시간은 포함하지 않는다. `http_req_failed`는 k6가 실패로 분류한 HTTP 요청의 비율이다. 응답 본문의 업무 결과까지 확인하려면 API에 맞는 검증을 추가해야 한다. 사용자별 데이터와 기능별 요청 비율도 실제 시나리오에 맞춰 확장한다. [k6 기본 지표](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/)
