로그인한 뒤 예약 번호만 바꿨는데 다른 사람의 예약 내역이 보인다면 어떨까? 로그인 여부는 확인했지만, 그 예약을 볼 수 있는 사람인지는 검사하지 않은 것이다. 사용자 정보를 돌려주는 API나 비밀번호를 바꾸는 API에서 이런 확인이 빠지면 작은 구현 실수가 큰 피해로 이어질 수 있다.

서버 개발자가 살펴야 할 보안은 요청 처리 코드에만 있지 않다. 인증 정보를 어디에 보관할지, 유출된 데이터로 무엇을 할 수 있는지, 어떤 네트워크 연결을 허용할지, 문제가 생겼을 때 무엇을 추적할 수 있는지도 함께 봐야 한다.

## 인증과 인가는 서로 다른 확인이다

<strong>인증(authentication)</strong>은 요청한 사용자가 누구인지 확인하는 과정이다. 아이디와 비밀번호를 확인하는 로그인, 2단계 인증, 생체 정보를 사용하는 인증 등이 여기에 해당한다.

<strong>인가(authorization)</strong>는 그 사용자가 요청한 기능을 실행하거나 자원에 접근할 수 있는지 확인하는 과정이다. 로그인에 성공한 사용자라도 다른 사람의 예약을 조회하거나 관리자 기능을 실행할 권한까지 생기는 것은 아니다.

특히 API가 전달받은 사용자 ID를 그대로 믿으면 문제가 생기기 쉽다. 내 정보를 조회하는 기능은 요청 파라미터의 사용자 ID 대신 **검증한 토큰이나 세션에서 얻은 사용자 식별자**를 기준으로 처리해야 한다. 예약 ID처럼 대상을 지정하는 값은 요청에서 받더라도, 그 대상에 대한 접근 권한은 별도로 검사한다.

비밀번호 변경처럼 민감한 기능은 로그인 여부뿐 아니라 변경 대상이 본인인지, 현재 비밀번호 확인 같은 추가 검증이 필요한지도 살핀다. API 주소와 사용자 ID를 아는 것만으로 다른 사람의 비밀번호를 바꿀 수 있어서는 안 된다.

## 토큰으로 인증 상태를 이어 간다

로그인에 성공하면 서버는 클라이언트에 토큰을 발급할 수 있다. 이후 클라이언트는 요청과 함께 토큰을 보내고, 서버는 이를 검증해 사용자를 식별한다. 매번 아이디와 비밀번호를 전송하지 않아도 인증 상태를 이어 갈 수 있다.

토큰으로 사용자를 알아내는 방식은 크게 두 가지다.

| 방식                      | 사용자 식별 정보를 두는 곳                                      | 요청을 받을 때 하는 일                         |
| ------------------------- | --------------------------------------------------------------- | ---------------------------------------------- |
| 임의의 토큰과 별도 저장소 | DB, Redis, 서버 세션 등에 토큰과 사용자의 대응 관계를 저장한다. | 토큰으로 저장소를 조회한다.                    |
| 사용자 정보를 담은 토큰   | JWT 같은 토큰 안에 사용자 식별 정보 등을 담는다.                | 토큰의 유효성을 검증하고 필요한 정보를 읽는다. |

![토큰과 사용자 정보의 연결 방식. 임의의 토큰은 서버가 공유 저장소에서 사용자 매핑을 조회한다. 서명된 JWT는 서버가 검증한 뒤 사용자 식별자를 읽는다.](/static/images/books/junior-backend-practical-knowledge/ch08/token-storage.svg)

### 별도 저장소를 사용하는 토큰

서버는 예측하기 어려운 고유 토큰을 만들고, 토큰과 사용자 식별자를 함께 저장한다. 생성 시간, 최근 사용 시간, 만료 시간, 클라이언트 정보도 필요에 따라 보관한다.

요청을 받으면 저장된 정보를 찾아 토큰이 유효한지 확인한다. 다음은 이런 흐름을 보여 주는 예제다.

```java
public long authenticatedAccountId(String rawToken) {
    LoginSession session = sessions.find(rawToken)
        .orElseThrow(AuthenticationRequiredException::new);

    if (!session.isValidAt(clock.instant())) {
        throw new AuthenticationRequiredException();
    }
    return session.accountId();
}
```

`sessions`는 토큰으로 로그인 정보를 조회하는 저장소다. `isValidAt()`은 만료나 무효화 여부를 검사한다고 가정한다. 저장소와 예외 클래스의 구현, 최근 사용 시각 갱신은 생략했다.

서블릿의 `HttpSession`도 서버가 세션 ID에 연결된 정보를 관리하는 방식이다. 다만 서버 한 대의 메모리에만 세션을 저장하면 다음 문제가 생긴다.

- 요청이 다른 서버로 가면 그 서버에는 해당 세션이 없을 수 있다.
- 서버를 재시작하면 메모리에 있던 세션이 사라진다.
- 보관할 수 있는 세션 수가 메모리 크기의 영향을 받는다.

같은 사용자의 요청을 같은 서버로 보내는 <strong>고정 세션(sticky session)</strong>으로 첫 번째 문제를 완화할 수 있다. DB나 Redis 같은 공용 저장소에 세션을 두면 여러 서버가 같은 세션을 조회할 수 있다. Spring Session처럼 `HttpSession` 사용 방식은 유지하면서 저장 위치를 바꾸는 도구도 있다.

### 토큰 자체에 사용자 정보를 담는 방식

JWT에는 사용자 식별자와 만료 시각 같은 정보를 담을 수 있다. 서명된 JWT를 사용하는 서버는 서명을 포함한 유효성을 검증한 뒤 사용자 식별자를 읽는다.

사용자와 토큰의 대응 관계를 요청마다 별도 저장소에서 찾지 않아도 되므로 서버를 수평 확장하기 편하다. 대신 토큰에 정보가 많아지면 요청마다 전송하는 데이터가 늘고, 이미 발급한 토큰을 즉시 무효화하려면 추가 처리가 필요하다.

토큰을 클라이언트에서 지웠다고 이미 복사된 토큰까지 무효가 되는 것은 아니다. 즉시 차단이 필요하다면 별도의 무효화 정보나 사용자별 유효 시각을 관리하는 등의 설계가 필요하다. 어느 방식이든 토큰에는 필요한 정보만 담는다.

### 쿠키와 헤더로 토큰을 전달한다

웹 브라우저에서는 쿠키를 많이 사용한다. 서버가 쿠키를 설정하면 브라우저가 조건에 맞는 후속 요청에 쿠키를 함께 전송한다. 서블릿 세션의 세션 ID도 이런 방식으로 전달할 수 있다.

`Authorization` 같은 요청 헤더에 토큰을 넣는 방식도 있다. 이 경우 클라이언트가 API를 호출할 때 헤더를 구성한다. **토큰의 저장 방식과 전달 방식은 따로 결정할 수 있다.** JWT를 쿠키로 보낼 수도 있고, 임의의 토큰을 헤더로 보낼 수도 있다.

### 토큰은 만료와 무효화까지 설계한다

토큰을 탈취한 사람은 정상 사용자인 것처럼 요청할 수 있다. 서버뿐 아니라 토큰을 보관하는 클라이언트도 보호해야 하며, 토큰이 유효한 기간을 제한해야 한다.

| 만료 기준             | 동작                                                                                             |
| --------------------- | ------------------------------------------------------------------------------------------------ |
| 발급 시각 기준        | 오전 9시에 유효 기간 1시간으로 발급했다면 오전 10시에 만료된다.                                  |
| 마지막 접근 시각 기준 | 마지막 접근 뒤 일정 시간 동안 사용하지 않으면 만료된다. 접근할 때마다 만료 시각이 뒤로 미뤄진다. |

만료 시간을 짧게 잡으면 탈취한 토큰을 사용할 수 있는 기간도 짧아지지만 정상 사용자도 자주 다시 인증해야 한다. 관리자 기능처럼 민감한 정보를 다루는 경우에는 편의성과 노출 위험을 더 신중하게 비교한다.

짧게 유지하는 **액세스 토큰**과 더 길게 유지하는 **리프레시 토큰**을 함께 사용할 수도 있다. 액세스 토큰이 만료되면 리프레시 토큰으로 새 액세스 토큰을 발급해 재로그인 횟수를 줄이는 방식이다. 재발급 기능도 인증 기능이므로 리프레시 토큰의 보관과 만료, 무효화까지 함께 다뤄야 한다.

접속 IP를 토큰 발급 당시의 정보와 비교하는 방법도 있다. 다만 이를 얼마나 강하게 적용할지는 실제 접속 환경을 고려해야 한다. 토큰 탈취가 의심되면 강제로 로그아웃시키거나 토큰을 무효화할 수 있는 수단도 준비한다.

## 권한은 기능과 대상 자원에서 확인한다

관리자 사이트에서는 같은 로그인 사용자라도 담당 업무에 따라 사용할 수 있는 기능이 다르다. 예약 조회는 가능하지만 환불은 할 수 없는 운영자도 있을 수 있다.

이런 권한을 관리하는 대표적인 방식이 <strong>역할 기반 접근 제어(RBAC)</strong>다. 역할에 허용 기능을 묶어 두고 사용자에게 역할을 부여한다. 새 운영자가 들어왔을 때 권한을 하나씩 부여하는 대신 알맞은 역할을 지정할 수 있다.

| 방식            | 관리 방법                                          | 살펴볼 비용                                               |
| --------------- | -------------------------------------------------- | --------------------------------------------------------- |
| 역할 기반       | 예약 운영자, 상품 관리자처럼 역할에 권한을 묶는다. | 비슷한 역할이 늘거나 쓰지 않는 역할이 남지 않게 관리한다. |
| 사용자별 권한   | 사용자에게 필요한 기능을 개별적으로 허용한다.      | 사용자가 늘수록 개별 권한을 관리하기 어려워질 수 있다.    |
| 속성 기반(ABAC) | 사용자 속성과 접근 조건을 조합해 판단한다.         | 세밀하게 제어할 수 있지만 속성과 규칙 정의가 복잡해진다.  |

시스템에 따라 여러 방식을 함께 사용할 수 있다. 작은 관리 도구에 지나치게 복잡한 권한 체계를 만들기보다 필요한 통제 수준을 먼저 정한다.

![인증 이후의 권한 확인. 서버가 확인한 사용자를 기준으로 기능 실행 권한과 예약 자원에 대한 접근 권한을 검사한 뒤 업무를 처리한다.](/static/images/books/junior-backend-practical-knowledge/ch08/authorization.svg)

내 예약을 조회하는 서비스를 예로 들면, 요청의 예약 ID와 인증한 사용자 ID를 함께 사용한다.

```java
public ReservationSummary findMine(long reservationId, long authenticatedAccountId) {
    Reservation reservation = reservations.findById(reservationId)
        .orElseThrow(ReservationNotFoundException::new);

    if (reservation.accountId() != authenticatedAccountId) {
        throw new AccessDeniedException();
    }
    return ReservationSummary.from(reservation);
}
```

`authenticatedAccountId`는 인증 처리에서 확인한 값이며 클라이언트가 지정한 사용자 ID를 그대로 넘기지 않는다. 이 예제는 소유자만 조회할 수 있다는 정책을 가정한다. 운영자의 대리 조회나 조직별 공유가 필요하다면 그 정책을 별도로 구현한다.

운영 계정도 사람마다 따로 발급한다. 여러 사람이 같은 계정을 사용하면 누가 환불하거나 정보를 조회했는지 추적하기 어렵다. 권한 관리와 작업자 식별이 함께 가능해야 한다.

## 데이터는 복구 필요에 따라 보호 방식을 고른다

비밀번호를 평문으로 저장하면 DB를 조회할 수 있는 사람이나 DB를 탈취한 공격자가 바로 읽을 수 있다. 같은 비밀번호를 여러 서비스에서 사용했다면 피해가 다른 서비스로 이어질 수도 있다.

저장된 데이터를 보호할 때는 **원래 값을 다시 읽어야 하는지**를 먼저 구분한다.

| 방식          | 원래 값의 복구                          | 사용하는 곳                                             |
| ------------- | --------------------------------------- | ------------------------------------------------------- |
| 단방향 해시   | 해시에서 원문을 복호화하는 기능이 없다. | 비밀번호 검증처럼 원문을 보관할 필요가 없는 경우        |
| 양방향 암호화 | 알맞은 키로 복호화한다.                 | 다시 읽어야 하는 민감 정보, 보호가 필요한 데이터 송수신 |

### 해시는 바이트를 고정 길이 값으로 바꾼다

해시 함수는 입력을 해시 값으로 변환한다. 같은 입력에는 같은 결과가 나오며, 입력이 조금만 달라도 결과가 크게 달라진다. 서로 다른 입력에서 같은 결과가 나올 가능성을 피할 수는 없으므로, 같은 해시 값이 곧 수학적인 원문 동일성 증명은 아니다. 안전한 해시 함수는 이런 충돌이나 원문을 찾아내기 어렵게 설계된다.

문자열을 다룰 때도 실제 연산은 바이트를 대상으로 한다. 문자 인코딩을 정해 바이트 배열로 바꾸고, 결과 바이트는 16진수나 Base64로 표현할 수 있다.

```java
public static String sha256Hex(String text) throws NoSuchAlgorithmException {
    byte[] bytes = text.getBytes(StandardCharsets.UTF_8);
    byte[] digest = MessageDigest.getInstance("SHA-256").digest(bytes);
    return HexFormat.of().formatHex(digest);
}
```

Java 17 이상의 `HexFormat`을 사용해 바이트의 16진수 변환 코드를 줄였다. 이 코드는 해시와 인코딩의 원리를 보여 주는 예제이며 **비밀번호 저장용 구현이 아니다.** Base64와 16진수 표현 자체에도 데이터를 숨기는 기능은 없다.

비밀번호는 가입할 때 검증용 값을 저장하고 로그인할 때 입력한 값이 맞는지 확인한다. 원래 비밀번호를 다시 꺼내 비교할 필요는 없다. 저장한 비밀번호를 복호화해 알려 주는 대신, 비밀번호를 다시 설정하는 절차가 필요하다.

### 솔트로 같은 비밀번호의 저장 결과를 다르게 만든다

일반 해시는 같은 입력에 같은 결과를 만든다. 공격자가 자주 사용하는 비밀번호와 해시 값을 미리 계산해 두면 유출된 값과 대조할 수 있다. 이런 사전 계산 공격을 어렵게 만들기 위해 사용자마다 다른 임의의 <strong>솔트(salt)</strong>를 함께 사용한다.

![솔트를 사용한 비밀번호 검증. 같은 비밀번호라도 서로 다른 솔트를 적용하면 저장 값이 달라진다. 로그인할 때는 해당 사용자에게 저장한 솔트와 알고리즘 설정을 사용해 검증한다.](/static/images/books/junior-backend-practical-knowledge/ch08/hash-salt.svg)

검증할 때도 가입 당시와 같은 솔트가 필요하다. 따라서 솔트를 포함해 검증에 필요한 설정을 저장하고, 검증 라이브러리가 이를 읽어 입력 값을 확인하게 한다. 사용자 ID처럼 예측 가능한 값을 솔트로 쓰기보다 사용자마다 임의의 값을 생성한다. 실제 비밀번호 저장에 필요한 알고리즘 선택은 아래 `보충`에서 따로 다룬다.

### 대칭 키와 비대칭 키는 키를 사용하는 방식이 다르다

**대칭 키 암호화**는 암호화와 복호화에 같은 비밀 키를 사용한다. AES가 대표적이다. 데이터를 주고받는 양쪽이 같은 키를 알아야 하므로 키의 생성, 전달과 보관이 중요하다. 키가 노출되면 암호화된 데이터를 읽을 수 있다.

**비대칭 키 암호화**는 공개 키와 개인 키의 쌍을 사용한다. 수신자의 공개 키로 암호화한 데이터는 대응하는 개인 키로 복호화한다. 공개 키는 공유할 수 있지만 개인 키는 소유자만 접근할 수 있어야 한다. RSA는 이런 공개 키 암호 체계의 한 예다.

![대칭 키와 공개 키 암호화의 차이. 대칭 키 방식은 같은 비밀 키로 암호화하고 복호화한다. 공개 키 암호화는 수신자의 공개 키로 암호화하고 대응하는 개인 키로 복호화한다.](/static/images/books/junior-backend-practical-knowledge/ch08/encryption-keys.svg)

Java에서 AES 키를 생성하고 다시 불러오는 기본 흐름은 다음과 같다.

```java
KeyGenerator generator = KeyGenerator.getInstance("AES");
generator.init(256);
SecretKey encryptionKey = generator.generateKey();

byte[] encodedKey = encryptionKey.getEncoded();
SecretKey restoredKey = new SecretKeySpec(encodedKey, "AES");
```

AES는 128·192·256비트 키를 사용한다. 위 예제의 256비트 키는 32바이트다. 키를 문자열 형태로 보관해야 한다면 Base64로 표현할 수 있지만, 인코딩한 키도 여전히 비밀 정보다.

RSA 키는 `KeyPairGenerator`로 생성한다. 인코딩한 키를 다시 읽을 때는 키 형식에 맞는 명세가 필요하다.

```java
KeyPairGenerator generator = KeyPairGenerator.getInstance("RSA");
generator.initialize(2048);
KeyPair pair = generator.generateKeyPair();

KeyFactory factory = KeyFactory.getInstance("RSA");
PublicKey publicKey = factory.generatePublic(
    new X509EncodedKeySpec(pair.getPublic().getEncoded()));
PrivateKey privateKey = factory.generatePrivate(
    new PKCS8EncodedKeySpec(pair.getPrivate().getEncoded()));
```

이 코드는 키 생성과 형식 변환만 보여 준다. 키 보관소, 접근 제어와 키 교체 처리는 생략했다.

### 키뿐 아니라 모드와 IV도 확인한다

AES를 사용한다는 말만으로 암호화 구성이 완성되지는 않는다. 암호화 모드와 패딩 규칙도 정해야 한다. `AES/CBC/PKCS5Padding` 같은 문자열은 알고리즘, 모드, 패딩을 함께 나타낸다. 블록 크기에 맞게 입력을 채우는 것이 패딩이며, GCM처럼 패딩이 필요 없는 모드도 있다.

초기화 벡터인 **IV**는 같은 키로 데이터를 암호화할 때 반복되는 결과가 드러나지 않도록 사용하는 값이다. 복호화할 때도 필요하므로 암호문과 함께 보관하거나 전달할 수 있다. 다만 IV의 길이와 생성·재사용 규칙은 모드에 따라 다르다. 모든 AES 모드에 같은 IV 규칙을 적용해서는 안 된다.

암호화 코드에서는 문자열을 바이트로 바꾸는 인코딩과 `Cipher`의 변환 이름을 명시한다. 운영에 사용할 모드와 무결성 보호까지 고려한 예제는 `보충`에 정리했다.

## HMAC으로 메시지의 변조를 확인한다

외부 시스템에서 예약 확정 결과를 받아 정산에 반영한다고 해 보자. 전달받은 상태나 금액이 중간에 바뀌면 잘못된 처리가 일어날 수 있다. 메시지가 바뀌지 않았는지, 공유한 비밀 키를 아는 쪽에서 만든 메시지인지 확인하는 방법 중 하나가 **HMAC**이다.

HMAC은 해시 함수와 비밀 키를 사용해 메시지 인증 코드인 MAC을 만든다. 송신자는 메시지와 MAC을 함께 보내고, 수신자는 받은 메시지로 MAC을 다시 계산해 비교한다.

![HMAC을 이용한 메시지 검증. 송신자가 공유 비밀 키와 메시지로 MAC을 계산해 메시지와 함께 보낸다. 수신자는 같은 비밀 키와 받은 메시지로 MAC을 다시 계산해 두 값을 비교한다.](/static/images/books/junior-backend-practical-knowledge/ch08/hmac.svg)

```java
public static byte[] authenticateMessage(byte[] message, byte[] sharedSecret)
    throws GeneralSecurityException {
    Mac mac = Mac.getInstance("HmacSHA256");
    mac.init(new SecretKeySpec(sharedSecret, "HmacSHA256"));
    return mac.doFinal(message);
}

public static boolean verifyMessage(byte[] message, byte[] receivedMac,
    byte[] sharedSecret) throws GeneralSecurityException {
    byte[] expectedMac = authenticateMessage(message, sharedSecret);
    return MessageDigest.isEqual(expectedMac, receivedMac);
}
```

문자열 메시지라면 송신자와 수신자가 같은 인코딩을 사용해야 한다. 위 예제는 바이트 배열을 그대로 입력받으며 MAC을 전송할 때의 Base64 변환과 키 보관은 생략했다.

HMAC은 비교적 단순하고 효율적이지만 비밀 키를 양쪽이 공유해야 한다. 키가 유출되면 다른 사람도 유효한 MAC을 만들 수 있고, 키 교체 시 양쪽의 변경을 맞춰야 한다. 메시지 내용 자체를 감추는 암호화와도 역할이 다르다.

## 방화벽으로 필요한 트래픽만 허용한다

서버를 외부에 공개하면 서비스 요청 외에도 포트 스캔이나 공격 트래픽이 들어올 수 있다. 방화벽은 네트워크 접근 범위를 제한하는 기본 수단이다. 물리 장비, 클라우드의 가상 방화벽, 서버 OS의 방화벽 등 여러 형태로 적용할 수 있다.

- **인바운드:** 외부에서 내부로 들어오는 트래픽이다.
- **아웃바운드:** 내부에서 외부로 나가는 트래픽이다.

인바운드는 서비스에 필요한 포트와 허용할 접속 범위를 정하고 나머지는 차단한다. 공개 서비스의 HTTPS 연결은 허용하더라도 관리용 서버나 관리 포트는 사내망 등 필요한 범위에서만 접근하게 구성한다.

![네트워크 접근 범위를 제한하는 방화벽. 공개 서비스에 필요한 HTTPS 연결과 허용된 관리망의 접근만 허용한다. 외부로 나가는 연결도 필요한 목적지로 제한한다.](/static/images/books/junior-backend-practical-knowledge/ch08/network-boundary.svg)

아웃바운드도 무제한으로 열어 두면 침해된 서버가 다른 공격의 경유지로 쓰일 수 있다. 실제로 통신해야 하는 외부 시스템과 목적을 파악하고 필요한 범위로 줄인다.

웹 방화벽인 **WAF**는 HTTP 요청을 분석해 SQL 인젝션이나 XSS 같은 웹 공격을 탐지·차단하는 데 사용한다. WAF를 적용해도 애플리케이션 자체의 검증은 필요하다.

여러 출발지에서 대량의 트래픽을 보내 서비스를 느리게 하거나 중단시키는 **분산 서비스 거부(DDoS)** 공격도 있다. 네트워크 장비나 서비스의 방어 기능을 활용하되 제공하는 보호 범위를 확인해야 한다.

## 감사 로그로 누가 무엇을 했는지 남긴다

감사 로그(audit log)는 사용자나 운영자가 수행한 중요한 활동을 추적하기 위한 기록이다. 문제가 생겼을 때 작업 순서를 재구성하고 누가 어느 시점에 어떤 데이터를 조회하거나 바꿨는지 확인하는 데 사용한다.

| 기록 대상                        | 남길 수 있는 정보                    |
| -------------------------------- | ------------------------------------ |
| 로그인과 로그아웃                | 계정, 시각, 성공·실패 여부           |
| 비밀번호 초기화와 보안 설정 변경 | 작업자, 변경 대상, 시각, 처리 결과   |
| 민감 정보 조회                   | 조회자, 대상 식별자, 시각, 조회 목적 |
| 예약·계약 등의 중요 정보 변경    | 작업자, 대상, 작업 종류, 시각, 결과  |

감사 로그는 오류 분석용 일반 로그와 목적이 다르다. 일반 로그는 필요에 따라 로그 수준을 조정할 수 있지만, 중요한 감사 기록이 그 설정에 따라 빠져서는 안 된다. 필요한 보관 기간과 열람 권한도 업무와 적용 기준에 맞게 정한다.

활동을 추적하는 데 필요하다고 해서 비밀번호, 원본 토큰이나 고객의 민감 정보를 통째로 기록하지 않는다. 로그를 볼 수 있는 사람에게 데이터가 다시 노출될 수 있기 때문이다.

## API 응답과 로그에서 데이터 노출을 줄인다

운영 화면에 고객 정보가 많이 표시될수록 한 번에 가져갈 수 있는 정보도 많아진다. 고객 목록에서 이름, 전화번호와 주소 전체를 보여 주기보다 업무에 필요한 항목을 고르고 일부를 마스킹한다.

이때 **화면에 그리기 전에 서버 응답부터 마스킹되어 있어야 한다.** API에는 전화번호 원문을 보내고 프런트엔드에서 별표로 가리기만 하면 개발자 도구에서 원래 값을 확인할 수 있다.

![서버에서 마스킹한 뒤 전달하는 고객 정보. 서버가 조회 권한을 확인하고 필요한 항목만 선택해 마스킹한다. API 응답과 화면에는 마스킹된 정보만 전달된다.](/static/images/books/junior-backend-practical-knowledge/ch08/server-masking.svg)

고객 목록 전체를 볼 수 있는 사람을 제한하고, 그 밖의 운영자는 고객이 알려 준 정보로 필요한 건만 찾게 할 수도 있다. 목록과 상세 화면을 빠르게 반복 조회하는 접근도 탐지해야 한다.

로그도 같은 기준으로 살핀다. 인증 요청이나 오류를 기록하면서 비밀번호나 개인정보를 함께 남기면 저장소를 보호한 의미가 줄어든다. 응답 데이터, 운영 화면과 로그를 각각 확인해야 한다.

## 비정상 접근은 탐지 이후의 대응까지 정한다

계정 탈취나 정보 수집은 정상 사용자와 다른 접근 패턴을 만들 수 있다.

- 평소와 다른 지역이나 기기에서 로그인한다.
- 로그인 실패가 짧은 시간에 반복된다.
- 같은 조회 API를 과도하게 호출한다.
- 권한이 없는 기능에 반복해서 접근한다.

서비스는 이런 신호를 사용자에게 알려 계정 상태를 확인하게 하거나, 정책에 따라 일시적인 접근 제한과 계정 잠금을 적용할 수 있다. 반복적인 로그인 시도는 여러 값을 대입하는 브루트 포스 공격의 신호일 수 있다. 개인정보 조회를 짧은 간격으로 계속하는 경우에는 정보 수집도 의심할 수 있다.

보안 알림만 보내는 것으로 끝내지 않고, 어떤 조건에서 차단하고 어떻게 정상 사용을 복구할지도 정해야 한다. 필요한 감사 기록이 있어야 차단 원인을 확인하기도 쉽다.

## 입력을 SQL 구조에 섞지 않는다

사용자 입력을 SQL 문자열에 이어 붙이면 입력이 쿼리의 일부로 해석될 수 있다. 예를 들어 예약 코드가 들어갈 자리에 조건식이 섞이면 의도한 한 건보다 많은 데이터를 조회할 수 있다. 이런 취약점을 이용하는 공격이 **SQL 인젝션**이다.

`PreparedStatement`를 사용해 SQL 구조와 입력 데이터를 분리한다. 값을 문자열에 직접 삽입하지 않고 매개변수로 바인딩한다.

```java
String sql = """
    SELECT reservation_id, status
    FROM reservation
    WHERE reservation_code = ? AND account_id = ?
    """;

try (PreparedStatement statement = connection.prepareStatement(sql)) {
    statement.setString(1, requestedCode);
    statement.setLong(2, authenticatedAccountId);

    try (ResultSet rows = statement.executeQuery()) {
        // 조회 결과에서 응답에 필요한 필드만 읽는다.
    }
}
```

`authenticatedAccountId`는 인증한 사용자의 ID다. 코드에서는 쿼리와 값 바인딩, 자원 해제만 보여 주며 연결 획득과 응답 객체 생성은 생략했다. 특수문자를 직접 치환하는 방식으로 SQL 인젝션을 막으려 하지 않는다.

서버 코드를 작성할 때는 다음 항목도 함께 살핀다.

| 항목               | 확인할 내용                                                                 |
| ------------------ | --------------------------------------------------------------------------- |
| 입력 검증          | 필수 값, 허용 길이, 값의 범위 등을 서버에서 검사한다.                       |
| 민감 정보 보호     | 다시 읽어야 하는 민감 정보와 인증용 비밀번호에 알맞은 보호 방식을 적용한다. |
| 오류 응답          | 내부 IP, DB 정보와 자세한 시스템 구성을 외부로 노출하지 않는다.             |
| 통신 보호          | HTTPS로 전송 중인 데이터를 보호한다.                                        |
| 브라우저 요청 정책 | 허용할 출처와 쿠키를 사용하는 요청의 CSRF 방어를 확인한다.                  |

## 개발자의 장비와 계정도 보호 대상이다

개발자 PC에는 서버 접속 권한이나 DB 접근 수단이 있을 수 있다. 출처가 불분명한 파일이나 의심스러운 첨부 파일을 실행하면 장비 하나의 침해가 서버와 데이터의 침해로 이어질 수 있다.

자리를 비울 때는 화면을 잠그고, 로그인한 운영 도구를 다른 사람이 사용할 수 있게 두지 않는다. 민감 정보가 들어 있는 출력물도 방치하지 않고 보관하거나 폐기한다.

방화벽, 감사 로그 저장 공간, 탐지 기능과 접근 제어에는 비용이 든다. 그렇다고 기본적인 인증과 인가, 민감 정보 보호와 네트워크 접근 제한을 뒤로 미룰 수는 없다. 현재 서비스에서 먼저 줄여야 할 노출과 피해를 정하고 필요한 통제를 적용한다.

## 보충

### 비밀번호는 전용 해시로 저장하고 재설정한다

솔트를 붙인 SHA-256도 계산이 빠르므로 공격자가 많은 비밀번호 후보를 빠르게 대입할 수 있다. 실제 저장에는 Argon2id처럼 비용을 조절할 수 있는 비밀번호 해시를 검증된 라이브러리로 사용한다. 기존 환경에 따라 bcrypt나 PBKDF2 등을 검토하며, 솔트와 알고리즘·비용 설정을 포함하는 저장 형식을 사용한다. [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

비밀번호를 잊었을 때는 원래 값이나 새 비밀번호를 이메일로 보내기보다, 만료 시간이 짧고 한 번만 사용할 수 있는 재설정 수단으로 본인을 확인한 뒤 새 값을 정하게 한다. 재설정 사실을 알리고 필요하면 기존 세션도 무효화한다.

### 암호화는 모드와 IV, 패딩까지 명시한다

암호문을 만들 수 있는 것과 변조를 알아낼 수 있는 것은 다르다. CBC 암호화만으로는 무결성을 보장하지 못하므로, 새 설계에서는 GCM 같은 인증된 암호화 모드를 검토한다. RSA도 `Cipher.getInstance("RSA")`처럼 제공자 기본값에 맡기기보다 용도에 맞는 패딩과 매개변수를 명시한다. [OWASP Cryptographic Storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html)

다음은 AES-GCM으로 예약 메모를 암호화하고 복호화하는 흐름을 보여 주는 예제다. 메서드에 전달하는 `key`는 앞서 생성한 AES 키다.

```java
public record EncryptedMemo(byte[] iv, byte[] ciphertext) {}

public static EncryptedMemo encryptMemo(String memo, SecretKey key)
    throws GeneralSecurityException {
    byte[] iv = new byte[12];
    new SecureRandom().nextBytes(iv);

    Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
    cipher.init(Cipher.ENCRYPT_MODE, key, new GCMParameterSpec(128, iv));
    byte[] ciphertext = cipher.doFinal(memo.getBytes(StandardCharsets.UTF_8));
    return new EncryptedMemo(iv, ciphertext);
}

public static String decryptMemo(EncryptedMemo encrypted, SecretKey key)
    throws GeneralSecurityException {
    Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
    cipher.init(Cipher.DECRYPT_MODE, key,
        new GCMParameterSpec(128, encrypted.iv()));
    byte[] plaintext = cipher.doFinal(encrypted.ciphertext());
    return new String(plaintext, StandardCharsets.UTF_8);
}
```

GCM에서는 **같은 키로 IV를 재사용하면 안 된다.** 예제는 매번 12바이트 난수를 만들지만, 대규모 사용에서는 키별 사용량과 IV 충돌 위험, 키 교체 정책도 관리해야 한다. 암호문에는 인증 태그가 포함되며, 검증에 실패하면 복호화 결과를 사용하지 않는다. 키 ID와 버전 관리, 저장 형식, 입력 크기 제한과 오류 응답 처리는 생략했다.

### 공개 키 암호화와 전자서명은 구분한다

암호화는 수신자의 공개 키로 숨기고 개인 키로 복호화하는 용도이며, 서명은 서명자의 개인 키로 생성한 서명을 공개 키로 검증한다. SSH의 공개 키 사용자 인증도 개인 키로 만든 서명을 서버가 검증하는 과정이다. 이를 단순히 개인 키로 암호화하고 공개 키로 복호화한다고 설명하면 용도를 혼동하기 쉽다.

### JWT의 서명 검증과 내용의 비밀 유지는 다르다

서명된 JWT의 내용은 암호화된 것이 아니므로 민감 정보를 넣지 않는다. 서버는 허용한 알고리즘과 신뢰하는 키로 검증하고 발급자, 수신 대상, 만료 등 서비스가 요구하는 조건을 확인해야 한다. 문자열을 디코딩해 사용자 ID를 읽는 것만으로 인증하지 않는다. [RFC 8725 — JWT Best Current Practices](https://www.rfc-editor.org/rfc/rfc8725.html)

세션 쿠키에는 `Secure`, `HttpOnly`, 적절한 `SameSite` 속성을 적용한다. IP는 모바일 네트워크나 프록시 등의 영향으로 달라질 수 있고 여러 사람이 같은 IP를 공유할 수도 있으므로, IP 일치만으로 정상 사용자를 증명하거나 탈취를 완전히 막을 수는 없다.

### HMAC은 재전송과 클라이언트의 거짓말까지 막아 주지 않는다

올바른 MAC이 붙은 메시지도 복사해서 다시 보낼 수 있다. 중복 처리가 문제라면 요청 ID와 만료 시각도 MAC 계산 범위에 포함하고, 수신 측에서 유효 시간과 이미 처리한 요청인지 확인하는 수단을 별도로 설계한다. MAC만 비교하는 위 예제에는 이 처리가 포함되어 있지 않다.

브라우저나 사용자 앱에 공유 비밀 키를 넣고 결과를 보내게 하면, 그 키를 알아낸 사용자는 바뀐 결과에도 MAC을 만들 수 있다. 금액이나 보상처럼 신뢰해야 하는 결과는 서버가 검증할 수 있는 근거로 판단해야 한다. HMAC은 비밀 키를 신뢰할 수 있게 관리하는 통신 주체 사이에서 사용한다.

### CORS와 CSRF는 인증·인가를 대신하지 않는다

CORS는 브라우저가 다른 출처의 응답을 읽는 범위를 제어하는 정책이다. 브라우저 밖의 호출을 차단하는 API 인증 수단이 아니며, CORS를 설정해도 일부 교차 출처 요청은 서버에 도달할 수 있다.

쿠키는 브라우저가 자동으로 붙일 수 있으므로 상태를 변경하는 요청에는 CSRF 토큰 등 사용 중인 인증 방식에 맞는 방어가 필요하다. `SameSite`는 보조 수단으로 적용하고, 캡차 하나로 CSRF 대책을 대신하지 않는다. HTTPS, WAF와 입력 검증도 각각의 보호 범위가 있으므로 서버의 권한 검사와 매개변수 바인딩을 함께 적용한다. [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)
