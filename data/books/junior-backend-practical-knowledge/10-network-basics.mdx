외부 API 주소도 맞고 방화벽 설정도 열려 있는데 연결이 안 된다면 어디를 봐야 할까? 상대 업체에 전달한 IP가 실제 요청이 나가는 IP와 다른 경우도 있다. 외부에서 우리 서비스로 들어올 때의 주소와, 우리 서버가 외부로 요청할 때 사용하는 주소가 항상 같지는 않다.

서버 개발자는 HTTP 클라이언트나 DB 드라이버를 통해 네트워크를 사용한다. 연결 문제를 살펴보려면 애플리케이션 코드와 함께 주소를 찾는 과정, 패킷이 이동하는 경로와 전송 방식도 이해해야 한다.

## 노드와 네트워크, 라우터

휴대폰, 노트북, 서버처럼 데이터를 주고받는 장치를 <strong>노드(node)</strong>라고 한다. 여러 노드가 서로 통신할 수 있도록 연결된 시스템이 네트워크다. 집의 공유기에 연결된 장치들이나 사무실 컴퓨터들이 하나의 네트워크를 구성하는 예다.

네트워크로 전달하는 데이터 단위를 패킷이라고 한다. 패킷에는 출발지와 목적지 같은 제어 정보를 담은 헤더와 실제 데이터를 담은 페이로드가 있다. 큰 데이터를 보낼 때는 여러 전송 단위로 나누어 전달한다.

서로 다른 네트워크 사이에서 패킷을 전달하는 장치가 <strong>라우터(router)</strong>다. 휴대폰에서 서버로 보낸 패킷은 중간의 여러 라우터를 거칠 수 있다. 각 라우터는 목적지에 도달할 수 있는 다음 경로를 선택해 전달한다.

![네트워크 사이에서 패킷을 전달하는 라우터. 사무실의 노드가 경계 라우터와 중간 라우터를 거쳐 다른 네트워크의 서버와 통신한다.](/static/images/books/junior-backend-practical-knowledge/ch10/network-route.svg)

노드 사이에 가능한 경로가 하나만 있는 것은 아니다. 따라서 연결 문제를 확인할 때도 출발 노드와 목적 노드뿐 아니라 그 사이의 경로를 함께 살펴야 한다.

## IP로 대상을 찾고 도메인으로 이름을 붙인다

패킷을 목적지로 전달하려면 주소가 필요하다. 네트워크에서 통신 대상을 구분하는 주소가 **IP 주소**다.

IPv4 주소는 `192.168.50.23`처럼 네 개의 숫자를 점으로 구분해 표현한다. 각 숫자는 0부터 255까지이며 전체 길이는 32비트다. 주소 공간이 한정되어 있어 더 넓은 128비트 주소를 사용하는 IPv6도 함께 사용한다.

숫자로 된 주소를 매번 기억하기는 어렵다. 그래서 `api.example.test`처럼 이름을 사용하고, 그 이름에 연결된 IP 주소를 찾는다. 이런 이름을 **도메인 이름**이라고 하며, 이름에 연결된 주소를 조회하는 시스템이 **DNS**다. 이 글의 `example.test`와 `198.51.100.x`는 설명을 위한 예시다.

### 도메인은 계층으로 나뉜다

도메인 이름의 각 부분은 점으로 구분한다. 오른쪽이 상위 계층이고 왼쪽으로 갈수록 하위 이름이다. `api.example.test`에서는 `test`, `example`, `api` 순서로 계층을 내려간다.

일반적인 도메인에는 `com`, `org` 같은 최상위 도메인이나 `kr`, `jp` 같은 국가 코드 최상위 도메인이 있다. `co.kr` 아래에 이름을 등록하는 경우처럼, 등록 단계는 최상위 도메인의 정책에 따라 달라질 수 있다.

브라우저나 서버 프로그램은 도메인에 연결할 때 필요한 IP 주소를 DNS에서 조회한다. 주소를 구한 다음 그 주소로 연결을 시도한다.

![도메인 조회와 서버 접속의 구분. 클라이언트가 DNS에 api.example.test의 주소를 묻고 IP 목록을 받는다. 이후 선택한 주소의 서버로 연결한다.](/static/images/books/junior-backend-practical-knowledge/ch10/dns-lookup.svg)

### 한 이름에 여러 주소가 연결될 수 있다

도메인 하나가 IP 하나에만 대응하는 것은 아니다. 여러 주소를 등록하면 요청을 여러 서버로 분산하는 데 사용할 수 있다.

다음은 `api.example.test`를 DNS에 등록했다고 가정한 설명용 조회 결과다. 실제로 실행해서 얻은 값은 아니다.

```text
$ nslookup api.example.test
Name:    api.example.test
Address: 198.51.100.20
Address: 198.51.100.21
```

여러 주소가 반환된다는 사실과 모든 요청이 정확히 같은 비율로 분산된다는 것은 다르다. DNS 조회 결과와 실제 연결 대상을 구분해서 살펴본다.

### localhost와 hosts 파일

자기 컴퓨터에서 띄운 서버에 접속할 때는 `localhost`를 자주 사용한다. IPv4의 `127.0.0.1`은 자기 자신을 가리키는 루프백 주소다.

운영체제에는 이름과 IP의 대응 관계를 정하는 `hosts` 파일도 있다. 리눅스에서는 `/etc/hosts`, 윈도우에서는 `C:\Windows\System32\drivers\etc\hosts`에 있다. 이름 조회 설정에 따라 이 파일에 지정한 주소를 DNS 조회보다 먼저 사용할 수 있다. 도메인으로 접속한 결과가 예상과 다르면 DNS뿐 아니라 로컬의 이름 매핑도 확인한다.

## IP의 할당 방식과 사용 범위는 별개다

IP를 살펴볼 때는 **고정·동적**과 **공인·사설**을 구분해야 한다. 앞의 구분은 주소를 할당하고 유지하는 방식이고, 뒤의 구분은 주소를 사용하는 범위에 관한 것이다.

### 고정 IP와 동적 IP

고정 IP는 노드가 계속 같은 주소를 사용하도록 지정하는 방식이다. 서버처럼 다른 노드에서 찾아올 대상은 주소가 일정해야 관리하기 편하다.

동적 IP는 **DHCP** 서버에서 주소와 네트워크 설정을 할당받는 방식이다. IP 주소뿐 아니라 게이트웨이, 서브넷 마스크, DNS 서버 정보도 함께 받을 수 있다. 공유기에 연결하는 노트북이나 휴대폰에서 많이 사용한다.

동적 IP라고 연결할 때마다 반드시 다른 주소가 되는 것은 아니다. 일정 기간 같은 주소를 다시 할당받을 수도 있다. 같은 네트워크에서 주소가 충돌하지 않도록 관리하는 것이 중요하다.

윈도우의 `ipconfig` 같은 명령으로 현재 할당된 정보를 확인할 수 있다. 다음은 출력 항목을 단순화한 예다.

```text
IPv4 주소      : 192.168.50.23
서브넷 마스크   : 255.255.255.0
기본 게이트웨이 : 192.168.50.1
DNS 서버       : 192.168.50.1
```

고정 주소를 직접 설정하더라도 기존에 다른 장치가 쓰는 주소나 DHCP가 할당하는 범위와 충돌하지 않게 구성해야 한다.

### 공인 IP와 사설 IP

공인 IP는 인터넷에서 통신 대상을 식별하는 데 사용하는 주소다. 공개 API나 웹 서비스를 제공할 때 외부에서 찾아오는 주소로 사용한다. 공인 IP가 있다고 해서 모든 접속을 허용한다는 뜻은 아니다. 실제 연결은 경로와 방화벽 정책 등의 영향을 받는다.

사설 IP는 조직이나 가정 같은 내부 네트워크에서 사용하는 주소다. 별개의 네트워크에서는 같은 사설 주소를 재사용할 수 있다. 집의 노트북과 다른 회사의 서버가 같은 `192.168.50.23`을 사용하더라도 서로 분리된 네트워크라면 그 사실만으로 충돌하지 않는다.

IPv4의 사설 주소 범위는 다음과 같다.

| 범위                              | CIDR 표기        |
| --------------------------------- | ---------------- |
| `10.0.0.0` ~ `10.255.255.255`     | `10.0.0.0/8`     |
| `172.16.0.0` ~ `172.31.255.255`   | `172.16.0.0/12`  |
| `192.168.0.0` ~ `192.168.255.255` | `192.168.0.0/16` |

사설 주소는 일반 인터넷에서 직접 목적지로 찾아가는 주소로 사용하지 않는다. 내부 노드가 외부와 통신하거나 외부 요청을 내부 서버에 전달하려면 그 사이를 연결하는 구성이 필요하다.

## NAT는 패킷의 주소를 바꾼다

<strong>NAT(Network Address Translation)</strong>는 네트워크 경계에서 패킷의 IP 주소를 변환하는 기술이다. 사설 주소를 사용하는 내부 노드와 외부 네트워크를 연결할 때 흔히 사용한다.

| 종류 | 바꾸는 주소 | 예시                                                                    |
| ---- | ----------- | ----------------------------------------------------------------------- |
| SNAT | 출발지 주소 | 내부 서버가 외부 API를 호출할 때 사설 출발지 주소를 공인 주소로 바꾼다. |
| DNAT | 목적지 주소 | 공개 주소로 들어온 요청의 목적지를 내부 서버 주소로 바꾼다.             |

![SNAT와 DNAT의 주소 변환 방향. 외부로 나가는 요청은 출발지 10.20.0.15가 198.51.100.10으로 바뀐다. 외부에서 공개 주소로 들어온 요청은 목적지가 10.30.0.20으로 바뀐다.](/static/images/books/junior-backend-practical-knowledge/ch10/nat-direction.svg)

### 외부 업체가 보는 IP는 내부 서버의 주소와 다를 수 있다

내부 서버의 주소가 `10.20.0.15`여도 외부 API 제공자는 SNAT를 거친 `198.51.100.10`을 출발지로 볼 수 있다. 상대 업체에 IP 허용을 요청할 때는 **실제로 외부 요청이 나가는 경로의 공인 IP**를 전달해야 한다. 실제 요청을 보내는 환경에서 외부 IP 확인 서비스를 이용하거나 상대 업체의 접속 로그를 확인해 출발지 주소를 알아볼 수 있다.

우리 서비스로 들어오는 요청에 사용한 공인 주소를 그대로 전달하면 맞지 않을 수 있다. 외부에서 들어오는 경로와 내부에서 나가는 경로가 다른 장비나 주소를 사용할 수 있기 때문이다.

반대 방향에서는 공인 주소를 네트워크 경계 장비에 두고 DNAT로 내부 서버에 전달할 수 있다. 공개 주소와 사설 주소의 대응 관계를 알면 서버에 공인 IP가 직접 할당되어 있지 않아도 외부 요청이 도착하는 구성을 이해할 수 있다.

## VPN으로 내부 네트워크에 접속한다

운영 중인 서버와 DB에는 관리 작업을 위해 접속할 필요가 있다. 그렇다고 모든 서버의 SSH 포트나 DB 포트를 인터넷에 공개할 수는 없다. 내부 서버가 많아질수록 개별 공개 주소를 관리하는 일도 복잡해진다.

<strong>VPN(Virtual Private Network)</strong>은 인터넷 같은 공용 네트워크를 통해 사설 네트워크에 연결하는 방법이다. 암호화된 연결을 사용해 개발자가 외부에서도 내부 네트워크에 접근할 수 있게 구성한다.

사무실과 서버 네트워크 사이의 VPN 장비를 연결하는 방식도 있고, 집이나 외부 공간의 노트북에 VPN 클라이언트를 설치해 접속하는 방식도 있다.

![VPN을 통한 내부 서버 접근. 원격 개발자가 VPN 게이트웨이까지 암호화된 터널을 만든 뒤 접근이 허용된 서버 네트워크에 접속한다.](/static/images/books/junior-backend-practical-knowledge/ch10/vpn-tunnel.svg)

VPN은 내부로 들어갈 통신 경로를 제공한다. VPN에 접속한 사용자에게 어떤 서버와 기능을 허용할지는 별도로 제한해야 한다. 주소 변환을 하는 NAT와 암호화된 연결을 구성하는 VPN도 서로 다른 역할이다.

## 프로토콜은 통신하는 방법을 정한 규칙이다

두 노드가 데이터를 주고받으려면 메시지의 형식과 전달 방법에 대한 약속이 필요하다. 이 약속이 <strong>프로토콜(protocol)</strong>이다.

TCP/IP 모델은 보통 네 계층으로 설명한다.

| 계층                | 역할과 예시                                                    |
| ------------------- | -------------------------------------------------------------- |
| 애플리케이션        | HTTP, SMTP처럼 서비스가 주고받을 메시지와 동작을 정한다.       |
| 전송                | TCP, UDP처럼 호스트의 애플리케이션 사이에서 데이터를 전달한다. |
| 인터넷              | IP 주소를 바탕으로 패킷을 다른 네트워크로 전달한다.            |
| 네트워크 인터페이스 | 실제 연결된 링크를 통해 데이터를 주고받는다.                   |

마지막 계층을 데이터 링크와 물리 계층으로 나누어 다섯 계층으로 설명하기도 한다. 계층 수만 외우기보다 HTTP가 어떤 전송 프로토콜 위에서 동작하는지 연결해서 보는 것이 유용하다.

### TCP는 연결을 맺고 순서와 재전송을 관리한다

TCP는 두 끝점 사이에 연결을 맺은 뒤 데이터를 주고받는다. 연결을 시작하는 기본 과정이 **3-way handshake**다.

1. 클라이언트가 연결을 요청하는 `SYN`을 보낸다.
2. 서버가 `SYN-ACK`으로 응답한다.
3. 클라이언트가 `ACK`을 보내 연결을 수립한다.

![TCP 연결을 시작하는 세 단계. 클라이언트가 SYN을 보내고 서버가 SYN-ACK으로 응답한다. 클라이언트가 ACK을 보내 연결을 수립한다.](/static/images/books/junior-backend-practical-knowledge/ch10/tcp-handshake.svg)

TCP는 데이터의 순서를 관리하고 유실된 데이터를 재전송한다. HTTP/1.1·HTTP/2와 SMTP처럼 정확하게 데이터를 전달해야 하는 프로토콜에서 널리 사용한다.

다만 순서를 맞추기 위해 기다리는 시간이 생길 수 있다. 앞부분이 유실되면 뒤의 데이터가 도착해도 애플리케이션에는 순서대로 전달해야 한다. 이런 앞선 데이터에 대한 대기를 **HOL(Head-of-Line) 블로킹**이라고 한다.

### UDP는 전달과 순서를 보장하는 기능을 제공하지 않는다

UDP는 TCP와 같은 연결 수립 과정 없이 데이터그램을 보낸다. UDP 자체가 도착 여부를 확인해 재전송하거나 보낸 순서대로 정렬해 주지는 않는다. 사용하는 쪽에서 유실과 순서 뒤바뀜을 고려해야 한다.

DNS 질의나 음성 통신, 게임처럼 이런 특성에 맞는 용도에서 사용한다. 다만 DNS나 게임이 항상 UDP만 사용한다는 뜻은 아니다. UDP 위에 필요한 신뢰성 기능을 별도로 구현할 수도 있다.

TCP는 느리고 UDP는 빠르다는 한 문장만으로 선택하기는 어렵다. 연결 수립과 재전송이 필요한지, 일부 데이터를 잃었을 때 어떤 처리가 가능한지 등 통신 요구를 기준으로 비교한다.

### QUIC은 UDP 위에서 연결과 신뢰성을 구현한다

QUIC은 UDP를 바탕으로 연결 관리, 손실 복구와 혼잡 제어 등을 구현한 전송 프로토콜이다. 연결 ID를 사용하고, TLS를 통합해 암호화된 통신을 제공한다.

한 연결에서 여러 스트림을 다루는 멀티플렉싱도 지원한다. HTTP/2도 여러 스트림을 처리하지만 하나의 TCP 연결을 사용하므로 TCP 계층에서 순서를 기다리는 영향이 여러 스트림에 미칠 수 있다. QUIC은 스트림을 나누어 이런 대기를 줄인다.

![HTTPS에서 사용하는 전송 구조의 차이. HTTP/1.1과 HTTP/2는 TLS와 TCP를 사용한다. HTTP/3는 TLS를 통합한 QUIC을 사용하고 QUIC은 UDP 위에서 동작한다.](/static/images/books/junior-backend-practical-knowledge/ch10/http-transport.svg)

HTTP/3는 QUIC을 사용한다. TCP 연결과 TLS 연결을 별도로 수립하는 흐름과 달리 QUIC은 전송 연결과 보안 협상을 결합해 연결 수립 지연을 줄일 수 있다.

브라우저 개발자 도구의 Network에서 `Protocol` 열을 보면 실제 요청에 사용한 프로토콜을 확인할 수 있다. `h2`는 HTTP/2, `h3`는 HTTP/3를 나타낸다. 서비스가 HTTP/3를 지원한다는 설명만으로 모든 요청이 HTTP/3를 사용했다고 판단하지 않고 실제 요청을 확인한다.

## 포트 번호의 개수와 TCP 연결 수는 다르다

TCP의 포트 번호는 16비트이며 최댓값은 65,535다. 하지만 서버 전체가 TCP 연결을 65,535개까지만 가질 수 있다는 뜻은 아니다.

TCP 연결은 다음 네 값의 조합으로 구분한다.

```text
(로컬 IP, 로컬 포트, 원격 IP, 원격 포트)
```

아래는 같은 서버의 443 포트가 서로 다른 클라이언트 연결을 구분하는 예다.

```text
로컬 주소             원격 주소
198.51.100.20:443  ←  192.0.2.10:51000
198.51.100.20:443  ←  192.0.2.11:51000
198.51.100.20:443  ←  192.0.2.10:51001
```

로컬 포트가 모두 443이어도 원격 IP나 원격 포트가 다르므로 다른 연결이다. 반대로 하나의 로컬 IP에서 하나의 원격 IP와 포트로 연결을 계속 만든다면 사용할 수 있는 로컬 포트 범위가 제약이 될 수 있다.

실제 연결 한도는 운영체제의 파일 디스크립터 한도와 포트 설정, 사용 가능한 자원에도 영향을 받는다. 주소와 포트의 이론적인 조합 수를 계산하는 것만으로 운영 서버의 연결 용량을 정할 수는 없다.

## 보충

### TCP는 메시지 경계를 보존하지 않는다

TCP가 애플리케이션에 제공하는 것은 순서가 보장되는 바이트 스트림이다. 보내는 쪽에서 두 번 나누어 썼다고 받는 쪽에서도 정확히 두 번 같은 크기로 읽는 것은 아니다.

```text
송신 측의 쓰기: [예약 요청 A] [예약 요청 B]
수신 측의 읽기: [예약 요] [청 A + 예약 요청 B]
```

따라서 TCP 위에 직접 프로토콜을 만든다면 길이 필드나 구분자처럼 메시지를 나누는 규칙이 필요하다. HTTP도 자신의 메시지 형식에 맞는 경계 처리를 한다. [RFC 9293 — TCP의 데이터 분할](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.7)

### QUIC도 손실이나 네트워크 제약을 없애지는 못한다

QUIC에서 패킷이 유실되면 그 패킷의 데이터를 기다리는 스트림은 영향을 받는다. 다른 스트림이 같은 순서 복구를 기다릴 필요가 줄어드는 것이지, 유실과 지연이 사라지는 것은 아니다. 여러 스트림의 데이터가 같은 패킷에 실려 있었다면 그 스트림들은 함께 영향을 받을 수도 있다. [RFC 9000 — 스트림과 패킷 전송](https://www.rfc-editor.org/rfc/rfc9000.html#section-13)

네트워크가 UDP를 차단하면 QUIC 연결을 만들지 못할 수 있다. HTTP/3를 도입할 때는 서버 지원뿐 아니라 중간 네트워크와 클라이언트의 연결 조건도 확인해야 한다. 연결 수립이나 손실 상황에서 얻는 이점이 실제 서비스에서도 나타나는지 측정한다. [RFC 9114 — HTTP/3 연결](https://www.rfc-editor.org/rfc/rfc9114.html#section-3.1)
