컨트롤러에서 요청을 받고 서비스에서 처리한 뒤 DB에 저장하는 코드는 익숙하다. 그런데 기능이 늘어나면 규칙을 어디에 둘지, 서비스를 어떻게 나눌지, 조회와 변경을 같은 모델로 처리해도 될지 고민하게 된다.

서버 구조와 설계 패턴은 이런 문제를 다루는 방법이다. 먼저 각 패턴이 무엇을 나누는지 살펴보면 차이가 보인다.

| 패턴                 | 나누거나 모으는 대상                                      |
| -------------------- | --------------------------------------------------------- |
| MVC                  | 입력 처리, 비즈니스 로직, 응답 생성의 역할을 나눈다.      |
| 계층형 아키텍처      | 역할에 따라 계층을 나누고 의존 방향을 정한다.             |
| DDD 전술 패턴        | 관련된 도메인 객체와 규칙을 애그리게트에 모은다.          |
| 마이크로서비스       | 도메인을 기준으로 서비스를 나누고 독립적으로 배포한다.    |
| 이벤트 기반 아키텍처 | 발생한 사실을 이벤트로 전달해 생산자와 소비자를 연결한다. |
| CQRS                 | 상태를 변경하는 모델과 조회하는 모델을 분리한다.          |

## MVC: 입력과 로직, 응답 생성을 나눈다

MVC는 Model–View–Controller의 약자다. 웹 요청을 처리할 때 세 요소는 다음 역할을 맡는다.

- **모델:** 회원 가입, 예약 취소처럼 비즈니스 기능을 실행한다.
- **뷰:** 실행 결과를 사용자가 받을 응답으로 만든다. HTML 화면뿐 아니라 JSON 응답도 여기에 해당한다.
- **컨트롤러:** 요청을 해석하고 모델을 실행한 뒤 결과를 보여 줄 뷰를 선택한다.

![MVC의 요청 처리 흐름. 사용자가 컨트롤러에 요청하면 컨트롤러는 모델의 기능을 실행한다. 이후 결과를 뷰에 전달하고 뷰가 사용자에게 응답한다.](/static/images/books/junior-backend-practical-knowledge/ch11/mvc.svg)

예약 취소 요청을 예로 들면 컨트롤러는 경로에 담긴 예약 ID를 읽고, 입력 형식을 검사하고, 취소 기능에 맞는 요청 데이터로 변환한다. 취소할 수 있는 상태인지 판단하고 상태를 변경하는 일은 모델이 맡는다. 결과를 HTML로 보여 줄지 JSON으로 보낼지는 응답을 만드는 쪽의 관심사다.

이 구조에서는 **비즈니스 로직과 응답 생성 사이의 의존이 줄어든다.** 화면 템플릿 기술을 바꿨다고 취소 규칙까지 수정할 필요는 없다. 반대로 취소 조건이 바뀌었다고 뷰가 그 규칙을 구현할 필요도 없다.

컨트롤러는 요청 처리의 흐름을 조정한다. 비즈니스 계산이나 화면 생성 코드를 모두 컨트롤러에 넣으면 이 구분이 흐려진다. 사용자 인증처럼 요청을 처리하는 데 필요한 기능과, 도메인에서 판단해야 할 규칙도 구분해서 둔다.

## 계층형 아키텍처: 역할과 의존 방향을 정한다

계층형 아키텍처에서는 각 계층이 자기 역할을 맡고, 상위 계층이 하위 계층을 사용한다. 하위 계층에서 상위 계층을 거꾸로 참조하지 않는 것이 기본 규칙이다.

웹 애플리케이션에서는 흔히 네 계층으로 구성한다.

| 계층          | 맡는 일                                            | 예시                       |
| ------------- | -------------------------------------------------- | -------------------------- |
| 표현 / UI     | 사용자와 상호작용하고 요청을 응용 계층에 전달한다. | 컨트롤러, 뷰               |
| 응용          | 요청한 기능의 실행 순서를 조정한다.                | 예약 취소 서비스           |
| 도메인 / 모델 | 도메인의 규칙과 상태 변경을 구현한다.              | 예약의 취소 가능 상태 판단 |
| 인프라 / 영속 | DB, 외부 시스템 등 구현 기술을 지원한다.           | DAO, 문자 발송 연동        |

![바로 하위 계층에 의존하는 네 계층의 구성 예. 표현, 응용, 도메인, 인프라 순서로 화살표가 이어진다. 아래 계층에서 위 계층을 참조하지 않는다.](/static/images/books/junior-backend-practical-knowledge/ch11/layers.svg)

바로 아래 계층만 사용할 수 있게 제한하기도 하고, 아래에 있는 여러 계층을 사용할 수 있게 허용하기도 한다. 어느 규칙을 택했는지 일관되게 적용해야 코드의 실행 흐름을 따라가기 쉽다.

MVC의 컨트롤러와 뷰는 이 구조의 표현 계층에 속한다. 따라서 MVC와 계층형 구조를 함께 사용할 수 있다. MVC의 모델을 DB 테이블에 대응하는 클래스 하나로만 생각하면 비즈니스 로직을 어디에 둘지 놓치기 쉽다.

### 도메인 계층이 비어 있으면 규칙이 흩어진다

서비스와 DAO만 두고 구현하면 도메인 규칙이 응용 코드나 SQL로 퍼지기 쉽다. 예를 들어 다음 쿼리는 예약 상태가 `RESERVED`일 때만 `CANCELED`로 바꾼다.

```sql
UPDATE reservation
SET status = 'CANCELED'
WHERE reservation_id = ?
  AND status = 'RESERVED';
```

서비스 코드가 아래처럼 되어 있다면, 취소 가능한 상태가 무엇인지는 서비스를 읽는 것만으로 알기 어렵다.

```java
int changedRows = reservationDao.cancel(reservationId);
if (changedRows == 0) {
    throw new ReservationCancellationFailedException();
}
```

코드에는 DAO 호출과 결과 건수 확인만 있고, 상태 변경 조건은 SQL 안에 있다. 같은 규칙이 컨트롤러나 다른 서비스에도 생기면 변경할 곳을 찾기가 더 어려워진다.

조건부 UPDATE 자체가 잘못된 것은 아니다. 여기서 살펴볼 문제는 **규칙을 확인하려면 여러 계층을 돌아다녀야 한다는 점**이다. 도메인이 복잡해질수록 관련 규칙을 한곳에 모아 둘 필요가 커진다.

## DDD 전술 패턴: 도메인 규칙을 객체에 모은다

DDD(Domain-Driven Design)의 전술 패턴은 도메인 객체와 규칙을 정리하는 데 사용한다. 복잡한 모델을 작은 단위로 다루고, 관련된 로직을 모아 응집도를 높이는 데 도움이 된다.

| 구성 요소     | 역할                                                                                              | 예약 도메인에서의 예                           |
| ------------- | ------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| 엔티티        | 고유한 식별자로 구분한다. 내부 값이 바뀌어도 같은 식별자를 가진 객체다.                           | 예약 번호로 구분하는 예약                      |
| 밸류          | 별도 식별자 없이 금액이나 주소 같은 값을 표현한다. 불변으로 구현하는 것이 권장된다.               | 결제 금액, 이용 기간                           |
| 애그리게트    | 관련 객체를 하나의 개념적 단위로 묶고 그 단위의 일관성을 관리한다.                                | 예약과 예약 항목을 묶은 예약 애그리게트        |
| 리포지터리    | 애그리게트를 저장하고 조회하는 인터페이스를 제공한다.                                             | 예약 리포지터리                                |
| 도메인 서비스 | 특정 애그리게트에 넣기 어려운 도메인 로직을 표현한다. 외부 연동이 필요한 규칙에도 사용할 수 있다. | 외부 정책을 확인해 취소 수수료를 계산하는 기능 |
| 도메인 이벤트 | 도메인에서 일어난 사실을 표현하고 다른 부분에 변화를 알린다.                                      | 예약 취소됨                                    |

앞의 취소 예제를 도메인 모델로 옮겨 보자. 응용 서비스는 예약을 조회하고 취소 기능을 호출한다. 어떤 상태에서 취소할 수 있는지는 예약 객체가 판단한다.

```java
public class Reservation {
    private ReservationStatus status;

    public void cancel() {
        if (status != ReservationStatus.RESERVED) {
            throw new ReservationCancellationFailedException();
        }
        status = ReservationStatus.CANCELED;
    }
}
```

```java
public class CancelReservationService {
    private final ReservationRepository reservations;

    public CancelReservationService(ReservationRepository reservations) {
        this.reservations = reservations;
    }

    @Transactional
    public void cancel(long reservationId) {
        Reservation reservation = reservations.findById(reservationId)
            .orElseThrow(ReservationNotFoundException::new);

        reservation.cancel();
        reservations.save(reservation);
    }
}
```

식별자 필드와 생성자, 상태 enum, 예외 클래스, 리포지터리 구현은 생략했다. `findById()`는 `Optional<Reservation>`을 반환한다고 가정하며, 저장 단계를 드러내기 위해 `save()`를 명시했다.

이 예제는 역할 구분에 집중한다. 실제 동시 요청의 잠금과 충돌 처리는 별도로 필요하다.

응용 서비스가 규칙까지 모두 구현하는 대신, **예약 객체에 취소 규칙을 두고 응용 서비스는 작업을 조정한다.** 규칙이 바뀌면 먼저 예약 객체를 살펴볼 수 있다.

DDD에는 전술 패턴 외에 도메인 모델이 적용되는 경계를 정하는 **바운디드 컨텍스트(bounded context)**도 있다. 복잡한 도메인을 경계별로 나누어 관리하는 개념이며, 서비스를 분리할 때도 관련이 있다.

## 마이크로서비스: 독립적으로 배포할 수 있게 나눈다

모놀리식 아키텍처는 여러 기능을 하나의 애플리케이션으로 구현한다. 마이크로서비스 아키텍처는 더 작은 서비스로 나누고 서비스 사이의 연동으로 전체 기능을 제공한다.

서비스가 작다는 것만으로 이점이 생기는 것은 아니다. **한 서비스를 바꿀 때 다른 서비스를 함께 배포하지 않아도 되는가**가 중요한 기준이다. 코드 저장소만 나누고 매번 함께 수정하고 배포해야 한다면 독립적으로 운영하기 어렵다.

| 관점          | 모놀리식                                                                                           | 마이크로서비스                                                               |
| ------------- | -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 개발과 배포   | 하나의 애플리케이션을 관리하므로 배포가 단순하다. 작은 변경도 전체를 다시 배포한다.                | 서비스별 변경과 배포가 가능하다. 대신 독립 배포를 위한 경계 설계가 필요하다. |
| 확장과 기술   | 구조가 단순하고 코드 관리가 쉽다. 규모가 커지면 개발 속도가 느려지거나 기술 변경이 어려울 수 있다. | 필요한 서비스를 따로 확장하고 서비스별로 기술을 선택할 수 있다.              |
| 테스트와 운영 | 전체 흐름의 테스트와 디버깅이 비교적 쉽다. 한 기능의 문제가 전체에 영향을 줄 수 있다.              | 서비스 간 흐름의 테스트와 디버깅이 어려워지고 인프라가 복잡해진다.           |
| 팀 간 조율    | 같은 애플리케이션 안에서 변경을 맞춘다.                                                            | 서비스 간 소통과 연동을 위한 비용이 커질 수 있다.                            |

### 서비스를 나눌 때 확인할 기준

1. **독립 배포:** 다른 서비스의 배포 없이 변경하고 출시할 수 있어야 한다. 이를 위해 서비스 간 결합도를 낮춘다.
2. **도메인 중심의 경계:** 하나의 도메인 기능이 여러 서비스에 걸쳐 있으면 변경과 출시 비용이 커진다.
3. **자기 상태의 소유:** 다른 서비스와 DB를 공유하지 않는다. 다른 서비스의 데이터가 필요하면 그 서비스의 API 등을 통해 접근한다.
4. **감당할 수 있는 크기:** 서비스 크기에 절대적인 기준은 없다. 조직이 운영할 수 있는 수준과 경계가 적절한지에 집중한다.
5. **유연함에 드는 비용:** 기술 선택과 확장, 견고함을 얻는 대신 운영 비용이 든다. 얻는 효과와 감당할 비용을 함께 본다.
6. **아키텍처와 조직의 관계:** 조직 구조는 시스템 구조에 영향을 준다. 비즈니스 도메인과 팀의 책임이 서비스 경계를 뒷받침하는지도 살핀다.

구조와 코드 품질이 좋지 않은 애플리케이션을 여러 서비스로 쪼갠다고 문제가 사라지지는 않는다. 같은 문제가 네트워크 연동과 함께 남으면 더 다루기 어려워질 수 있다.

모놀리식 안에서도 모듈을 나누고 모듈 간 의존을 줄일 수 있다. 이런 **모듈러 모놀리스**는 하나의 애플리케이션을 유지하면서 유지보수성을 높이는 선택지다. 마이크로서비스는 유행이나 새로운 기술을 써 보고 싶은 마음보다, 분리해서 얻을 효과가 분명할 때 도입을 검토한다.

## 이벤트 기반 아키텍처: 일어난 사실을 전달한다

이벤트는 이미 발생한 사실이다. `예약 확정됨`, `결제 완료됨`, `인증 실패함`처럼 과거형으로 표현하면 명령과 구분하기 쉽다.

이벤트 기반 아키텍처는 세 요소로 구성된다.

- **생산자:** 이벤트를 생성하고 브로커에 전달한다.
- **브로커 또는 라우터:** 이벤트에 관심 있는 소비자에게 전달한다.
- **소비자:** 전달받은 이벤트에 맞게 자신의 작업을 수행한다.

![이벤트를 통한 시스템 연동. 예약 서비스가 예약 확정 이벤트를 브로커에 전달한다. 브로커는 알림 서비스와 이용 준비 서비스에 이벤트를 전달하고 각 서비스가 자신의 작업을 수행한다.](/static/images/books/junior-backend-practical-knowledge/ch11/events.svg)

예약 서비스는 예약이 확정되었다는 사실을 전달한다. 알림 서비스는 고객에게 안내를 보내고, 이용 준비 서비스는 필요한 준비를 시작할 수 있다. 생산자가 각 소비자의 처리 코드를 직접 호출하지 않아도 된다.

데이터 변경을 전달하는 용도 외에 이상 징후를 알리는 데도 사용할 수 있다. 인증 시스템이 로그인 실패 이벤트를 발행하면 다른 시스템이 연속 실패 횟수를 확인해 비정상 접근 여부를 판단하는 식이다.

Kafka 같은 메시징 기술을 이벤트 브로커로 사용할 수 있다. 생산자와 소비자가 브로커를 통해 간접적으로 연결되므로 서로의 배포에 미치는 영향을 줄이고 새로운 소비자를 추가하기 쉽다. 반면 이벤트가 중간 단계를 거치기 때문에, 발행된 이벤트가 어디까지 처리되었는지 추적할 수단이 필요해진다.

### 이벤트를 상태의 기록으로 사용할 수도 있다

이벤트를 삭제하지 않고 보관하도록 구성하고, 시스템의 모든 상태 변화를 이벤트로 남긴다면 기록을 통해 상태 변화를 추적할 수 있다. 이런 기록은 이벤트 소싱에서 상태를 구성하는 근거로도 사용할 수 있다.

다만 이벤트를 전달하는 구조와 이벤트를 상태의 원본으로 사용하는 설계는 구분해서 이해해야 한다. 브로커를 사용한다는 사실만으로 모든 상태 변경이 빠짐없이 기록되거나 재구성되는 것은 아니다.

## CQRS: 변경과 조회에 서로 다른 모델을 쓴다

예약을 취소할 때는 예약 상태와 취소 가능 조건이 필요하다. 예약 목록을 보여 줄 때는 숙소 이름, 이미지, 예약자 이름 같은 데이터를 함께 보여 주고 싶다. 변경할 때 필요한 데이터와 조회할 때 필요한 데이터가 서로 다르다.

두 요구를 하나의 모델에 계속 넣으면 모델이 커진다. 상태 변경 코드를 읽을 때 조회 화면만을 위한 속성까지 함께 봐야 하고, 화면 요구가 늘어날수록 변경 모델도 영향을 받는다.

CQRS(Command Query Responsibility Segregation)는 **상태를 변경하는 명령 모델과 상태를 읽는 조회 모델을 분리**한다.

- 명령 모델은 취소 가능 여부 같은 도메인 규칙을 실행하고 상태를 변경한다.
- 조회 모델은 화면에 필요한 데이터를 조회하는 데 맞춰 구성한다.

![같은 DB를 사용하는 CQRS 구조. 변경 요청은 명령 모델에서 규칙을 확인하고 DB에 반영한다. 조회 요청은 별도의 조회 모델에서 화면에 필요한 데이터를 읽는다. 모델은 분리되어도 DB를 반드시 나눌 필요는 없다.](/static/images/books/junior-backend-practical-knowledge/ch11/cqrs.svg)

모델을 나누면 각 기능에 맞게 구현하고 서로에게 미치는 영향을 줄일 수 있다. 조회 쪽에 캐시를 붙이거나 조회 전용 DB를 확장하는 방법도 검토하기 쉬워진다.

물론 비용도 있다. 명령과 조회에 필요한 코드를 따로 작성해야 한다. 서로 다른 저장 기술을 도입하면 배워야 할 기술이 늘고, 저장소를 나눴다면 데이터를 동기화할 방법도 필요하다.

단순한 CRUD에 모델만 둘로 늘리면 추가된 코드에 비해 얻는 이점이 작을 수 있다. 조회와 변경의 요구가 얼마나 다른지, 현재 모델이 얼마나 복잡한지부터 확인한다.

## 보충

### CQRS에 별도 DB나 이벤트 소싱이 필수인 것은 아니다

명령 모델과 조회 모델이 같은 DB를 사용해도 CQRS를 적용할 수 있다. 이벤트 소싱은 상태 변경을 이벤트의 연속으로 저장하는 별도의 패턴이며, CQRS와 함께 사용할 수 있는 선택지다.

읽기와 쓰기 저장소를 나누고 비동기로 동기화한다면, 변경 직후 조회 결과에는 아직 이전 값이 보일 수 있다. 이 경우에는 저장소 간 반영 지연을 전제로 화면과 처리 흐름을 설계해야 한다. [Microsoft Azure Architecture Center — CQRS](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs)

### DB 변경과 이벤트 발행 사이의 실패도 다뤄야 한다

예약 상태를 DB에 저장한 뒤 이벤트를 발행하기 전에 프로세스가 종료되면, 예약은 확정되었는데 다른 서비스는 그 사실을 모를 수 있다.

이때 검토할 수 있는 방법이 **트랜잭셔널 아웃박스**다. 상태 변경과 발행할 이벤트를 같은 DB 트랜잭션에 저장하고, 별도 처리가 커밋된 이벤트를 브로커에 전달한다. 전달을 재시도하면서 같은 이벤트가 중복 도착할 수 있으므로, 소비자는 처리한 이벤트 ID를 확인하는 등 같은 이벤트를 여러 번 받아도 결과가 중복되지 않게 만들어야 한다. [AWS Prescriptive Guidance — Transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)
