API가 응답하는 데 800ms가 걸렸는데 CPU를 사용한 시간은 4ms라면, 나머지 시간에는 무엇을 했을까? DB가 쿼리 결과를 보내거나 외부 API가 응답하기를 기다렸을 수 있다. 이런 요청이 많아지면 계산보다 **기다리는 요청을 유지하는 비용**이 문제가 된다.

먼저 기억할 내용은 네 가지다.

- 블로킹 I/O에서는 작업이 끝날 때까지 호출한 스레드가 기다린다. 요청마다 플랫폼 스레드를 할당하면 동시 요청이 늘수록 메모리 부담도 커진다.
- 가상 스레드는 지원되는 I/O를 기다리는 동안 캐리어 스레드를 다른 작업에 내준다. 순차적인 코드 흐름을 유지하면서 많은 대기 요청을 다룰 수 있다.
- 논블로킹 I/O는 개별 연결의 데이터를 기다리며 스레드를 붙잡아 두는 대신, 준비된 연결을 골라 처리한다. 소수의 스레드로 많은 연결을 관리할 수 있다.
- 두 방식 모두 느린 쿼리나 CPU 계산 자체를 빠르게 만들지는 않는다. 무엇이 병목인지 확인한 뒤 적용해야 한다.

## I/O 대기가 스레드 자원을 차지한다

서버는 클라이언트뿐 아니라 DB, Redis, 외부 API와도 네트워크로 데이터를 주고받는다. 애플리케이션 코드에 소켓이 보이지 않아도 JDBC 드라이버나 HTTP 클라이언트 내부에서는 데이터를 보내고 응답을 읽는다.

다음 코드에서는 `read()`가 반환될 때까지 호출한 스레드가 다음 작업으로 넘어가지 못한다.

```java
outputStream.write(requestBytes);
int size = inputStream.read(buffer);
// read()가 반환된 뒤 다음 작업을 실행한다.
```

출력도 버퍼 상태에 따라 대기할 수 있고, 입력은 읽을 데이터가 도착하지 않았다면 기다린다. 이때 **블로킹되는 대상은 호출한 스레드**다.

![서버가 DB와 외부 API에 요청하고, 요청을 담당한 플랫폼 스레드가 응답을 기다리는 동안에도 다른 실행 가능한 스레드는 CPU를 사용할 수 있다.](/static/images/books/junior-backend-practical-knowledge/ch07/network-wait.svg)

### 대기 중인 스레드가 CPU를 계속 쓰는 것은 아니다

스레드가 블로킹되면 OS는 다른 실행 가능한 스레드에 CPU를 할당할 수 있다. 따라서 I/O 대기를 곧바로 CPU가 바쁘게 낭비되는 상태라고 이해하면 안 된다.

문제는 요청을 담당한 플랫폼 스레드가 응답을 기다리는 동안에도 그 스레드의 스택 같은 자원이 필요하다는 점이다. 스레드 풀을 사용한다면 대기 중인 요청이 풀의 자리를 차지한다. 풀의 모든 스레드가 기다리고 있으면 CPU에 여유가 있어도 새 요청을 바로 처리하지 못할 수 있다.

### 스레드를 늘리면 어디까지 해결될까?

스레드를 더 만들면 일부 요청이 I/O를 기다리는 동안 다른 요청을 실행할 수 있다. 하지만 스레드를 계속 늘릴 수는 없다.

| 비용      | 요청이 많아지면 생기는 일                                                        |
| --------- | -------------------------------------------------------------------------------- |
| 메모리    | 플랫폼 스레드마다 스택 등 자원이 필요하다.                                       |
| 생성 비용 | 요청이 올 때마다 새 스레드를 생성하고 시작하는 부담이 커진다.                    |
| 스케줄링  | 실행 가능한 스레드가 많아지면 실행 순서를 조정하고 전환하는 비용이 커질 수 있다. |

컨텍스트 스위칭은 실행 중인 스레드의 상태를 저장하고 다른 스레드의 상태를 복원하는 과정이다. 전환 자체가 요청의 비즈니스 로직을 처리해 주지는 않는다.

플랫폼 스레드의 스택을 1MB로 가정하면 1만 개의 스택만 약 10GB다. 다만 이는 크기를 비교하기 위한 계산이다. 스택 크기는 환경과 설정에 따라 다르고, 예약한 메모리 전체를 처음부터 물리 메모리로 사용하는 것도 아니다.

서버를 늘리거나 더 큰 장비를 쓰는 방법도 있다. 구현을 크게 바꾸지 않고 처리 용량을 확보할 수 있지만 비용이 든다. 같은 자원으로 더 많은 요청을 처리하려면 대기 요청 하나가 차지하는 비용도 줄여야 한다.

## 가상 스레드는 기다리는 비용을 줄인다

플랫폼 스레드는 OS 스레드와 일대일로 대응한다. 반면 Java의 <strong>가상 스레드(virtual thread)</strong>는 JVM이 관리하며, 여러 가상 스레드를 적은 수의 플랫폼 스레드에 번갈아 올려 실행한다. Go의 고루틴도 런타임이 관리하는 경량 실행 단위라는 공통점이 있다.

가상 스레드를 실제로 실행하는 플랫폼 스레드를 **캐리어(carrier) 스레드**라고 한다. 가상 스레드를 캐리어에 올리는 것이 마운트, 분리하는 것이 언마운트다.

1. 가상 스레드 A가 캐리어에 올라 코드를 실행한다.
2. 지원되는 네트워크 I/O에서 기다려야 하면 A를 중단하고 캐리어에서 분리한다.
3. 캐리어는 실행 가능한 가상 스레드 B를 실행한다.
4. A의 I/O 대기가 끝나면 A가 다시 스케줄링되어 실행을 이어 간다. 이전과 다른 캐리어에서 실행될 수도 있다.

![하나의 캐리어가 요청 A를 실행하다가 A의 I/O 대기 중에는 요청 B와 C를 실행한다. A의 응답이 준비되면 실행을 이어 간다.](/static/images/books/junior-backend-practical-knowledge/ch07/virtual-carrier.svg)

개발자가 작성한 코드에서는 여전히 `read()` 호출이 끝난 뒤 다음 줄로 넘어간다. **요청의 가상 스레드는 기다리지만, 그 요청 때문에 캐리어까지 계속 기다릴 필요는 없는 것**이다. 모든 블로킹 연산이 반드시 캐리어를 내주는 것은 아니므로 사용하는 API와 실행 환경은 확인해야 한다.

### 메모리와 생성 비용이 작다

가상 스레드의 스택은 힙에 보관되며 필요한 만큼 늘고 줄어든다. 플랫폼 스레드보다 적은 비용으로 많은 실행 단위를 유지할 수 있다.

가령 가상 스레드당 메모리가 평균 2KB이고 캐리어가 8개라고 가정해 보자. 가상 스레드 1만 개는 약 20MB, 캐리어 스택을 각각 1MB로 잡으면 추가로 8MB가 필요하다. 플랫폼 스레드 1만 개와 자릿수부터 달라진다. 2KB나 28MB를 실제 서비스의 고정 사용량으로 외우기보다는, 호출 깊이와 보관하는 데이터에 따라 비용이 달라진다는 점을 기억하면 된다.

생성 비용이 작으므로 가상 스레드는 작업이 필요할 때 만들고 작업이 끝나면 종료하는 방식으로 사용한다. 플랫폼 스레드처럼 재사용하기 위한 풀을 미리 만들 필요가 없다.

### 빨라지는 것은 계산이 아니라 처리량이다

가상 스레드가 효과를 내기 좋은 조건은 **I/O 대기가 많고, 동시에 처리해야 할 요청도 많은 경우**다.

| 작업                                         | 가상 스레드로 기대할 수 있는 효과                                                         |
| -------------------------------------------- | ----------------------------------------------------------------------------------------- |
| DB·외부 API 응답을 오래 기다리는 다수의 요청 | 대기 중 캐리어를 공유해 같은 자원으로 더 많은 요청을 유지하고 처리할 수 있다.             |
| 정렬·이미지 변환 같은 CPU 중심 작업          | 계산량이 줄지 않는다. 스레드를 많이 만들어도 CPU 코어 이상의 계산 능력이 생기지는 않는다. |
| 동시 요청이 적은 서비스                      | 이미 자원에 여유가 있다면 차이가 작을 수 있다.                                            |

예를 들어 16코어 서버에서 초당 500개 요청을 받고 요청 하나에 평균 20ms가 걸린다면, 평균적으로 처리 중인 요청 수는 약 10개다. 이 정도 부하에서는 플랫폼 스레드만으로도 충분할 수 있다. 많은 가상 스레드가 적은 캐리어를 공유할 상황 자체가 적기 때문이다.

동시에 수백·수천 개의 요청이 대기하는 상황이라면 이야기가 달라진다. 가상 스레드의 메모리 이점이 커지고 플랫폼 스레드 부족으로 생기던 대기도 줄일 수 있다. 그래도 외부 API가 응답하는 데 걸리는 시간이나 쿼리 실행 시간 자체가 짧아지는 것은 아니다.

### 기존 코드 흐름을 유지하기 쉽다

가상 스레드의 장점은 순차적인 코드를 크게 바꾸지 않아도 된다는 점이다. 요청을 보내고, 응답을 받고, 결과를 가공하는 흐름을 유지할 수 있다. 적용할 때는 사용하는 프레임워크와 드라이버가 해당 환경에서 잘 동작하는지 확인한다.

가상 스레드 하나를 시작하려면 `Thread.ofVirtual()`을 사용할 수 있다.

```java
Thread worker = Thread.ofVirtual().start(() -> {
    // 이 안에서 DB 조회나 외부 API 호출 같은 작업을 수행한다.
});
worker.join(); // 작업이 끝날 때까지 호출한 쪽에서 기다린다.
```

`join()`의 `InterruptedException` 처리는 생략했다. 서버 프레임워크를 사용한다면 직접 요청마다 스레드를 만들기보다, 프레임워크가 제공하는 가상 스레드 실행 설정을 확인한다.

반면 논블로킹 I/O로 전환하면 데이터를 기다리는 방식뿐 아니라 결과를 이어서 처리하는 코드 구조도 달라질 수 있다. 기존 구현을 유지하면서 스레드 비용부터 줄일 수 있는지 살펴볼 이유가 여기에 있다.

## 논블로킹 I/O는 준비된 연결을 골라 처리한다

논블로킹 I/O에서는 지금 처리할 데이터가 없다고 호출한 스레드가 계속 기다리지 않는다. Java의 `SocketChannel`을 논블로킹 모드로 설정하면 `read()`가 현재 읽을 수 있는 만큼 읽고 반환한다.

```java
// channel은 연결된 논블로킹 SocketChannel이다.
// buffer에는 데이터를 받을 빈 공간이 있다고 가정한다.
int readBytes = channel.read(buffer);

if (readBytes > 0) {
    // 읽은 바이트를 누적하고 처리한다.
} else if (readBytes == 0) {
    // 이번 호출에서 읽은 데이터가 없다.
} else {
    // -1: 입력 스트림이 끝났다.
    channel.close();
}
```

`0`은 연결 종료를 뜻하지 않는다. 반대로 데이터를 일부 읽었다고 요청 메시지 하나를 전부 받았다는 뜻도 아니다.

### 반복해서 read()만 호출하면 바쁜 대기가 된다

데이터가 없는데도 무한 루프에서 `read()`를 계속 호출하면 유용한 작업 없이 CPU를 사용한다. 논블로킹으로 바꿨다는 사실만으로 효율이 좋아지는 것은 아니다.

보통은 여러 채널을 등록한 뒤, 어떤 채널에서 읽기·쓰기·연결 수락 같은 작업이 가능한지 알림을 받아 처리한다. Java에서는 `Selector`가 이 역할을 한다. 이런 방식을 <strong>I/O 멀티플렉싱(다중화)</strong>이라고 한다.

```text
채널과 관심 있는 연산을 Selector에 등록한다.

반복:
  준비된 연산이 생길 때까지 select()에서 기다린다.
  선택된 키를 하나씩 꺼내고 선택 집합에서 제거한다.
  연결 수락 / 읽기 / 쓰기 등 준비된 작업을 처리한다.
```

여기서 `select()`는 대기할 수 있다. 개별 연결 하나의 데이터가 오기를 기다리는 대신 **여러 연결 중 처리할 일이 있는 연결을 기다린다**는 차이가 있다. 논블로킹 I/O가 모든 함수 호출에서 대기를 없앤다는 뜻은 아니다.

## 리액터와 이벤트 루프

준비된 이벤트를 기다리고 알맞은 처리 코드에 넘기는 구조를 **리액터(Reactor) 패턴**이라고 한다.

- 리액터는 이벤트를 기다리고 어떤 핸들러를 실행할지 결정한다.
- 핸들러는 연결을 받아들이거나 데이터를 읽고 처리하는 일을 맡는다.
- 이 과정을 반복하는 실행 흐름이 이벤트 루프다.

![여러 소켓의 준비 이벤트를 Selector로 모아 이벤트 루프가 핸들러에 전달한다. 오래 걸리는 별도 작업은 작업 스레드에서 처리하고 결과를 돌려준다.](/static/images/books/junior-backend-practical-knowledge/ch07/selector-reactor.svg)

이벤트 루프 하나에서는 핸들러가 차례대로 실행된다. 핸들러 하나가 긴 CPU 계산을 하거나 블로킹 호출을 하면, 같은 이벤트 루프가 담당하는 다른 연결도 그동안 기다린다.

멀티코어를 활용하려면 연결을 여러 이벤트 루프로 나눠 맡길 수 있다. 오래 걸리는 계산이나 블로킹 작업을 별도의 작업 스레드로 넘기는 방법도 있다. 다만 다른 스레드에 넘기는 순간 결과를 전달하고 동시 접근을 조정하는 처리도 필요해진다.

### 저수준 처리는 프레임워크에 맡긴다

TCP 입력에서는 한 줄이 여러 번에 나눠 도착하거나, 한 번 읽은 데이터에 여러 줄이 들어올 수 있다. 블로킹 코드에서는 `BufferedReader.readLine()`이 줄을 구분하는 처리를 맡아 준다. 논블로킹 채널을 직접 다룬다면 연결마다 미완성 데이터를 보관하고 메시지 경계를 찾는 처리가 필요하다.

이런 코드를 직접 만들면 버퍼 관리와 메시지 분리 같은 일이 비즈니스 로직보다 커질 수 있다. Netty나 Reactor Netty 같은 프레임워크는 이벤트 루프와 디코더 등을 제공해 이 부담을 줄인다. 대신 프레임워크의 비동기 API와 실행 모델을 익혀야 한다.

## 어떤 방식을 선택할까?

먼저 성능 문제가 있는지, 그 원인이 무엇인지 확인한다. 문제가 없고 예상 부하도 충분히 감당한다면 구현을 복잡하게 바꿀 이유는 적다.

| 관찰한 문제                                                        | 먼저 검토할 방법                                       |
| ------------------------------------------------------------------ | ------------------------------------------------------ |
| 특정 DB 쿼리가 느려졌다.                                           | 실행 계획, 인덱스, 쿼리와 캐시를 점검한다.             |
| 이미지 변환 등 계산 중 CPU가 포화된다.                             | 연산 최적화, 작업 분리, CPU 자원 확장을 검토한다.      |
| I/O 대기 요청 때문에 플랫폼 스레드·메모리가 부족하다.              | 가상 스레드 적용 가능성과 기존 코드 호환성을 확인한다. |
| 많은 연결을 유지하는 데 자원이 들고 연결 처리 구조를 바꿀 수 있다. | 논블로킹 I/O와 관련 프레임워크를 검토한다.             |
| 병목은 확인했지만 구현을 바꿀 여력이 없다.                         | 서버 확장으로 우선 완화하고 변경 시점을 잡는다.        |

![성능 문제가 있는지 확인한 뒤, CPU 계산과 개별 작업 지연은 해당 원인을 개선하고 I/O 대기 요청의 자원 비용은 가상 스레드 또는 논블로킹 I/O로 줄이는 선택 흐름.](/static/images/books/junior-backend-practical-knowledge/ch07/choose-io-model.svg)

가상 스레드와 논블로킹 I/O 중 하나가 항상 더 좋은 것은 아니다. 코드 변경 범위, 유지보수 비용, 팀의 경험, 실제 부하를 함께 본다. 당장 구조를 바꾸기 어렵더라도 작은 실험으로 동작 방식과 측정 방법을 익혀 두면 문제가 생겼을 때 판단하기 쉽다.

### 성능 수치에서는 무엇을 비교했는지 본다

연결을 유지하는 비용, 요청 처리량, 개별 요청의 응답 시간은 서로 다른 지표다. 최대 동시 접속 수가 크게 늘었다고 해서 모든 API의 응답이 같은 비율로 빨라지는 것은 아니다.

연결 유지 실험에서 유리한 결과가 나왔더라도, 실제 DB 조회와 외부 API 호출이 포함된 요청에서는 다른 결과가 나올 수 있다. 장비와 메모리 제한, 연결당 데이터 크기, 실제 처리 내용을 함께 보고 우리 서비스와 비슷한 조건에서 비교한다.

## 보충

### 블로킹과 동기·비동기는 다른 질문이다

블로킹·논블로킹은 호출한 쪽이 그 자리에서 기다리는지, 동기·비동기는 작업 완료와 결과를 어떤 방식으로 받는지에 관한 구분이다.

| 방식          | 호출한 쪽의 흐름                                                |
| ------------- | --------------------------------------------------------------- |
| 블로킹 읽기   | 읽을 데이터가 없으면 호출이 반환할 때까지 기다린다.             |
| 논블로킹 읽기 | 현재 가능한 만큼 읽고 반환한다. 결과를 보고 이후 처리를 정한다. |
| 비동기 API    | 작업을 요청한 뒤 완료를 콜백이나 Future 등의 형태로 전달받는다. |

`Selector`의 준비 알림은 메시지 전체의 수신이나 비즈니스 작업의 완료 알림이 아니다. 또한 비동기 API를 썼어도 호출한 스레드에서 즉시 `Future.get()`으로 기다릴 수 있다. API 이름만 보고 실행 중인 스레드가 대기하는지 판단하지 않는다. [Java Selector](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/channels/Selector.html), [OpenJDK JEP 444](https://openjdk.org/jeps/444)

### Java 21~23과 Java 24 이후의 pinning 차이

가상 스레드가 캐리어에서 분리되지 못하는 상태를 **pinning**이라고 한다. Java 21~23에서는 `synchronized` 구간 안에서 블로킹되면 캐리어도 함께 묶일 수 있었다.

JDK 24에서는 `synchronized`로 인한 주요 pinning 제약이 개선되었다. 따라서 가상 스레드를 사용한다는 이유만으로 모든 `synchronized`를 `ReentrantLock`으로 바꿀 필요는 없다. 다만 네이티브 호출과 관련된 일부 상황 등 남아 있는 제약은 따로 확인해야 한다. 캐리어를 내줄 수 있더라도 같은 잠금을 기다리는 작업끼리는 계속 직렬화된다. [OpenJDK JEP 491](https://openjdk.org/jeps/491)

### 가상 스레드가 많아져도 DB 연결은 한정되어 있다

가상 스레드 1만 개를 만들 수 있어도 DB 연결 풀이 30개라면, 그 풀에서 동시에 빌려 쓸 수 있는 연결은 30개다. 더 많은 요청을 받아들인 뒤 DB 연결을 기다리게 만드는 것만으로 처리량이 계속 늘지는 않는다.

가상 스레드를 재사용하기 위한 풀은 필요 없지만, 제한된 자원에 대한 동시 접근 제어는 필요하다. DB 연결 풀, 외부 API의 동시 호출 제한, 세마포어는 각 자원의 처리 능력에 맞춰 유지한다. 대기 요청이 무한히 쌓이지 않도록 타임아웃과 요청 수 제한도 함께 정한다. [OpenJDK JEP 444 — 가상 스레드와 동시성 제한](https://openjdk.org/jeps/444#Do-not-pool-virtual-threads)

### 평균 동시 요청 수를 계산해 보기

안정적으로 요청을 처리하는 시스템에서는 다음 관계로 필요한 동시성의 규모를 가늠할 수 있다.

```text
평균 처리 중 요청 수 ≈ 초당 처리량 × 평균 응답 시간(초)

500건/초 × 0.02초 = 평균 10건
5,000건/초 × 0.2초 = 평균 1,000건
```

리틀의 법칙(Little's Law)을 요청 처리에 적용한 계산이다. 두 번째 상황은 동시에 많은 요청을 유지해야 하므로 요청당 스레드 비용이 더 크게 드러난다. 다만 평균값이므로 순간적인 요청 집중이나 긴 꼬리 지연까지 반영한 풀 크기 설정값은 아니다. [OpenJDK JEP 444 — 동시성과 처리량](https://openjdk.org/jeps/444#The-thread-per-request-style)

### 논블로킹 코드를 직접 짤 때 빠뜨리기 쉬운 것

- **부분 읽기:** 한 번의 `read()`가 메시지 전체를 반환한다는 보장은 없다. 미완성 데이터는 연결별로 보관하고 다음 입력과 합쳐야 한다.
- **부분 쓰기:** `write()`도 일부 바이트만 쓰거나 `0`을 반환할 수 있다. 남은 데이터는 보관하고 쓰기가 가능해질 때 이어서 보내야 한다.
- **쓰기 이벤트 등록:** 보낼 데이터가 남았을 때 쓰기 준비 이벤트를 기다리고, 모두 보내면 관심 연산에서 제외한다. 불필요한 쓰기 알림이 반복되면 바쁜 루프가 될 수 있다.
- **버퍼 한도:** 느린 상대에게 보낼 데이터를 계속 쌓으면 스레드를 아껴도 메모리가 부족해질 수 있다. 메시지 크기와 대기 버퍼에 상한을 둔다.

준비 알림은 다음 I/O를 시도할 기회다. 실제 읽고 쓴 바이트 수와 버퍼에 남은 데이터를 기준으로 상태를 갱신해야 한다. [Java SocketChannel](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/channels/SocketChannel.html), [Java SelectionKey](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/channels/SelectionKey.html)

### 바꾼 뒤에는 같은 부하로 비교한다

연결 수만 늘려 보는 테스트와 실제 DB·외부 API를 호출하는 테스트는 결과가 다를 수 있다. 같은 요청량과 작업 내용을 기준으로 처리량, p95·p99 응답 시간, 오류율, CPU와 메모리, 스레드 수, DB 연결 대기 시간을 함께 본다.

스레드 메모리는 줄었는데 DB 대기와 타임아웃이 늘었다면 병목이 다른 곳으로 옮겨 갔을 수 있다. 자원을 적게 쓰는지와 사용자가 원하는 시간 안에 응답을 받는지를 함께 확인한다.

## 복습 질문

<details>
<summary>CPU에는 여유가 있는데 요청이 밀릴 수 있는 이유는?</summary>

요청 처리 스레드가 모두 I/O 응답을 기다리거나 DB 연결 같은 제한 자원을 기다릴 수 있다. CPU 사용률만으로 서버에 여유가 있다고 판단할 수는 없다.

</details>

<details>
<summary>가상 스레드를 쓰면 느린 쿼리도 빨라질까?</summary>

쿼리 자체의 실행 시간은 줄지 않는다. 기다리는 동안의 플랫폼 스레드 비용을 줄일 수 있을 뿐이다. 쿼리가 병목이면 실행 계획과 인덱스 등을 먼저 확인한다.

</details>

<details>
<summary>논블로킹 I/O의 이벤트 루프에서 블로킹 API를 호출하면?</summary>

그 호출을 실행한 이벤트 루프가 기다리므로 같은 루프가 담당하는 다른 연결의 처리도 지연된다. 작업을 별도 스레드로 넘기거나 실행 모델에 맞는 API를 써야 한다.

</details>

<details>
<summary>가상 스레드 풀을 만들지 않는 것과 동시 요청을 제한하지 않는 것은 같은 말일까?</summary>

다르다. 가상 스레드는 재사용하기 위한 풀이 필요 없지만, DB나 외부 API가 감당할 수 있는 동시 작업 수와 전체 대기 요청 수는 제한해야 한다.

</details>
