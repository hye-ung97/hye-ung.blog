관리자 페이지에서 내려받기 버튼을 눌렀는데 파일이 내려오지 않았습니다. 개발자 도구에는 `Failed to fetch`라는 오류가 남았습니다.

처음에는 파일 생성에 문제가 생긴 줄 알았습니다. 그런데 내보내기 API는 200을 반환했고, 저장소에도 CSV 파일이 있었습니다. 파일을 만드는 데는 문제가 없었습니다.

최근 서비스를 분리하면서 파일 저장소를 바꾼 일이 있었습니다. 원인은 새 저장소의 CORS 설정이었습니다. 기존 저장소는 모든 출처를 허용했지만, 새 저장소는 등록된 출처만 허용했습니다. 그 목록에 관리자 페이지 주소가 빠져 있었습니다.

## 파일을 만드는 것과 가져오는 것은 별개였다

내려받기 버튼을 누르면 서버가 CSV를 만들고 파일 URL을 반환합니다. 관리자 페이지는 그 URL을 `fetch()`로 읽은 뒤 파일로 저장합니다.

API가 성공했다는 것은 파일 URL을 받았다는 뜻입니다. 그 URL에서 파일 내용을 가져오는 요청은 따로 있습니다. 이번에는 이 두 번째 요청에서 문제가 생겼습니다.

![CSV 다운로드가 막힌 위치. API는 CSV를 생성하고 파일 URL을 반환한다. 파일 저장소는 CSV를 응답하지만 CORS 허용 헤더가 없다. 브라우저는 응답을 JavaScript에 전달하지 않아 파일 저장으로 이어지지 않는다.](/static/images/cors-download/download-flow-v2.png)

## 브라우저는 응답을 읽어도 되는지 확인한다

관리자 페이지와 파일 저장소는 서로 다른 주소에 있습니다. 여기서 브라우저가 비교하는 기준은 출처입니다. 출처는 프로토콜, 호스트, 포트를 합친 값입니다. 하나라도 다르면 다른 출처로 봅니다.

예를 들어 `https://admin.example.com`과 `https://storage.googleapis.com`은 호스트가 다릅니다. 관리자 페이지의 JavaScript가 저장소의 응답을 읽으려면 저장소에서 이를 허용해야 합니다.

이 제한은 동일 출처 정책에서 나옵니다. 아무 사이트의 JavaScript나 다른 사이트의 응답을 읽을 수 있다면, 악성 사이트가 사용자의 로그인 상태를 이용해 다른 서비스의 개인정보를 읽으려 할 수 있습니다. 브라우저는 이런 접근을 기본적으로 제한합니다.

CORS는 서버가 특정 출처에 응답을 읽도록 허용하는 방법입니다. 브라우저는 서버가 보낸 HTTP 헤더를 보고 허용 여부를 판단합니다.

## 허용은 응답 헤더에 담긴다

관리자 페이지에서 파일을 요청하면 브라우저는 현재 페이지의 출처를 요청 헤더에 넣습니다.

```http
Origin: https://admin.example.com
```

저장소가 이 출처를 허용하면 응답에 다음 헤더를 붙입니다.

```http
Access-Control-Allow-Origin: https://admin.example.com
```

브라우저는 이 값을 확인한 뒤 JavaScript에 응답을 전달합니다. 헤더가 없거나 출처가 맞지 않으면 응답을 읽지 못하게 막습니다.

이번에는 새 저장소에 관리자 페이지 출처가 등록되어 있지 않았습니다. 그래서 필요한 허용 헤더가 응답에 붙지 않았고, 브라우저의 `fetch()`가 실패했습니다.

![CORS 설정 전후의 차이. 설정 전에는 응답에 허용 헤더가 없어 JavaScript가 CSV를 읽지 못한다. 관리자 페이지 출처를 등록한 뒤에는 허용 헤더가 포함되어 JavaScript가 CSV를 읽을 수 있다.](/static/images/cors-download/cors-check-v2.png)

단순한 GET 요청은 서버에 도착해 정상 응답을 받아도 이 검사를 통과하지 못할 수 있습니다. 서버가 응답하는 것과 브라우저가 그 응답을 JavaScript에 전달하는 것은 별개입니다.

요청 메서드나 헤더에 따라서는 브라우저가 `OPTIONS` 요청으로 허용 여부를 먼저 확인하기도 합니다. 이를 사전 요청이라고 합니다. 모든 CORS 요청에 이 과정이 있는 것은 아닙니다.

## 주소창에서 열리는 것만으로는 부족하다

파일 URL을 주소창에 직접 넣으면 열리는데, 내려받기 버튼에서는 실패할 수도 있습니다.

주소창에서 파일을 여는 것과 페이지의 JavaScript가 파일 내용을 읽는 것은 다른 동작입니다. 주소창으로 이동하는 경우에는 `fetch()`와 같은 CORS 검사가 적용되지 않습니다. URL이 열린다고 해서 다운로드 코드도 동작한다고 볼 수는 없습니다.

새 저장소의 CORS 허용 목록에 관리자 페이지 주소를 추가했습니다. 개발, QA, 스테이징 환경에서 요청했을 때 허용 헤더가 내려오는 것을 확인했고, 코드 수정은 필요하지 않았습니다.

저장소가 바뀌면서 파일을 읽을 수 있는 출처도 달라졌던 겁니다. 파일 생성까지는 정상이어서, 브라우저가 파일을 가져오는 요청을 확인하고 나서야 원인을 찾을 수 있었습니다.
