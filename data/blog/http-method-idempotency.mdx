## 들어가며

PUT은 같은 요청을 100번 보내도 결과가 한 번 보낸 것과 같다. 요청이 변화가 아니라 리소스의 최종 상태를 지정하기 때문이다.

이 글은 이 질문에서 출발해 HTTP 메서드를 멱등성이라는 기준으로 정리한다. 메서드는 클라이언트가 리소스에 원하는 동작을 알리는 신호이고, 멱등성은 그 요청을 실패 시 다시 보내도 되는지 알려주는 성질이다.

## 주요 메서드 한눈에 보기

실무에서 주로 쓰는 건 GET, POST, PUT, PATCH, DELETE 다섯 가지다.

| 메서드  | 용도                             | 요청 본문 | 안전 | 멱등       |
| ------- | -------------------------------- | --------- | ---- | ---------- |
| GET     | 리소스 조회                      | 보통 없음 | O    | O          |
| POST    | 리소스 생성, 처리 요청           | 있음      | X    | X          |
| PUT     | 리소스 전체 교체 (없으면 생성)   | 있음      | X    | O          |
| PATCH   | 리소스 일부 수정                 | 있음      | X    | 보장 안 됨 |
| DELETE  | 리소스 삭제                      | 보통 없음 | X    | O          |
| HEAD    | GET과 같되 헤더만 응답           | 없음      | O    | O          |
| OPTIONS | 지원 메서드 확인, CORS preflight | 없음      | O    | O          |

## GET vs POST, PUT vs PATCH

### GET vs POST

GET은 데이터를 URL 쿼리스트링에 담아 조회에 쓰고, POST는 본문에 담아 생성이나 처리 요청에 쓴다. GET은 안전하고 멱등해서 브라우저와 프록시가 마음대로 캐싱하고 재시도할 수 있지만, POST는 그럴 수 없다. POST가 본문을 쓴다고 보안이 강한 건 아니고, 암호화는 HTTPS의 역할이다.

### PUT vs PATCH

PUT은 리소스를 통째로 교체한다. `{name, email, age}`인 유저에 PUT으로 `{name}`만 보내면 email과 age가 사라질 수 있다. PATCH는 보낸 필드만 부분 수정한다.

## 안전성과 멱등성

안전(Safe)하다는 건 요청이 서버 상태를 바꾸지 않는다는 뜻이다. GET, HEAD, OPTIONS처럼 조회만 하는 메서드가 여기에 속한다.

멱등(Idempotent)하다는 건 같은 요청을 여러 번 보내도 서버 상태가 한 번 보낸 것과 같다는 뜻이다. 안전한 메서드는 상태를 아예 바꾸지 않으니 모두 멱등하다.

멱등성을 가르는 기준은 요청이 **최종 상태를 지정하느냐, 변화를 지시하느냐**다. 최종 상태를 지정하면 몇 번을 보내도 그 상태로 수렴하고, 변화를 지시하면 보낼 때마다 결과가 누적된다.

- **PUT**: "1번 유저를 `{철수, 25}`로 만들어라"는 최종 상태 지정이다. 자세한 이유는 바로 다음 섹션에서 다룬다.
- **DELETE**: "1번 유저가 없는 상태로 만들어라"는 지정이다. 두 번째 요청 때도 여전히 없는 상태다.
- **GET**: 상태를 바꾸지 않으니 당연히 멱등하다.
- **POST**: "새 유저를 하나 추가해라"는 변화 지시다. 두 번 보내면 철수가 두 명 생긴다.
- **PATCH**: `{"age": 26}`처럼 값을 지정하면 멱등하지만, "나이를 1 늘려라"처럼 변화를 보내면 멱등하지 않다. 그래서 스펙상 멱등성이 보장되지 않는다.

### DELETE 두 번째 요청의 404

같은 DELETE를 두 번 보내면 첫 응답은 200, 두 번째는 404일 수 있다. 그래도 멱등하다. 멱등성은 응답 코드가 아니라 서버 상태를 기준으로 하고, 두 경우 모두 리소스는 없는 상태이기 때문이다.

## PUT은 왜 멱등할까?

PUT 요청은 리소스의 최종 상태를 통째로 담고 있어서, 몇 번을 보내도 서버는 같은 상태로 덮어쓸 뿐이다. 같은 데이터를 POST로 보냈을 때와 비교하면 차이가 분명해진다.

```
PUT /users/1   { "name": "철수", "age": 25 }

1번째 → users/1 = {철수, 25}
2번째 → users/1 = {철수, 25}   (같은 값으로 덮어씀)
3번째 → users/1 = {철수, 25}

POST /users    { "name": "철수", "age": 25 }

1번째 → users/1 = {철수, 25}
2번째 → users/2 = {철수, 25}   (새 리소스 추가)
3번째 → users/3 = {철수, 25}
```

차이는 URI에서 시작된다. PUT은 `/users/1`처럼 대상을 직접 지정하니 매번 같은 자리를 덮어쓰고, POST는 `/users` 컬렉션에 보내니 서버가 매번 새 자리를 만든다.

1번 유저가 처음에 없었다면 첫 PUT이 리소스를 생성한다. 그래도 두 번째부터는 같은 내용으로 덮어쓰기만 하니 최종 상태는 여전히 하나다.

단, 멱등성은 HTTP가 자동으로 보장하는 게 아니라 서버 구현이 지켜야 하는 약속이다. PUT 본문을 기존 목록에 덧붙이도록(append) 구현하면 요청마다 리소스가 늘어나 멱등성이 깨지고, 클라이언트의 재시도도 안전하지 않게 된다. 반면 요청마다 로그를 남기거나 수정 이력을 쌓는 건 클라이언트가 요청한 효과가 아니라서 멱등성과 무관하다.

## 멱등성과 재시도

### 재시도와 Idempotency-Key

요청이 타임아웃되면 클라이언트는 서버가 처리했는지 알 수 없다. 멱등한 요청은 안심하고 다시 보낼 수 있지만, POST를 재시도하면 주문이나 결제가 중복될 수 있다.

그래서 결제 API는 클라이언트가 요청마다 고유한 `Idempotency-Key`를 헤더에 담아 보내게 한다. 서버는 첫 처리 결과를 키와 함께 저장해 두고, 같은 키로 다시 들어온 요청에는 새로 처리하지 않고 저장된 결과를 그대로 돌려준다. [Stripe](https://docs.stripe.com/idempotency), [토스페이먼츠](https://docs.tosspayments.com/reference/using-api/idempotency-key) 같은 결제 서비스가 이 방식으로 POST를 멱등하게 만든다.

## 정리

처음 질문으로 돌아가면, PUT이 멱등한 이유는 리소스의 최종 상태를 지정하기 때문이다. 요청이 최종 상태를 지정하는지, 변화를 지시하는지만 따져보면 어떤 메서드든 멱등성을 스스로 판단할 수 있고, 실패한 요청을 재시도해도 되는지도 알 수 있다.
