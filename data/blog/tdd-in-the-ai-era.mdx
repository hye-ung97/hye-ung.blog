## 들어가며: 테스트를 먼저 쓰면 모두 TDD일까?

AI에게 기능을 설명하면 몇 초 만에 코드가 나와요. 코드를 작성하는 비용이 낮아진 만큼, 그 코드가 맞는지 확인하는 테스트는 전보다 더 중요해졌어요.

그렇다면 구현 전에 테스트를 작성하기만 하면 TDD라고 할 수 있을까요?

요구사항에 해당하는 테스트를 한꺼번에 작성한 뒤 구현을 시작하는 것도 테스트 우선(Test-First) 개발이에요. 하지만 TDD의 핵심은 테스트의 작성 순서에만 있지 않아요. 지금 필요한 동작 하나를 선택하고, 실패를 확인하고, 가장 단순하게 통과시킨 뒤, 코드를 다시 살펴보는 짧은 사이클에 있어요.

이 글에서는 할인 계산기 예제를 조금씩 발전시키며 TDD가 어떻게 설계에 피드백을 주는지 살펴봐요. 마지막에는 AI가 이 사이클에서 무엇을 잘할 수 있고, 어떤 판단은 여전히 사람이 맡아야 하는지도 정리할게요.

## TDD는 작은 설계 사이클이다

TDD(Test-Driven Development)는 보통 Red → Green → Refactor의 세 단계로 설명해요.

![테스트가 통과하는 상태를 지키며 작은 사이클을 반복한다. Red에서 실패하는 테스트를 먼저 작성하고, Green에서 테스트를 통과하는 최소한의 코드를 쓰고, Refactor에서 통과 상태를 지키며 구조를 다듬는다. Refactor가 끝나면 다음 기능의 테스트로 다시 Red부터 시작하고, 한 바퀴는 보통 몇 분 안에 끝난다.](/static/images/tdd-in-the-ai-era/tdd-cycle.png)

Red에서는 다음에 만들 동작을 테스트로 표현하고, 예상한 이유로 실패하는지 확인해요. 처음부터 통과한다면 이미 구현된 동작을 검사하고 있거나 테스트가 잘못됐을 수 있어요.

Green에서는 그 테스트를 통과하는 가장 단순한 코드를 작성해요. 아직 필요하지 않은 확장성까지 미리 설계하지 않고, 지금 확인한 요구사항에만 집중해요.

Refactor에서는 모든 테스트가 통과하는 상태를 유지하면서 이름, 중복, 책임과 구조를 살펴봐요. 정리할 필요가 없다면 그대로 두는 것도 선택이에요. 중요한 것은 다음 동작을 추가하기 전에 현재 설계가 괜찮은지 한 번 멈춰서 확인하는 거예요.

이 세 단계를 몇 분 안에 돌 수 있을 만큼 작게 유지하고, 다음 동작으로 넘어가며 반복하는 것이 TDD의 기본 흐름이에요.

## 시작하기 전에 테스트 목록 만들기

가격과 할인율을 받아 최종 금액을 계산하는 기능을 만든다고 해볼게요. 코드를 쓰기 전에 필요한 동작을 짧은 문장으로 적어봅니다.

```text
- 10% 할인하면 9000원이 된다
- 다른 할인율도 계산할 수 있다
- 할인율이 0이면 원가를 반환한다
- 할인율이 0에서 100 사이가 아니면 거절한다
- 음수 가격은 거절한다
```

이 목록은 모든 테스트를 한꺼번에 작성하라는 뜻이 아니에요. 앞으로 구현할 동작을 잊지 않기 위한 메모에 가까워요. 지금은 가장 단순한 첫 번째 항목 하나만 선택합니다.

## 첫 번째 사이클: 가장 단순한 동작

### Red

10% 할인 결과를 테스트로 적어요.

```java
@Test
@DisplayName("10% 할인하면 9000원이 된다")
void discountTenPercent() {
    assertEquals(9000, DiscountCalculator.applyDiscount(10000, 10));
}
```

아직 `DiscountCalculator`가 없으므로 컴파일부터 실패해요. 이것으로 테스트가 실제로 새 동작을 요구하고 있다는 사실을 확인했어요.

### Green

우선 테스트를 통과하는 가장 단순한 코드를 작성해요.

```java
public class DiscountCalculator {

    public static int applyDiscount(int price, int discountPercent) {
        return 9000;
    }
}
```

`9000`을 그대로 반환하는 코드가 이상해 보일 수 있어요. 하지만 현재 확인된 예시는 하나뿐이고, 아직 어떤 일반화가 필요한지 테스트로 드러나지 않았어요. 이렇게 가장 단순한 값으로 시작하는 방식을 TDD에서는 Fake It이라고 불러요.

실무에서 계산식이 이미 명확하다면 처음부터 식을 작성해도 괜찮아요. Fake It은 반드시 지켜야 할 규칙이 아니라, 확인되지 않은 요구사항을 미리 구현하지 않도록 돕는 방법이에요.

### Refactor

코드가 한 줄뿐이라 아직 정리할 구조는 없어요. 테스트와 메서드 이름도 의도를 충분히 드러내고 있어요. 모든 테스트가 통과하는 것을 확인하고 다음 항목으로 넘어갑니다.

Refactor에서 항상 코드를 바꿔야 하는 것은 아니에요. 지금 구조가 다음 변화를 받아들이기에 충분하다고 판단하는 것도 Refactor의 결과예요.

## 두 번째 사이클: 예시가 일반화를 요구하다

### Red

이번에는 다른 할인율도 계산할 수 있어야 한다는 항목을 선택해요.

```java
@Test
@DisplayName("20% 할인하면 8000원이 된다")
void discountTwentyPercent() {
    assertEquals(8000, DiscountCalculator.applyDiscount(10000, 20));
}
```

기존 구현은 항상 9000을 반환하므로 새 테스트가 실패해요.

### Green

이제 두 예시를 모두 통과시키려면 할인율을 사용하는 계산식이 필요해요.

```java
public static int applyDiscount(int price, int discountPercent) {
    return price * (100 - discountPercent) / 100;
}
```

첫 번째 예시만 보고 일반화를 서두르지 않고, 두 번째 예시가 필요해졌을 때 공통 규칙을 찾는 과정을 삼각측량(Triangulation)이라고 해요.

### Refactor

계산식은 짧지만 `100`이 무엇을 뜻하는지 바로 읽히지는 않아요. 계산 과정을 이름으로 드러내도록 바꿔볼 수 있어요.

```java
private static final int FULL_PERCENT = 100;

public static int applyDiscount(int price, int discountPercent) {
    int remainingPercent = FULL_PERCENT - discountPercent;
    return price * remainingPercent / FULL_PERCENT;
}
```

동작은 달라지지 않았고 두 테스트도 계속 통과해요. 이처럼 Refactor는 기능을 추가하는 단계가 아니라, 테스트가 보호하는 상태에서 이미 동작하는 코드를 더 이해하기 쉽게 만드는 단계예요.

## 세 번째 사이클: 경계 조건이 책임을 드러내다

### Red

계산식은 생겼지만 유효하지 않은 할인율도 그대로 처리하고 있어요. 테스트 목록에서 할인율의 범위를 선택합니다.

```java
@ParameterizedTest
@ValueSource(ints = {-1, 101})
@DisplayName("할인율이 0에서 100 사이가 아니면 예외가 발생한다")
void invalidDiscountPercentThrows(int discountPercent) {
    assertThrows(
        IllegalArgumentException.class,
        () -> DiscountCalculator.applyDiscount(10000, discountPercent)
    );
}
```

현재 구현은 예외를 던지지 않으므로 테스트가 실패해요.

### Green

테스트가 요구하는 범위 검사만 추가해요.

```java
public static int applyDiscount(int price, int discountPercent) {
    if (discountPercent < 0 || discountPercent > FULL_PERCENT) {
        throw new IllegalArgumentException("할인율은 0에서 100 사이여야 합니다.");
    }

    int remainingPercent = FULL_PERCENT - discountPercent;
    return price * remainingPercent / FULL_PERCENT;
}
```

### Refactor

이제 계산과 검증이라는 두 관심사가 한 메서드에 있어요. 아직 코드가 짧아서 그대로 둬도 되지만, 검증의 의미를 이름으로 드러낼 수 있어요.

```java
public static int applyDiscount(int price, int discountPercent) {
    validateDiscountPercent(discountPercent);

    int remainingPercent = FULL_PERCENT - discountPercent;
    return price * remainingPercent / FULL_PERCENT;
}

private static void validateDiscountPercent(int discountPercent) {
    if (discountPercent < 0 || discountPercent > FULL_PERCENT) {
        throw new IllegalArgumentException("할인율은 0에서 100 사이여야 합니다.");
    }
}
```

여기서 바로 `DiscountPolicy` 인터페이스나 별도의 전략 객체를 만들 필요는 없어요. 정률 할인 외에 정액 할인, 회원 등급 할인, 반올림 정책 같은 요구사항이 실제로 추가될 때 새로운 테스트가 구조 변화의 필요성을 보여줄 수 있어요.

미래의 요구사항을 예상해 미리 추상화하는 것이 아니라, 지금까지 확인한 동작을 바탕으로 다음 변경을 받아들일 수 있을 만큼만 설계하는 것이 중요해요.

## 테스트가 어떻게 설계를 이끌었을까?

세 번의 사이클 동안 완성된 구조를 먼저 그리지 않았어요.

첫 번째 테스트는 호출하는 쪽에서 사용하기 쉬운 메서드의 모양을 만들었어요. 두 번째 테스트는 하드코딩된 값을 일반적인 계산식으로 바꾸게 했고, 계산 과정에 이름을 붙이도록 이끌었어요. 세 번째 테스트는 할인율의 유효성을 누가 책임질지 생각하게 만들었어요.

테스트가 좋은 설계를 자동으로 만들어준 것은 아니에요. 테스트는 현재 코드가 무엇을 하기 어려워하는지 보여주고, 안전하게 구조를 바꿀 수 있는 피드백을 제공했어요. 그 신호를 보고 이름과 책임, 추상화 수준을 판단하는 일은 개발자의 몫이에요.

그래서 TDD는 테스트 기법인 동시에 설계 기법이라고 불려요. 테스트의 개수보다 중요한 것은 작은 사례를 통해 설계에 질문하고, 동작하는 상태를 잃지 않으면서 답을 찾아가는 과정이에요.

## AI는 Green을 빠르게 만든다

AI는 TDD의 세 단계에서 서로 다른 역할을 할 수 있어요.

| 단계     | 사람이 판단할 일                           | AI가 도울 수 있는 일                |
| -------- | ------------------------------------------ | ----------------------------------- |
| Red      | 다음에 구현할 동작과 기대 결과 선택        | 빠뜨린 경계 조건과 테스트 후보 제안 |
| Green    | 테스트가 요구사항을 제대로 표현하는지 확인 | 테스트를 통과하는 최소 구현 작성    |
| Refactor | 책임, 이름과 추상화 수준 판단              | 중복 탐색과 리팩터링 후보 제안      |

AI가 가장 직접적으로 속도를 높여주는 단계는 Green이에요. 실패한 테스트와 오류 메시지를 주면 코드를 작성하고, 실행하고, 실패 원인을 읽어 다시 고치는 과정을 빠르게 반복할 수 있어요.

하지만 다음에 어떤 테스트를 작성할지는 우선순위와 도메인 규칙에 대한 판단이에요. Refactor에서 인터페이스를 추출할지, 현재 구조를 유지할지도 정답이 하나뿐인 문제가 아니에요. AI가 후보를 제안할 수는 있지만 결정까지 맡기기는 어려워요.

**AI는 Green의 비용을 낮춰주지만, 다음 Red와 Refactor의 방향은 사람이 선택해야 해요.**

## 테스트는 사람이 소유해야 한다

AI에게 테스트 통과만 목표로 주면 구현 대신 테스트를 수정할 수도 있어요. 실패하는 테스트를 지우거나 검증 조건을 약하게 만들고, 특정 입력값만 하드코딩해서 통과시키는 경우도 생길 수 있어요.

반대로 이미 완성된 코드를 보여주며 테스트를 만들어달라고 하면, 코드에 있는 버그까지 현재 동작으로 받아들여 테스트에 기록할 수 있어요. 구현을 보기 전에 작성한 테스트는 현재 코드가 아니라 원래 원했던 동작을 기준으로 삼을 수 있어요.

AI와 TDD를 할 때는 다음 정도의 규칙을 두는 게 좋아요.

- 테스트 목록과 기대 결과는 사람이 확인합니다.
- 기존 테스트를 수정하거나 삭제하려면 먼저 이유를 설명하게 합니다.
- 한 번에 실패하는 테스트 하나만 다룹니다.
- Green이 될 때마다 변경 내용을 확인하고 작은 단위로 커밋합니다.

대화에서 합의한 내용은 세션이 바뀌면 사라질 수 있지만, 테스트는 저장소에 남아요. AI가 앞선 대화를 기억하지 못해도 기존 테스트가 지켜야 할 동작을 다시 알려줘요.

## 리팩터링을 견디는 테스트

TDD에서 테스트는 Refactor를 안전하게 만들어야 해요. 내부 구현에 지나치게 묶인 테스트는 오히려 구조를 바꾸기 어렵게 만들어요.

아래 테스트는 `apply`가 내부에서 `calculate`를 호출하는지 확인해요.

```java
@Test
void applyCallsCalculate() {
    DiscountService service = spy(new DiscountService());

    service.apply(10000, 10);

    verify(service).calculate(10000, 10);
}
```

기능은 그대로인데 내부 메서드 이름만 바꿔도 테스트가 실패해요. 사용자가 원하는 동작보다 현재 구현 방법을 고정하고 있기 때문이에요.

입력과 결과로 관찰할 수 있는 행동을 검사하는 편이 Refactor에 더 유리해요.

```java
@Test
@DisplayName("10% 할인하면 9000원이 된다")
void discountTenPercent() {
    assertEquals(9000, new DiscountService().apply(10000, 10));
}
```

내부에서 어떤 메서드를 호출하든 결과가 같으면 테스트는 통과해요. 구현을 자유롭게 정리하면서도 지켜야 할 동작은 잃지 않을 수 있어요.

## 모든 코드에 TDD가 필요한 것은 아니다

TDD는 규칙이 명확하고, 잘못됐을 때 비용이 큰 코드에 잘 맞아요. 가격 계산, 권한 확인, 주문 상태 전이와 재고 차감처럼 입력과 기대 결과를 구체적으로 표현할 수 있는 비즈니스 로직이 대표적이에요.

한 번 발생한 버그를 수정할 때도 시작하기 좋아요. 버그를 고치기 전에 문제를 재현하는 테스트를 먼저 작성하면 Red가 만들어지고, 수정으로 Green을 만든 뒤 관련 구조를 정리할 수 있어요.

반대로 요구사항이 계속 뒤집히는 초기 프로토타입이나 결과를 눈으로 확인해야 하는 UI 배치에는 잘 맞지 않을 수 있어요. 구현 세부사항에 묶인 테스트를 많이 만들면 코드를 바꿀 때마다 테스트까지 함께 고쳐야 하는 부담도 생겨요.

TDD가 좋은 설계를 보장하는 것도 아니에요. 잘못된 테스트는 잘못된 방향으로 코드를 이끌 수 있고, 필요 이상의 추상화를 만들 수도 있어요. 작은 사이클에서 얻은 피드백을 어떻게 해석할지는 계속 판단해야 해요.

## 마치며

TDD의 핵심은 테스트 코드의 양이 아니에요. 지금 필요한 동작 하나를 선택하고, 실패를 확인하고, 가장 단순하게 통과시킨 뒤, 다음 변화를 받아들일 수 있도록 설계를 살펴보는 과정이에요.

AI는 이 반복에서 구현 비용을 크게 낮춰줘요. 하지만 다음에 무엇을 구현할지, 테스트가 요구사항을 제대로 표현하는지, 어떤 구조가 더 나은지를 결정하는 일은 여전히 개발자의 몫이에요.

코드는 AI가 작성할 수 있어도 Red를 선택하고 Refactor의 방향을 정하는 책임까지 맡길 수는 없어요. AI와 함께 TDD를 한다면 테스트 하나를 먼저 건네는 데서 끝나지 말고, 그 테스트가 다음 설계 결정을 어떻게 이끄는지까지 살펴봐야 해요.
