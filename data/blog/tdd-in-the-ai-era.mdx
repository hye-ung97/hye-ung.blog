## 들어가며

요즘은 AI에게 "이 기능 만들어줘"라고 하면 몇 초 만에 코드가 나와요. 코드를 쓰는 속도는 예전과 비교할 수 없을 만큼 빨라졌죠. 그런데 그 코드가 정말 맞는지 확인하는 시간은 생각만큼 줄지 않았어요.

AI와 오래 작업하다 보면 이런 경험도 한 번쯤 하게 돼요. 대화가 길어지거나 세션이 바뀌면서 AI가 앞에서 정한 규칙을 잊고, 멀쩡히 동작하던 코드를 조용히 바꿔버리는 거죠. 이럴 때 끝까지 믿을 수 있는 건 결국 테스트 코드예요.

이 글에서는 20년 넘게 이어져 온 개발 방법론인 TDD가 무엇인지, 그리고 AI가 코드를 쓰는 지금 왜 오히려 더 중요해졌는지 이야기해보려고 해요.

## TDD란 무엇인가

TDD(Test-Driven Development, 테스트 주도 개발)는 **코드를 작성하기 전에, 그 코드가 통과해야 할 테스트를 먼저 작성하는 개발 방식**이에요. 켄트 벡(Kent Beck)이 익스트림 프로그래밍(XP)의 핵심 실천법으로 정리하면서 널리 알려졌어요.

보통 우리는 기능을 먼저 만들고, 잘 되는지 확인하려고 테스트를 나중에 붙여요. TDD는 이 순서를 뒤집어요. "이 코드는 이렇게 동작해야 한다"를 테스트로 먼저 적고, 그 테스트를 통과시키기 위해 코드를 작성하죠.

순서만 바꾼 것 같지만 효과는 꽤 달라요. 테스트가 개발이 끝난 뒤의 확인 절차가 아니라, 개발 방향을 이끄는 도구가 되기 때문이에요. 이름에 '주도(Driven)'가 붙은 이유가 여기에 있어요.

## Red → Green → Refactor

TDD는 세 단계로 이루어진 짧은 사이클을 계속 반복해요.

![테스트가 통과하는 상태를 지키며 작은 사이클을 반복한다. Red에서 실패하는 테스트를 먼저 작성하고, Green에서 테스트를 통과하는 최소한의 코드를 쓰고, Refactor에서 통과 상태를 지키며 구조를 다듬는다. Refactor가 끝나면 다음 기능의 테스트로 다시 Red부터 시작하고, 한 바퀴는 보통 몇 분 안에 끝난다.](/static/images/tdd-in-the-ai-era/tdd-cycle.png)

빨간불에서 시작해 초록불을 켜고, 초록불을 유지한 채 코드를 다듬은 뒤 다음 기능으로 넘어가요.

**Red** 단계에서는 만들고 싶은 기능에 대한 테스트를 작성해요. 아직 구현이 없으니 테스트는 실패하고 빨간불이 켜져요.

**Green** 단계에서는 그 테스트를 통과하는 가장 단순한 코드를 작성해요. 이때는 코드가 조금 지저분해도 괜찮아요.

**Refactor** 단계에서는 테스트가 계속 통과하는 상태를 유지하면서 중복을 없애고 구조를 다듬어요.

간단한 할인 계산 함수로 예를 들어볼게요.

```java
// Red: applyDiscount가 아직 없으므로 컴파일조차 되지 않는다
@Test
@DisplayName("10% 할인하면 9000원이 된다")
void discountTenPercent() {
    assertEquals(9000, DiscountCalculator.applyDiscount(10000, 10));
}

// Green: 테스트를 통과할 만큼만 구현한다
public class DiscountCalculator {
    public static int applyDiscount(int price, int percent) {
        return price * (100 - percent) / 100;
    }
}
```

여기에 "할인율이 100을 넘으면 에러가 나야 한다"는 요구가 생겼다면, 코드부터 고치지 않아요. 그 상황을 검증하는 테스트를 먼저 추가하고 실패하는 것을 확인해요.

```java
@Test
@DisplayName("할인율이 100을 넘으면 예외가 발생한다")
void discountOver100Throws() {
    assertThrows(IllegalArgumentException.class,
            () -> DiscountCalculator.applyDiscount(10000, 150));
}
```

그다음 이 테스트를 통과하도록 구현하고, 정리하는 사이클을 다시 한 바퀴 돌면 돼요.

## TDD를 하면 무엇이 좋아질까

**요구사항이 명확해져요.** 테스트를 먼저 쓰려면 "이 함수는 무엇을 받고 무엇을 돌려줘야 하지? 예외 상황은?"을 구현 전에 정해야 해요. 모호했던 요구사항이 테스트를 쓰는 순간 구체적인 문장이 되고, 그 테스트는 그대로 실행 가능한 명세가 돼요.

**코드를 고치는 게 두렵지 않아요.** 기능마다 테스트가 쌓여 있으니 코드를 크게 바꿔도 기존 동작이 깨졌는지 몇 초 만에 확인할 수 있어요. 리팩터링을 미루게 만드는 "건드렸다가 뭐 하나 터지면 어쩌지"라는 불안이 줄어들죠.

**설계가 좋아지는 경향이 있어요.** 테스트하기 어려운 코드는 대개 의존성이 얽혀 있거나 한 번에 너무 많은 일을 해요. 테스트를 먼저 쓰다 보면 자연스럽게 작고, 역할이 분명하고, 의존성이 분리된 코드를 만들게 돼요.

**피드백이 빨라요.** 버그는 늦게 발견될수록 고치는 비용이 커져요. TDD는 방금 작성한 몇 줄에서 문제가 생기면 바로 알려주기 때문에, 원인을 찾느라 헤매는 시간이 줄어요.

덤으로 필요한 만큼만 만들게 되고, 테스트 코드가 "이 코드는 이렇게 쓰는 거예요"를 보여주는 살아있는 문서 역할도 해줘요.

## TDD는 테스트 기법이 아니라 설계 기법이다

TDD에서 흔히 오해하는 부분이 있어요. 이름에 '테스트'가 들어가다 보니 테스트를 많이 쓰는 방법론으로 생각하기 쉽지만, 핵심은 **설계와 피드백 루프**에 있어요.

코드를 다 짠 뒤에 테스트를 붙이는 방식(Test-Last)도 결과물만 보면 비슷해 보여요. 둘 다 테스트 코드가 남으니까요. 차이는 테스트가 설계 과정에 개입하느냐에 있어요. 테스트를 먼저 쓰면 구현을 고민하기 전에 "이 코드를 쓰는 사람 입장에서 어떤 모습이어야 편할까"를 먼저 생각하게 돼요.

TDD에는 또 하나의 의미가 있어요. 켄트 벡은 TDD를 프로그래밍하면서 느끼는 두려움을 관리하는 방법으로 설명하기도 했어요. 큰 문제를 한 번에 풀려고 하지 않고, 지금 확실히 동작하는 작은 한 걸음을 계속 쌓아가는 것. 이 사고방식 자체가 TDD의 본질이라고 볼 수 있어요.

## AI 시대에 TDD가 더 중요해진 이유

한 문장으로 정리하면 이래요. **AI는 TDD의 비용을 낮춰주고, 가치는 오히려 높여줘요.**

예전에는 코드를 작성하는 것 자체가 비싼 일이었어요. 이제는 수백 줄이 몇 초 만에 나오지만, 그 코드가 맞는지 확인하는 비용은 거의 그대로예요. 개발의 병목이 '작성'에서 '검증'으로 옮겨간 셈이고, TDD는 바로 그 검증 기준을 코드보다 먼저 정해두는 방법이에요.

**테스트는 AI에게 줄 수 있는 가장 정확한 명세예요.** "할인 기능 만들어줘"라는 요청은 해석의 여지가 많아요. 반올림은? 음수는? 100% 초과는? 반면 `applyDiscount(10000, 10) == 9000`은 누가 읽어도 같은 뜻이에요.

**테스트는 AI의 컨텍스트 밖에 저장된 기억이에요.** 대화 초반에 "음수 금액은 0으로 처리하자"고 정했더라도, 세션이 바뀌면 AI는 그 결정을 잊을 수 있어요. 그 결정이 테스트로 남아 있으면 AI가 잊어도 테스트가 실패하면서 알려줘요. 채팅 속 합의는 사라지지만 테스트는 저장소에 남아요.

**AI 에이전트에게 피드백 루프를 만들어줘요.** 테스트가 있으면 AI는 코드를 짜고, 돌려보고, 실패하면 에러를 읽고 다시 고치는 과정을 스스로 반복할 수 있어요. 테스트가 없으면 "그럴듯해 보이는 코드"에서 멈추고, 맞는지는 사람이 일일이 확인해야 해요.

**나중에 쓴 테스트는 버그까지 정답으로 기록할 수 있어요.** AI에게 "이 코드에 대한 테스트 짜줘"라고 하면, 코드에 버그가 있어도 테스트가 그 동작을 그대로 박제하는 경우가 많아요. 구현을 보기 전에 쓴 테스트는 "원래 이렇게 동작해야 한다"는 의도를 담기 때문에 이런 오염에서 자유로워요.

다만 함정도 있어요. AI는 테스트 통과가 목표가 되면 구현 대신 테스트를 고치거나 지우고, 특정 입력값만 하드코딩해서 통과시키기도 해요. 그래서 **테스트는 사람이 소유해야 해요.** 테스트가 깨졌을 때 요구사항이 바뀐 건지, 코드가 잘못된 건지는 사람이 판단하고, 프로젝트 규칙 파일에 "테스트 수정은 먼저 물어볼 것" 같은 지침을 적어두면 좋아요.

## TDD를 잘 쓰는 법

**테스트 목록부터 적어요.** 바로 테스트 코드를 쓰기보다 기능이 해야 할 일을 짧은 문장으로 먼저 나열해요. "10% 할인하면 9000원", "할인율 0이면 원가 그대로", "음수 가격은 에러"처럼요. 그리고 가장 단순한 것부터 하나씩 지워나가면 돼요.

**Red를 눈으로 확인해요.** 테스트를 쓰고 바로 구현으로 넘어가지 말고, 실제로 실패하는지 한 번 돌려보세요. 처음부터 통과하는 테스트는 assert를 빼먹었거나 엉뚱한 대상을 검증하고 있을 수 있어요.

**Green은 최소한으로, Refactor는 빼먹지 않게요.** 테스트 하나를 통과시킬 만큼만 구현하고, 초록불이 뜨면 바로 다음 기능으로 가고 싶은 마음을 참고 코드를 정리해요. Refactor를 건너뛰면 TDD는 그냥 "테스트가 붙은 지저분한 코드"가 돼요.

**구현이 아니라 행동을 테스트해요.** 가장 중요한 원칙이에요.

```java
// 나쁜 예: 내부 메서드 호출 여부에 묶여 있다
@Test
void applyCallsCalculate() {
    DiscountService service = spy(new DiscountService());
    service.apply(10000, 10);
    verify(service).calculate(10000, 10);
}

// 좋은 예: 입력과 결과만 확인한다
@Test
@DisplayName("10% 할인하면 9000원이 된다")
void discountTenPercent() {
    assertEquals(9000, new DiscountService().apply(10000, 10));
}
```

첫 번째 테스트는 내부 메서드 이름만 바꿔도 깨져요. 기능은 멀쩡한데 테스트가 깨지니, 리팩터링을 도와야 할 테스트가 오히려 발목을 잡아요. 두 번째는 내부를 어떻게 바꾸든 결과만 맞으면 통과해요.

**적용할 곳을 골라요.** 모든 코드에 똑같이 적용하려고 하면 지쳐요. 가격 계산, 권한 체크, 상태 전이처럼 규칙이 명확하고 틀리면 비싼 비즈니스 로직에 집중하는 게 효과가 가장 커요. 커버리지 100%는 목표로 삼지 않는 게 좋아요.

**AI와 함께라면 한 번에 하나씩 맡겨요.** 테스트 목록은 사람이 정하고, AI에게는 "이 테스트 하나를 통과시켜줘"처럼 요청해요. 테스트가 통과할 때마다 커밋해두면, AI가 엉뚱하게 고쳤을 때 바로 되돌릴 수 있어요.

## TDD는 만능일까

물론 아니에요. 익숙해지기 전까지는 개발 속도가 느리게 느껴지고, 구현 세부사항에 강하게 묶인 테스트를 쓰면 리팩터링할 때마다 테스트를 다 고쳐야 하는 부담이 생겨요.

요구사항이 계속 뒤집히는 탐색용 프로토타입이나, 결과를 눈으로 확인해야 하는 UI 레이아웃에는 잘 맞지 않을 수도 있어요. 연구 결과도 코드 품질이 개선된다는 쪽이 많지만, 생산성에 대해서는 엇갈리는 편이에요.

그래서 TDD를 종교처럼 모든 곳에 적용하기보다, 팀과 도메인에 맞춰 적용 범위를 정하는 게 현실적이에요. 특히 AI와 함께라면 몇 분 단위로 쪼개는 의식을 그대로 지키는 것보다 **"검증 기준을 먼저 정하고, 그 기준은 사람이 소유한다"는 정신**을 지키는 게 더 중요해요.

## 마치며

AI가 코드를 대신 써주는 시대에 개발자에게 남는 가장 중요한 일은 "무엇이 맞는 동작인가"를 정의하는 거예요. TDD는 그 정의를 코드보다 먼저, 실행 가능한 형태로 남기는 연습이에요.

처음부터 새 기능 전체를 TDD로 하려면 부담스러우니, **버그 수정부터** 시작해보세요. 버그를 발견하면 고치기 전에 그 버그를 재현하는 실패 테스트를 먼저 쓰고, 그다음 고치는 거예요. 사이클을 자연스럽게 익힐 수 있고, 같은 버그가 다시 생기는 것도 막아줘요.

다음에 AI에게 기능을 맡길 때, "만들어줘" 대신 테스트 하나를 먼저 건네보는 건 어떨까요?
