## 들어가며

프로젝트 초반에는 API가 몇 개 되지 않습니다. 사용자 목록이 필요하면 조회 API를 만들고, 주문 기능이 필요하면 주문 생성 API를 추가합니다. 각 API가 제대로 동작하는지만 확인해도 큰 문제가 없어 보입니다.

기능이 늘어나면 상황이 달라집니다. 비슷한 기능인데도 어떤 URL에는 동사가 들어가고, 어떤 URL에는 단수형과 복수형이 섞입니다. 성공과 실패를 모두 200으로 반환하거나, 같은 의미의 필드가 API마다 다른 이름을 사용하기도 합니다.

API를 만든 사람에게는 익숙한 규칙이지만 처음 사용하는 사람은 매번 문서를 확인해야 합니다. 이때 필요한 것은 더 복잡한 규칙이 아니라 다음 동작을 예상할 수 있게 해주는 일관된 기준입니다.

![REST API의 요청과 응답 흐름. 클라이언트가 HTTP 메서드와 URL로 API 서버에 요청을 보내면 서버는 리소스를 처리한다. 서버는 처리 결과를 HTTP 상태 코드와 JSON 응답에 담아 클라이언트에 돌려준다.](/static/images/rest-api-design-principles/request-response-flow.png)

## 주소만 보고 동작을 예상할 수 있게 만들기

### 1. URL에는 동작보다 리소스를 표현한다

처음 API를 만들다 보면 URL에 동작을 직접 넣고 싶어집니다.

```http
GET /getUsers
POST /createUser
POST /deleteUser
```

무엇을 하는 API인지는 바로 알 수 있습니다. 하지만 기능이 늘어나면 `get`, `create`, `remove`, `delete`처럼 비슷한 표현이 섞이기 시작합니다. URL과 HTTP 메서드가 동작을 중복해서 설명하는 문제도 생깁니다.

URL은 대상을 나타내고 HTTP 메서드는 동작을 나타내도록 역할을 나누면 더 단순해집니다.

```http
GET /users
POST /users
DELETE /users/42
```

`/users`는 사용자라는 리소스를 나타냅니다. 조회인지 생성인지 삭제인지는 HTTP 메서드가 알려줍니다. 새로운 기능이 추가돼도 기존 규칙으로 URL을 예상하기 쉬워집니다.

### 2. 리소스 이름은 복수형으로 통일한다

`/user/42`와 `/users/42` 중 하나만 맞다고 말하기는 어렵습니다. 중요한 것은 어떤 형태를 선택했는지보다 같은 규칙을 계속 유지하는 것입니다.

일반적으로는 복수형을 사용하면 컬렉션과 개별 리소스를 자연스럽게 표현할 수 있습니다.

```http
GET /users
GET /users/42
GET /users/42/orders
```

`/users`는 사용자 목록이고 `/users/42`는 그중 한 명입니다. 단수형과 복수형이 섞이지 않으니 URL을 외워야 하는 부담도 줄어듭니다.

### 3. HTTP 메서드의 의미를 지킨다

HTTP 메서드는 클라이언트가 리소스에 원하는 동작을 전달합니다. GET은 조회, POST는 생성이나 처리 요청, PUT은 전체 교체, PATCH는 일부 수정, DELETE는 삭제에 사용합니다.

예를 들어 사용자의 이름만 바꾼다면 다음과 같이 표현할 수 있습니다.

```http
PATCH /users/42
```

```json
{
  "name": "홍길동"
}
```

특히 PUT과 PATCH는 프로젝트마다 다르게 사용되기 쉽습니다. 두 메서드를 구분하기로 했다면 실제 구현도 그 약속을 따라야 합니다. 메서드별 의미와 멱등성은 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)에, PATCH의 동작은 [RFC 5789](https://www.rfc-editor.org/rfc/rfc5789.html)에 정의되어 있습니다.

### 4. 리소스 관계를 지나치게 깊게 표현하지 않는다

사용자의 주문을 조회하는 URL은 관계를 이해하는 데 도움이 됩니다.

```http
GET /users/42/orders
```

하지만 모든 관계를 URL에 담으려고 하면 주소가 금세 길어집니다.

```http
GET /users/42/orders/100/items/3/reviews
```

이 정도로 깊어진 URL은 읽기도 어렵고 관계가 바뀌었을 때 수정하기도 어렵습니다. 중첩된 URL은 소유 관계를 설명하는 데 필요한 수준까지만 사용하는 편이 낫습니다. 독립적으로 조회할 수 있는 리소스라면 별도의 주소를 제공할 수 있습니다.

```http
GET /items/3/reviews
```

![일관성이 없는 API와 정리된 API의 비교. 기존 API는 URL에 get, create, delete 같은 동작이 반복된다. 개선한 API는 users라는 리소스를 중심에 두고 GET, POST, DELETE 메서드로 동작을 구분한다.](/static/images/rest-api-design-principles/endpoint-before-after.png)

## 요청의 결과를 명확하게 전달하기

### 5. 상황에 맞는 HTTP 상태 코드를 사용한다

응답 본문에 성공 여부가 있다는 이유로 모든 요청에 200을 반환하면 클라이언트는 본문을 읽은 뒤에야 실패를 알 수 있습니다.

```json
{
  "success": false,
  "message": "사용자를 찾을 수 없습니다."
}
```

사용자가 존재하지 않는다면 404가 요청 결과를 더 명확하게 표현합니다. 조회 성공에는 200, 생성 성공에는 201, 응답 본문이 필요 없는 성공에는 204를 사용할 수 있습니다. 잘못된 요청에는 400, 인증이 필요하면 401, 권한이 없으면 403을 반환할 수 있습니다.

상태 코드를 가능한 한 많이 사용하는 것이 목표는 아닙니다. 클라이언트가 결과를 구분하고 다음 행동을 결정할 수 있을 정도로 일관되게 사용하는 것이 중요합니다.

### 6. 응답 데이터의 구조를 통일한다

한 API에서는 생성 시간을 `createdAt`으로 반환하고 다른 API에서는 `createdDate`로 반환한다면 두 필드가 같은 의미인지 문서를 다시 확인해야 합니다.

```json
{
  "id": 42,
  "name": "홍길동",
  "createdAt": "2026-10-01T12:00:00Z"
}
```

필드 이름뿐 아니라 날짜 형식과 빈 값의 표현도 통일해야 합니다. 값이 없을 때 `null`을 반환할지, 빈 문자열을 반환할지, 필드를 생략할지도 미리 정해 두는 편이 좋습니다.

모든 응답을 반드시 `data`로 감싸야 하는 것은 아닙니다. 어떤 형태를 선택하든 같은 종류의 응답이 같은 구조를 갖는 것이 더 중요합니다.

### 7. 에러 응답에는 식별 가능한 코드를 포함한다

에러 메시지는 사람이 읽기에는 편하지만 프로그램이 실패 원인을 구분하는 기준으로 사용하기에는 불안정합니다. 문구가 바뀌거나 다른 언어로 번역될 수 있기 때문입니다.

```json
{
  "code": "EMAIL_ALREADY_EXISTS",
  "message": "이미 사용 중인 이메일입니다.",
  "details": {
    "field": "email"
  }
}
```

클라이언트는 `code`를 기준으로 에러 종류를 판단하고 `message`를 사용자에게 보여줄 수 있습니다. 형식이 통일되어 있으면 이메일 입력란을 강조하거나 재시도 버튼을 보여주는 처리도 단순해집니다.

에러 응답에 더 많은 표준 정보가 필요하다면 [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)의 Problem Details 형식도 참고할 수 있습니다.

## 오래 사용할 수 있는 API 만들기

### 8. 목록 조회에는 필터링과 페이지네이션을 고려한다

개발 초기에는 전체 목록을 한 번에 반환해도 문제가 없어 보입니다. 데이터가 늘어나면 응답이 무거워지고 조회 시간도 길어집니다.

```http
GET /users?status=active&sort=createdAt&order=desc&limit=20
```

목록 API에는 필요한 데이터만 고를 수 있는 필터와 정렬 기준, 한 번에 가져올 개수를 지정할 방법이 필요합니다.

관리자 화면처럼 특정 페이지로 이동해야 한다면 페이지 번호 방식이 편리합니다. 데이터가 계속 추가되는 피드에서는 커서 방식이 더 안정적일 수 있습니다. 한 가지 방식을 모든 목록에 적용하기보다 데이터가 바뀌는 방식과 화면의 사용 방법을 함께 살펴봐야 합니다.

### 9. 기존 클라이언트와의 호환성을 지킨다

이미 사용 중인 응답 필드를 삭제하거나 의미를 바꾸는 일은 생각보다 영향이 큽니다. 서버에서는 작은 변경처럼 보여도 해당 필드를 사용하는 웹과 앱에서는 오류가 발생할 수 있습니다.

기존 동작을 유지하기 어려운 변경이라면 새로운 버전을 제공할 수 있습니다.

```http
GET /v1/users
GET /v2/users
```

그렇다고 사소한 변경마다 버전을 추가하면 관리해야 할 API만 늘어납니다. 새로운 필드를 추가하는 것처럼 기존 클라이언트를 깨뜨리지 않는 변경인지, 기존 계약을 바꾸는 변경인지 먼저 판단해야 합니다.

### 10. 문서와 실제 구현을 함께 관리한다

API 문서가 없으면 사용자는 코드를 직접 확인하거나 담당자에게 물어봐야 합니다. 문서가 있더라도 실제 응답과 다르면 더 큰 혼란을 만듭니다.

좋은 문서에는 URL과 HTTP 메서드, 요청 값, 응답 예시, 상태 코드, 에러 코드, 인증 방법이 담겨 있어야 합니다. OpenAPI 같은 명세를 활용하면 문서와 구현 사이의 차이를 줄이는 데 도움이 됩니다.

문서를 한 번 작성하고 끝내는 것보다 API가 바뀔 때 문서도 함께 바뀌는 구조를 만드는 일이 중요합니다.

## 완벽한 REST보다 일관된 API

실제 프로젝트에서는 비즈니스 요구사항과 개발 일정, 기존 시스템의 구조를 함께 고려해야 합니다. REST 원칙만으로 표현하기 어려운 기능도 있습니다.

그럴 때 중요한 것은 RESTful이라는 이름에 맞추기 위해 억지로 URL을 만드는 것이 아닙니다. 왜 이런 형태를 선택했는지 설명할 수 있고, 같은 상황에 같은 기준을 적용할 수 있어야 합니다.

URL은 리소스를 표현하고 HTTP 메서드는 동작을 표현합니다. 요청 결과는 상태 코드로 전달하고 응답과 에러 형식은 일관되게 유지합니다. 여기에 변경 가능성과 문서화까지 고려하면 처음 API를 접하는 사람도 다음 동작을 어렵지 않게 예상할 수 있습니다.

좋은 API는 문서를 보지 않아도 모든 것을 알 수 있는 API가 아닙니다. 문서를 보기 전의 예상과 문서를 확인한 뒤의 실제 동작이 크게 다르지 않은 API에 가깝습니다.

지금 사용하고 있는 API는 처음 보는 사람도 요청과 응답을 어렵지 않게 예상할 수 있을까요? 그렇지 않다면 가장 자주 사용하는 API 하나부터 URL, HTTP 메서드, 상태 코드, 응답 형식을 차례로 점검해 보세요. 좋은 API 설계는 많은 규칙을 한꺼번에 적용하는 것이 아니라, 팀이 합의한 기준을 꾸준히 지키는 데서 시작합니다.
