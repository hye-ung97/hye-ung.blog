상품 조회 API에 Redis 캐시를 적용했다고 해보자. 캐시에 값이 있으면 바로 반환하고, 없으면 DB에서 가져와 저장한다. 같은 상품을 반복해서 조회할수록 DB에 가는 요청은 줄어든다.

그런데 인기 상품의 캐시가 만료되는 순간에는 어떨까? 다음 요청 하나가 값을 다시 채우면 될 것 같다. 그 요청이 DB 응답을 기다리는 동안 다른 요청이 들어오면, 그 요청도 비어 있는 캐시를 확인한다.

**첫 번째 요청이 캐시를 채우기 전까지, 같은 상품의 DB 조회가 여러 번 시작될 수 있다.**

## 캐시가 없으면 DB에서 가져온다

익숙한 Cache-aside 코드부터 시작하자. Redis 클라이언트는 연결돼 있고, `db.selectProduct`는 상품 하나를 조회하는 함수라고 가정한다.

```javascript
async function getProduct(productId) {
  const key = `product:${productId}`
  const cached = await redis.get(key)

  if (cached !== null) {
    return JSON.parse(cached)
  }

  const product = await db.selectProduct(productId)
  await redis.set(key, JSON.stringify(product), { EX: 60 })
  return product
}
```

캐시를 확인하고, 없으면 DB에서 조회해 60초 동안 저장한다. 한 요청 안에서는 순서대로 실행된다. 다만 다른 요청이 같은 상품을 이미 조회하고 있는지는 확인하지 않는다.

상품 1의 캐시가 만료된 뒤 A, B, C가 들어오면 다음 순서가 가능하다.

```text
A: cache miss → DB 조회 시작
B: cache miss → DB 조회 시작
C: cache miss → DB 조회 시작

A: DB 조회 완료 → 캐시 저장
B: DB 조회 완료 → 캐시 저장
C: DB 조회 완료 → 캐시 저장
```

A가 캐시를 채우기 전에 B와 C도 miss를 확인했다. 요청마다 코드는 정상적으로 동작했지만, 같은 데이터를 가져오는 DB 조회도 세 번 실행됐다.

이처럼 캐시를 다시 채우는 동안 [여러 요청이 원본 데이터를 중복 조회하는 상황](https://redis.io/blog/cache-layer-architecture-guide/)을 <strong>캐시 스탬피드(Cache Stampede)</strong>라고 한다. 인기 키의 만료에서 발생하는 대표적인 문제다.

DB 조회가 오래 걸리면 캐시가 비어 있는 구간도 길어진다. 그 사이 들어온 요청이 다시 DB로 향하므로, 이미 바쁜 DB에 조회가 더 쌓일 수 있다.

## 같은 상품에 요청 100개를 겹쳐 보내기

실험에서는 Redis 7.0.8과 Node.js 22.22.3을 사용했다. 상품 데이터는 Node.js에 포함된 SQLite에 넣고, 애플리케이션 프로세스는 하나만 실행했다.

동시 요청은 같은 프로세스에서 `getProduct()`를 100회 동시에 호출해 재현했다. 측정한 시간은 함수 호출부터 결과 반환까지이며, HTTP 요청의 왕복 시간은 포함하지 않는다.

캐시를 저장한 뒤 실제 TTL 만료를 기다리고, 상품 1을 조회한다. 이때 모든 호출이 첫 `GET`에서 miss를 확인한 뒤 함께 다음 단계로 넘어가도록 Promise로 실행 순서를 맞췄다.

DB 조회 경로에는 100ms의 대기를 추가했다. 첫 요청이 캐시를 채우기 전에 다른 요청이 들어오는 구간을 확보하기 위해서다. SQLite의 실제 조회가 100ms 걸린다는 뜻은 아니다.

```text
캐시 TTL 만료 확인
  → 요청 100개가 첫 GET 실행
  → 모두 cache miss 확인
  → 다음 단계 함께 진행
  → DB 조회 횟수와 요청별 완료 시간 측정
```

기본 구현에서는 세 번의 실행 모두 **DB 조회가 100번** 발생했다. 모든 요청이 비어 있는 캐시를 확인하고 각자 조회를 시작했기 때문이다.

실제 트래픽에서 동시 요청 수와 DB 조회 횟수가 항상 같지는 않다. 늦게 도착한 요청은 먼저 채워진 캐시를 읽을 수 있다. 이번 실험은 저장 전에 miss가 겹치는 순서를 고정해 재현한 것이다.

## 진행 중인 조회 결과를 함께 기다리기

같은 키를 조회하는 작업이 이미 있다면, 새 요청은 그 작업의 결과를 기다리도록 바꿔보자. 이를 <strong>요청 합치기(Request Coalescing)</strong>라고 한다.

Node.js에서는 진행 중인 조회 작업의 Promise를 키별로 `Map`에 보관해 결과를 공유할 수 있다.

![같은 상품의 중복 조회와 요청 합치기 비교. 위에서는 요청 A, B, C가 같은 DB에 각각 조회를 보낸다. 아래에서는 세 요청이 진행 중인 조회의 Promise를 공유해 DB 조회가 한 번만 실행된다. 하나의 애플리케이션 프로세스를 기준으로 한 흐름이다.](/static/images/redis-cache-stampede/request-coalescing-flow-v2.png)

```javascript
const inFlight = new Map()

async function getProduct(productId) {
  const key = `product:${productId}`
  const cached = await redis.get(key)

  if (cached !== null) {
    return JSON.parse(cached)
  }

  const existing = inFlight.get(key)
  if (existing) {
    return existing
  }

  const loading = (async () => {
    const cachedAgain = await redis.get(key)
    if (cachedAgain !== null) {
      return JSON.parse(cachedAgain)
    }

    const product = await db.selectProduct(productId)
    await redis.set(key, JSON.stringify(product), { EX: 60 })
    return product
  })()

  inFlight.set(key, loading)

  try {
    return await loading
  } finally {
    inFlight.delete(key)
  }
}
```

첫 요청이 조회 작업을 만들고 `inFlight`에 저장한다. 같은 키의 다른 요청은 이 Promise를 반환받아 결과를 기다린다. 이 코드에서 진행 중인 작업을 확인하고 등록하는 두 단계 사이에는 `await`가 없다.

캐시를 한 번 더 읽는 이유도 있다. 첫 miss를 확인한 요청이 늦게 진행되는 동안 앞선 작업이 완료됐을 수 있다. 그때 이미 채워진 캐시를 확인하면 DB를 다시 조회할 필요가 없다.

같은 조건으로 실행하자 DB 조회는 세 번 모두 1번으로 줄었다. 요청은 100개였지만 캐시를 채우는 작업은 하나였다.

조회가 실패했을 때도 확인했다. 기다리던 요청들이 같은 실패를 전달받고, `finally`에서 작업이 제거된 뒤 다음 요청은 새 조회를 시작할 수 있었다. 실제 코드에서는 DB 타임아웃도 설정해야 한다. 진행 중인 작업이 끝나지 않으면 해당 키의 요청이 계속 기다리기 때문이다.

이 `Map`은 하나의 프로세스 안에서만 공유된다. 서버나 Node.js 프로세스가 여러 개라면 각각 조회 작업을 만들 수 있다. Redis를 함께 사용한다고 해서 애플리케이션 메모리의 `Map`까지 공유되는 것은 아니다. 서버 사이의 갱신도 합쳐야 한다면 분산 락 같은 별도의 조정 방법을 검토해야 한다.

## 캐시가 만료되기 전에 갱신하기

요청 합치기를 적용한 뒤에도 결과를 받기까지 약 100ms의 대기가 남았다. 같은 DB 조회가 끝나기를 함께 기다렸기 때문이다.

```text
A: cache miss → DB 조회
B: cache miss → A의 조회 결과 대기
C: cache miss → A의 조회 결과 대기
```

만료 직후의 대기까지 줄이려면 캐시가 사라지기 전에 갱신을 시작할 수 있다. 이를 **조기 갱신**이라고 한다.

예를 들어 실제 TTL은 60초로 두고, 저장 후 50초부터 갱신을 시도하도록 기준을 나눈다. 캐시에는 데이터와 함께 갱신을 시작할 시각을 저장한다.

```javascript
const entry = {
  data: product,
  refreshAfter: Date.now() + 50_000,
}

await redis.set(key, JSON.stringify(entry), { EX: 60 })
```

50초 이전에는 캐시 값을 반환한다. 50초가 지난 뒤 실제 만료인 60초 전에 요청이 들어오면 기존 값을 반환하면서 백그라운드 갱신을 시작한다. 갱신 결과가 도착하면 캐시를 교체한다.

![조기 갱신의 요청과 백그라운드 작업 순서. 50~60초 사이에 요청을 받은 애플리케이션이 Redis에서 기존 값을 읽고 DB 갱신 조회를 시작한다. DB 조회가 끝나기 전에 기존 값으로 응답하고, 이후 새 값을 Redis에 저장하면서 TTL을 다시 설정한다. 아래에는 갱신하지 못한 채 60초가 지나면 다음 요청이 DB 조회 결과를 기다리는 별도 경로를 표시했다.](/static/images/redis-cache-stampede/early-refresh-sequence-v2.png)

그림의 50초와 60초는 동작을 설명하기 위한 예시다. 아래 실험에서는 갱신 기준을 50ms, 실제 TTL을 1초로 설정했다.

갱신을 시작할 기준을 soft TTL, 기존 값을 사용할 수 있는 마지막 기준을 hard TTL로 [나누는 방식](https://aws.amazon.com/builders-library/caching-challenges-and-strategies/)이다.

갱신 구간에 들어온 요청이 모두 백그라운드 작업을 시작하면 중복 조회가 다시 생긴다. 이번 구현에서는 갱신 작업도 같은 키의 Promise를 공유하게 했다.

상품 가격 10,000원이 캐시에 남아 있는 동안 DB 값을 12,000원으로 두고, 갱신 구간에 요청 100개를 겹쳐 실행했다. 이 실험에서는 hard TTL 전에 시작된 백그라운드 갱신 작업을 합쳤다.

이 요청들은 모두 캐시의 10,000원을 반환받았다. 백그라운드 DB 조회는 한 번 실행됐고, 조회가 끝난 뒤 캐시는 12,000원으로 바뀌었다.

## 세 방법의 결과 비교

아래 시간은 조회 함수를 호출한 뒤 결과를 받을 때까지 걸린 시간이다. p50은 호출의 50%가, p95는 95%가 이 시간 안에 완료됐다는 뜻이다. 각 방법을 세 번 실행하고, 실행별 p50과 p95의 중앙값을 표에 적었다.

시간에는 첫 캐시 조회와 실행 순서를 맞추는 대기도 포함된다. 조기 갱신의 DB 조회 횟수는 백그라운드 작업이 끝난 뒤 집계했다.

| 방법                        | DB 조회 횟수 | 완료 시간 p50 | 완료 시간 p95 | 요청이 받은 값  |
| --------------------------- | ------------ | ------------- | ------------- | --------------- |
| 기본 Cache-aside            | 100번        | 107.85ms      | 108.58ms      | DB의 새 값      |
| 요청 합치기                 | 1번          | 103.78ms      | 104.25ms      | DB의 새 값      |
| 조기 갱신(갱신 요청 합치기) | 1번          | 1.32ms        | 1.54ms        | 갱신 전 캐시 값 |

요청 합치기는 DB 조회 횟수를 줄였다. 요청들은 여전히 DB 조회가 끝나기를 약 100ms 기다렸다.

조기 갱신은 DB 조회를 기다리지 않아 빨랐지만, 요청이 받은 가격은 여전히 10,000원이었다. 새 가격인 12,000원이 필요한 요청이라면 이 결과를 그대로 사용할 수 없다.

이 수치는 로컬 재현 실험의 결과다. 로컬 Redis와의 TCP 통신은 포함되지만, HTTP 왕복 시간이나 별도 DB 서버의 네트워크 지연, DB 커넥션 풀 대기는 포함되지 않는다. 여러 서버의 트래픽도 재현하지 않았다. 서비스의 응답 시간이 얼마나 줄어들지는 해당 환경에서 따로 측정해야 한다.

조기 갱신을 적용하기 전에는 이전 값을 어디까지 허용할지 정해야 한다. 상품 상세 화면에서 잠깐 이전 정보가 보이는 것과, 주문을 확정할 때 이전 가격을 사용하는 것은 요구사항이 다르다.

갱신 구간에 요청이 없거나 갱신이 실패하면 실제 만료에 도달할 수도 있다. 이때 사용할 cache miss 처리도 남겨둬야 한다.

만료 후에도 요청이 몰릴 수 있으므로, 이 경로의 요청 합치기는 별도로 적용하고 확인해야 한다. 백그라운드 실패는 기록하고, hard TTL 이후에는 이전 값을 계속 반환하지 않도록 해야 한다.

## TTL을 흩어주면 인기 키 하나도 괜찮을까?

여러 캐시 키를 비슷한 시점에 저장하고 같은 TTL을 주면, 만료도 한꺼번에 몰릴 수 있다. TTL에 무작위 값을 더하는 [TTL Jitter](https://redis.io/blog/how-to-tame-the-thundering-herd-problem/)는 이 만료 시점을 흩어준다.

```javascript
const ttl = 55 + Math.floor(Math.random() * 11)

await redis.set(key, JSON.stringify(product), { EX: ttl })
```

이 코드는 키를 저장할 때 55~65초 사이의 TTL을 선택한다. 서비스에서 허용하는 데이터 지연이 최대 60초라면 상한도 그 기준에 맞춰야 한다.

이번에는 서로 다른 키 20개로 별도 실험을 했다. 고정 TTL은 400ms, 분산 TTL은 재현 가능하도록 키마다 400~800ms의 서로 다른 값을 줬다. 키들을 한 배치로 조회하고, miss가 나면 DB를 읽어 60초 TTL로 다시 채웠다. 한 배치의 조회가 끝나면 20ms 뒤 다음 배치를 실행했다.

조회가 몰리는 정도는 실험 시작부터 100ms씩 나눈 고정 구간별로 집계했다. 아래 최대치는 이 구간들 중 DB 조회가 가장 많이 시작된 구간의 횟수다.

| 만료 설정  | 전체 DB 조회 횟수 | 100ms 구간의 최대 DB 조회 시작 횟수 |
| ---------- | ----------------- | ----------------------------------- |
| 같은 TTL   | 20번              | 20번                                |
| 분산한 TTL | 20번              | 6번                                 |

전체 조회 횟수는 같았다. 한 구간에 몰리는 조회가 줄어든 것이다. 이 실험은 한 번의 실행 결과이며, 만료 간격과 요청 패턴을 바꾸면 최대치는 달라질 수 있다.

다만 인기 상품 하나의 TTL을 60초에서 63초로 바꿔도, 63초 뒤 그 키에 요청이 겹치는 상황은 남는다. **TTL 분산은 같은 키의 조회 작업을 합쳐주지 않는다.**

인기 키 하나의 중복 조회에는 요청 합치기를 적용하고, 여러 키의 만료가 겹친다면 TTL 분산을 함께 검토할 수 있다.

## 만료 직후의 요청도 확인하기

캐시가 채워져 있고 갱신 시점도 되지 않았다면 세 구현 모두 캐시 값만 반환한다. 차이는 캐시가 비거나 갱신할 시점이 됐을 때 나타난다.

중복 조회를 줄이는 것과 최신 값을 보장하는 것은 별개다. 조회와 수정이 겹치는 상황의 캐시 무효화도 따로 검토해야 한다.

캐시 만료 직후에 요청을 겹쳐 보내보자. DB 조회가 몇 번 실행되는지, 얼마나 기다리는지, 어떤 값을 받는지 함께 확인하자. 조기 갱신을 쓴다면 갱신이 실패해 실제 만료에 도달했을 때도 같은 항목을 확인해야 한다.
