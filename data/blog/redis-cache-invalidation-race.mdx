상품 정보를 Redis에 캐싱하고 있다고 해보자. 조회 요청이 들어오면 캐시를 확인하고, 값이 없으면 DB에서 가져와 저장한다.

상품 정보를 수정할 때는 DB를 업데이트한 뒤 캐시를 삭제한다. 다음 조회에서 변경된 값을 가져오도록 하기 위해서다.

흐름만 보면 문제가 없어 보인다. DB에는 새 값이 있고, 이전 값을 담고 있던 캐시도 지웠다.

그런데 조회 요청과 수정 요청이 겹치면, **삭제한 캐시에 이전 값이 다시 들어갈 수 있다.** 캐시 삭제 로그까지 정상으로 남았는데도 말이다.

## 익숙한 캐싱 코드에서 시작하기

이런 조회 방식을 [Cache-aside](https://redis.io/docs/latest/develop/use-cases/cache-aside/)라고 한다. 애플리케이션이 먼저 캐시를 확인하고, 값이 없으면 DB에서 조회해 캐시에 저장한다.

데이터가 수정되면 DB 변경을 커밋한 뒤 기존 캐시를 삭제한다. 다음 조회에서 변경된 값을 가져와 캐시를 다시 채우도록 하기 위해서다.

이 흐름을 Node.js 코드로 옮겨보자. Redis 호출은 [node-redis](https://redis.io/docs/latest/develop/clients/nodejs/)의 형태를 따르고, DB 접근 부분은 흐름이 잘 보이도록 간단히 적었다. Redis 클라이언트는 이미 연결돼 있다고 가정한다.

```javascript
async function getPrice(productId) {
  const key = `product:${productId}:price`
  const cached = await redis.get(key)
  if (cached !== null) {
    return Number(cached)
  }

  const price = await db.selectPrice(productId)
  await redis.set(key, String(price), { EX: 60 })
  return price
}

async function updatePrice(productId, price) {
  await db.updatePriceAndCommit(productId, price)
  await redis.del(`product:${productId}:price`)
}
```

`updatePriceAndCommit`은 DB 커밋이 끝나야 완료되는 함수다. 이번에는 DB 커밋과 Redis 명령이 모두 정상적으로 처리된다고 가정한다. Redis 복제 지연도 없다. 이 조건에서도 요청 순서가 엇갈리면 문제가 생긴다.

Node.js에서도 이 흐름은 겹칠 수 있다. 한 요청이 `await`로 DB나 Redis의 응답을 기다리는 동안 다른 요청이 진행할 수 있기 때문이다. 한 요청 안에서 순서대로 기다린다고 해서 다른 요청의 실행까지 막는 것은 아니다.

## 캐시를 지운 뒤, 누가 다시 저장했을까?

상품 가격을 10,000원에서 12,000원으로 변경하는 상황을 생각해보자. 상품 캐시는 만료돼 비어 있고, 조회 요청 A와 수정 요청 B가 거의 동시에 들어온다.

A가 먼저 캐시를 확인한다. 값이 없으니 DB에서 10,000원을 읽는다. 아직 B가 가격을 바꾸기 전이다.

여기서 A가 캐시에 저장하기까지 잠깐 늦어진다고 해보자. 그 사이 B가 DB 가격을 12,000원으로 바꾸고 커밋한 뒤, 캐시를 삭제한다.

B가 처리를 끝내고 나서야 A가 다시 진행한다. A가 들고 있는 조회 결과는 여전히 10,000원이다. 이 값을 그대로 캐시에 저장한다.

![캐시 삭제 이후 오래된 값이 다시 저장되는 순서. 아래로 갈수록 시간이 흐른다. 조회 요청 A는 캐시 miss를 확인하고 DB에서 10,000원을 읽은 뒤 저장 직전에 대기한다. 수정 요청 B가 DB를 12,000원으로 바꾸고 커밋한 뒤 DEL을 실행한다. 캐시에 키가 없어 반환값은 0이다. 이후 A가 이전 값 10,000원을 캐시에 저장한다. 최종 상태는 DB 12,000원, Redis 10,000원이며 만료 전 다음 조회는 캐시의 이전 값을 받는다.](/static/images/redis-cache-invalidation-race/stale-repopulation-v3.png)

이후 요청 C는 캐시에서 10,000원을 찾는다. Cache hit이므로 DB를 확인하지 않고 그대로 반환한다.

**B의 삭제가 끝난 뒤 A의 저장이 실행됐다.** DB가 바뀌었다고 해서 A가 이미 읽어둔 값까지 바뀌는 것은 아니다.

조회 코드와 수정 코드를 따로 보면 각각 자연스럽다. 두 요청의 실행 순서를 함께 볼 때 비로소 틈이 드러난다. 이런 상황을 경쟁 상태, 또는 race condition이라고 한다.

## 실행 순서를 고정해서 재현하기

동시 요청을 많이 보내도 이 순서가 매번 나오지는 않는다. 재현하려면 A가 DB를 읽은 직후 멈추고, B의 처리가 끝난 뒤 다시 진행하도록 만들면 된다.

실험에서는 Redis 7.0.8과 Node.js 22.22.3을 사용했다. DB는 SQLite로 두고, 조회와 수정에 각각 별도 연결을 사용했다. A는 조회 연결을 닫은 뒤 대기하고, B는 수정을 커밋한 뒤 캐시를 삭제한다.

실행 순서는 Promise 두 개로 맞췄다. 하나는 A가 DB를 읽었다는 신호이고, 다른 하나는 B의 수정과 캐시 삭제가 끝났다는 신호다. 아래의 `createSignal`은 Promise와 그 Promise를 완료하는 `resolve` 함수를 함께 반환하는 작은 도우미다.

```javascript
const productId = 1
const key = `product:${productId}:price`
const dbRead = createSignal()
const updateDone = createSignal()

async function requestA() {
  const oldPrice = await db.selectPrice(productId)
  dbRead.resolve() // B에게 DB 조회 완료를 알린다
  await updateDone.promise // B의 수정과 삭제가 끝날 때까지 대기한다
  await redis.set(key, String(oldPrice), { EX: 2 })
}

async function requestB() {
  await dbRead.promise
  await db.updatePriceAndCommit(productId, 12000)
  await redis.del(key)
  updateDone.resolve() // A의 캐시 저장을 진행시킨다
}

await Promise.all([requestA(), requestB()])
```

두 함수를 함께 시작하고, Promise 신호로 필요한 지점에서 기다리게 한다. 위 코드는 요청이 엇갈리는 부분만 보여주기 위해 캐시 조회 단계는 생략했다. 캐시가 만료되기까지의 시간인 TTL은 2초로 설정해, 만료 후 동작도 빨리 확인할 수 있도록 했다.

순차 호출과 요청이 겹친 경우를 비교하면 다음과 같은 결과가 나온다.

```text
[순차 실행]
C: cache miss, 응답 = 12000

[요청이 겹친 실행]
A: cache miss
A: DB 조회 = 10000, 캐시 저장 직전 대기
B: DB 수정 및 커밋 = 12000
B: DEL 반환값 = 0 (현재 키 없음)
A: 이전 값 10000을 캐시에 저장 (TTL 2초)
C: cache hit, 응답 = 10000 / DB = 12000
TTL 만료 후: cache miss, 응답 = 12000
```

순차 실행에서는 A의 저장이 끝난 뒤 B가 수정하고 캐시를 지운다. 다음 조회는 DB의 12,000원을 가져온다.

요청이 겹친 실행에서는 B의 삭제 뒤에 A의 저장이 따라온다. DB는 12,000원이지만 다음 조회는 캐시의 10,000원을 받는다.

여기서 `DEL`의 반환값이 0인 점도 눈여겨볼 만하다. [DEL](https://redis.io/docs/latest/commands/del/)은 실제로 삭제한 키의 수를 반환한다. 삭제 시점에는 캐시가 비어 있으니 0이 정상이다. 이 명령은 미래의 `SET`까지 막아주지는 않는다.

## Redis 명령이 원자적이어도 이 틈은 남는다

이 실험에서 Redis가 처리한 순서는 단순하다.

```text
B: DEL product:1:price
A: SET product:1:price 10000 EX 2
```

각 명령은 정상적으로 처리됐다. `DEL` 뒤에 `SET`이 왔으니 마지막으로 저장한 값이 남는다.

우리가 하나의 작업처럼 생각했던 것은 DB 조회, DB 수정, 캐시 삭제, 캐시 저장까지 이어지는 애플리케이션의 흐름이다. 개별 Redis 명령의 원자성만으로는 이 전체 순서를 묶을 수 없다.

DB 수정 코드를 트랜잭션으로 감싸는 것만으로도 해결되지 않는다. 이번 실험은 B가 커밋한 뒤 캐시를 지우도록 했는데도 재현됐다. DB 트랜잭션이 A의 Redis 저장까지 제어하지는 않기 때문이다.

Redis의 [MULTI/EXEC](https://redis.io/docs/latest/develop/using-commands/transactions/)이나 Lua도 Redis 안의 작업을 묶는 수단이다. DB와 Redis를 오가는 흐름까지 자동으로 하나의 트랜잭션으로 만들어주지는 않는다.

## TTL이 있으면 괜찮을까?

TTL은 도움이 된다. 실험에서도 2초가 지나 키가 만료된 뒤에는 DB의 12,000원을 다시 가져왔다.

다만 그동안 캐시를 읽은 요청은 10,000원을 받는다. TTL이 제한하는 것은 오래된 값이 캐시에 머무는 시간이다. 오래된 값이 다시 저장되는 상황 자체를 막지는 않는다.

![TTL은 이전 값을 저장한 시점부터 흐른다. 시간축에서 B의 DB 커밋과 A의 SET 사이를 저장 지연으로, A의 SET부터 키 만료까지를 TTL 2초로 구분한다. SET 이후 만료 전까지 캐시 hit은 10,000원을 반환한다. 만료 후 다음 조회는 DB에서 12,000원을 읽는다. 조회 시 TTL을 연장하거나 같은 이전 값을 추가로 저장하지 않는 경우다.](/static/images/redis-cache-invalidation-race/ttl-window-v3.png)

TTL이 시작되는 시점도 중요하다. `SET ... EX 2`의 2초는 B가 DB를 수정한 시점이 아니라, A가 캐시에 저장한 시점부터 흐른다. A가 저장하기까지 오래 지연됐다면 그 지연에 TTL까지 더해진다.

이 설명은 조회할 때 TTL을 연장하지 않고, 같은 오래된 값을 또 저장하는 요청도 없는 경우를 기준으로 한다. 캐시 저장 순간부터의 만료 시간과 DB 수정 이후 데이터가 오래된 채 보이는 시간을 같은 것으로 생각하면 안 된다.

## 캐시를 먼저 지우면 해결될까?

순서를 바꿔 캐시를 삭제한 뒤 DB를 수정하면 어떨까? 이번에는 DB 수정이 끝나기 전의 조회가 문제가 된다.

```text
B: 캐시 삭제
A: cache miss → 아직 수정 전인 DB에서 10000 조회
A: 캐시에 10000 저장
B: DB를 12000으로 수정하고 커밋
```

이 순서에서도 캐시에 이전 값이 남는다. 그래서 두 동작의 순서를 뒤집는 것만으로는 충분하지 않다. DB를 먼저 바꾼 뒤 캐시를 지우는 기본 흐름을 유지하면서, 남아 있는 경쟁 상태를 어떻게 다룰지 결정해야 한다.

잠깐 기다렸다가 캐시를 한 번 더 삭제하는 방법도 떠올릴 수 있다. 이때 추가 삭제가 A의 저장보다 뒤에 실행되면 해당 값을 지울 수 있다. 하지만 A가 예상보다 더 늦게 끝나면 같은 틈이 다시 생긴다. 고정된 대기 시간만으로 모든 실행 순서를 보장하기는 어렵다.

## 우리 서비스는 어느 정도의 지연을 허용할까?

먼저 정할 것은 데이터가 얼마나 늦어도 되는지다. 같은 상품 데이터라도 화면에 보여주는 정보와 주문을 처리할 때 쓰는 정보의 요구사항은 다를 수 있다.

| 사용하는 곳             | 먼저 정할 기준                                     | 선택 방향                                                              |
| ----------------------- | -------------------------------------------------- | ---------------------------------------------------------------------- |
| 조회 통계, 인기 글 목록 | 몇 초나 몇 분의 갱신 지연을 허용할 수 있는가       | DB 수정 후 무효화와 TTL로 단순하게 운영할 수 있다                      |
| 상품 상세 화면          | 이전 정보가 보일 때 사용자에게 어떤 영향을 주는가  | 허용 범위에 맞춰 TTL을 정하고, 필요하면 재저장을 제어한다              |
| 주문 확정, 재고 차감    | 처리 시점의 가격과 재고를 어떤 기준으로 확정하는가 | 캐시 값만으로 결정하지 않고 DB의 트랜잭션이나 조건부 갱신으로 확인한다 |

잠깐의 지연을 허용할 수 있다면, 이 경쟁 상태를 알고 TTL로 관리하는 선택도 가능하다. 허용할 수 없다면 늦게 돌아온 조회 결과가 캐시를 덮어쓰지 못하게 하는 추가 설계가 필요하다.

예를 들어 수정 여부를 구분할 수 있는 버전 번호를 두고, 수정 전 버전의 조회 결과는 저장하지 않는 방법을 검토할 수 있다.

이때 단순히 버전을 확인한 뒤 별도로 `SET`하는 코드로 끝내면, 확인과 저장 사이에 다시 수정이 끼어들 수 있다. Redis 쪽 확인과 저장을 원자적으로 묶는 것뿐 아니라, DB 커밋과 무효화 정보 갱신 사이의 실패도 함께 다뤄야 한다. 버전 필드를 추가하는 것만으로 해결됐다고 보기 어려운 이유다.

중요한 업무 판단을 DB에서 처리하는 방법에도 동시성 제어는 필요하다. 재고를 읽고 나중에 별도로 차감하면 그 사이 다른 주문이 들어올 수 있다. 확인과 변경을 같은 트랜잭션의 적절한 잠금이나 조건부 `UPDATE`로 묶어야 한다.

## 캐시 삭제 로그 다음에 확인할 것

이전 값이 계속 조회된다면, 캐시 삭제가 호출됐는지만 확인해서는 원인을 놓칠 수 있다. 같은 키에 대해 **삭제 이후 누가 어떤 값을 저장했는지**까지 이어서 봐야 한다.

요청 ID와 상품 ID를 기준으로 DB 조회, DB 커밋, 캐시 삭제, 캐시 저장의 순서를 맞춰보자. 순차 호출로 확인했다면, 이번 실험처럼 조회와 수정이 겹치는 조건도 만들어볼 필요가 있다.
