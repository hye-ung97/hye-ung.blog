## 들어가며

결론부터 말하면, 락을 획득하지 못한 요청에는 **409 Conflict**가 가장 적절합니다. 하지만 실무에서는 408이나 503을 주는 경우도 적지 않습니다. 이 글에서는 각 코드가 왜 맞지 않는지, 그리고 409를 어떻게 써야 하는지 정리합니다.

상황은 이렇습니다. 포인트 차감 API에 분산 락을 걸었습니다. 사용자가 버튼을 빠르게 두 번 눌러, 같은 요청이 거의 동시에 들어옵니다. 첫 번째 요청이 락을 잡고 처리 중이라, 두 번째 요청은 락을 얻지 못합니다.

이때 두 번째 요청의 처리 방식은 크게 두 가지입니다.

- **대기 후 실패**: 일정 시간 락을 기다리다가 끝내 얻지 못하고 실패합니다.
- **즉시 실패(fail-fast)**: 기다리지 않고 바로 실패를 알립니다.

![요청 B는 기다리든 바로 실패하든 409를 받는다. 따닥 클릭으로 같은 요청이 거의 동시에 들어온 상황이다. 첫 번째 클릭인 요청 A는 락을 획득해 포인트 차감을 처리하고, 처리가 끝나면 락을 해제한다. 요청 A가 락을 잡고 있는 구간에 요청 B가 도착한다. 대기 후 실패하는 요청 B는 락이 풀리길 기다리다가 락이 해제되기 전에 대기 시간을 초과해 409 · LOCK_TIMEOUT을 받는다. 즉시 실패(fail-fast)하는 요청 B는 락 획득 시도를 즉시 거절당해 409 · RESOURCE_LOCKED를 받는다.](/static/images/lock-failure-status-code/lock-contention.png)

요청 A가 락을 잡고 있는 동안 도착한 요청 B는, 기다리든 바로 실패하든 결국 409를 받습니다.

두 경우 모두 "타임아웃이니까 408", "서버가 바쁘니까 503"이라는 답이 먼저 떠오르기 쉽습니다. 하나씩 살펴보겠습니다.

## 408 Request Timeout이 아닌 이유

408은 이름에 "Timeout"이 들어 있어서, 락 대기 타임아웃에 딱 맞아 보입니다. 하지만 408의 의미는 **서버가 클라이언트의 요청 전송을 기다리다 시간이 초과됐다**는 것입니다. 예를 들어 클라이언트가 연결만 열어두고 요청 본문을 보내지 않는 경우입니다.

즉 408은 "네가 너무 늦게 보냈다"는 뜻이고, 락 대기는 "서버 쪽 자원이 사용 중이다"는 뜻입니다. 타임아웃의 방향이 정반대입니다.

또 일부 브라우저나 HTTP 클라이언트는 408을 받으면 연결 문제로 보고 자동으로 재전송하기도 합니다. 의도하지 않은 재시도가 일어나면 오히려 락 경합이 더 심해질 수 있습니다.

## 503 Service Unavailable이 아닌 이유

503은 "서버가 일시적으로 요청을 처리할 수 없다"는 뜻입니다. 과부하나 점검처럼 **서버 전체의 상태**를 알리는 코드입니다. 락 경합은 서버는 멀쩡하고, 특정 자원 하나만 잠긴 상황입니다.

더 큰 문제는 5xx가 "서버 잘못"을 뜻한다는 점입니다. 5xx를 반환하면 이런 일이 생길 수 있습니다.

- 에러율 모니터링에 잡혀 장애 알람이 울립니다.
- 호출하는 서비스의 서킷 브레이커가 열려, 정상적인 다른 요청까지 차단될 수 있습니다.
- 로드밸런서나 게이트웨이가 해당 서버를 비정상으로 판단할 수 있습니다.

따닥 클릭으로 생기는 락 경합은 장애가 아니라 **예상 가능한 정상 상황**입니다. 그러니 5xx가 아니라 4xx로 응답해야 합니다.

같은 이유로 504 Gateway Timeout도 맞지 않습니다. 504는 게이트웨이나 프록시가 뒤쪽 서버의 응답을 받지 못했을 때 쓰는 코드입니다.

## 정답은 409 Conflict

409는 **요청이 대상 자원의 현재 상태와 충돌한다**는 뜻입니다. 다른 작업이 자원을 점유하고 있어 지금은 처리할 수 없는 상황에 정확히 맞습니다. 4xx라서 장애 알람도 울리지 않습니다.

대기 후 실패와 즉시 실패에 모두 409를 쓰면 됩니다. 두 상황의 차이는 상태 코드가 아니라 **응답 본문의 에러 코드**로 구분합니다. 재시도 시점은 `Retry-After` 헤더로 힌트를 줄 수 있습니다.

```http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json
Retry-After: 1

{
  "type": "https://api.example.com/errors/resource-locked",
  "title": "Resource is locked",
  "status": 409,
  "code": "RESOURCE_LOCKED",
  "detail": "다른 요청이 이 주문을 처리 중입니다. 잠시 후 다시 시도해 주세요."
}
```

에러 코드는 예를 들어 이렇게 나눌 수 있습니다. 클라이언트는 셋 다 "잠시 후 그대로 재시도하면 되는 충돌"로 처리하면 됩니다.

| 상황                          | 에러 코드             |
| ----------------------------- | --------------------- |
| 락을 기다리다 타임아웃        | `LOCK_TIMEOUT`        |
| 락을 즉시 얻지 못함           | `RESOURCE_LOCKED`     |
| 같은 멱등 키의 요청이 처리 중 | `REQUEST_IN_PROGRESS` |

### 423 Locked는 어떨까?

이름만 보면 423 Locked가 더 정확해 보입니다. 하지만 423은 WebDAV(RFC 4918)에서 명시적인 `LOCK` 메서드를 위해 정의한 코드입니다. 일반 HTTP 클라이언트나 라이브러리는 423을 특별히 처리하지 않습니다.

팀 안에서 합의하고 문서에 명확히 적는다면 423을 써도 됩니다. 다만 대부분의 공개 API는 더 널리 알려진 409를 씁니다.

### 412와 헷갈리지 말 것

412 Precondition Failed는 낙관적 락에서 씁니다. `If-Match` 헤더로 보낸 버전(ETag)이 현재 버전과 다를 때 반환합니다. "락이 잡혀 있다"가 아니라 "네가 본 버전이 낡았다"는 뜻이라, 비관적 락 상황과는 다릅니다.

## 한 걸음 더: 락은 중복을 막아주지 않는다

락은 요청을 줄 세워 순서대로 실행시킬 뿐, 중복 실행을 막지는 않습니다. 대기 방식에서 첫 요청이 금방 끝나면 이런 일이 생깁니다.

1. 요청 A가 락을 잡고 포인트를 차감합니다.
2. 요청 B는 락을 기다립니다.
3. A가 끝나고 락을 해제합니다.
4. B가 락을 얻어 포인트를 **한 번 더** 차감합니다.

그래서 락을 얻은 뒤에는 "이미 처리된 요청인지"를 반드시 다시 확인해야 합니다. 이 확인을 체계적으로 하는 방법이 <strong>멱등 키(Idempotency-Key)</strong>입니다. 클라이언트가 요청마다 고유한 키를 헤더에 담고, 서버는 키별로 처리 상태와 결과를 저장합니다.

```http
POST /points/deduct
Idempotency-Key: "8e03978e-40d5-43e8-bc93-6894a57f9324"
```

IETF의 [Idempotency-Key 헤더 초안](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header)은 같은 키로 들어온 요청을 이렇게 다룹니다. 원래 요청이 아직 처리 중이면 409로 충돌을 알립니다. 이미 끝났다면 실패가 아니라 **첫 요청의 결과를 그대로** 돌려줍니다.

같은 키에 다른 본문을 보내면 422로, 필수인 키가 빠지면 400으로 거절합니다. 아직 표준으로 확정되지 않은 초안이지만, 결제 API들이 이미 비슷한 방식을 씁니다.

### 기다릴까, 바로 실패할까?

**같은 사용자의 중복 요청**(따닥)은 기다려 봐야 결국 중복이므로 즉시 실패가 낫습니다. 반면 **여러 사용자가 같은 자원을 두고 경쟁**하는 경우(재고 차감 등)는 수백 ms 정도 짧게 대기하는 편이 사용자 경험에 유리합니다. Redisson의 `tryLock(waitTime, leaseTime)`처럼 대기 시간을 받는 락을 쓰면 두 전략을 같은 코드로 조절할 수 있습니다.

## 마치며

처음 질문으로 돌아가 보겠습니다. 버튼을 두 번 눌러 락을 못 잡은 요청에는 무엇을 줘야 할까요? 408도, 503도 아닌 **409 Conflict**입니다.

408은 타임아웃의 방향이 반대이고, 503은 정상적인 경합을 서버 장애로 만들어 버립니다. 409는 "지금 이 자원은 다른 작업과 충돌 중이니, 잠시 후 그대로 다시 보내라"는 뜻을 정확히 전달합니다.

글에서 다룬 상황별 응답을 한눈에 보면 다음과 같습니다.

| 상황                                 | 응답                               | 이유                               |
| ------------------------------------ | ---------------------------------- | ---------------------------------- |
| 락 대기 중 타임아웃                  | 409 + `LOCK_TIMEOUT`               | 자원 점유로 인한 충돌              |
| 락 즉시 획득 실패                    | 409 + `RESOURCE_LOCKED` (또는 423) | 자원 점유로 인한 충돌              |
| 같은 멱등 키 요청이 처리 중          | 409 + `REQUEST_IN_PROGRESS`        | 그대로 재시도 가능한 충돌          |
| 같은 멱등 키, 원 요청 완료 후 재시도 | 첫 요청의 응답 그대로              | 멱등성 보장                        |
| 같은 멱등 키, 다른 본문              | 422                                | 키 오용                            |
| 낙관적 락 버전 불일치                | 412                                | `If-Match` 전제 조건 실패          |
| 쓰면 안 되는 코드                    | 408, 503, 504                      | 방향이 반대이거나 서버 장애를 뜻함 |

상태 코드를 고를 때 "무슨 일이 있었는지"만 보면 408이나 503처럼 그럴듯한 오답에 빠지기 쉽습니다. 대신 <strong>"누구의 문제이고, 클라이언트가 무엇을 해야 하는지"</strong>를 기준으로 삼아 보세요. 이 기준 하나면 처음 보는 에러 상황에서도 알맞은 코드를 고를 수 있습니다.

마지막으로, 락은 순서를 정해줄 뿐 중복을 막아주는 것은 멱등성이라는 점을 기억해 주세요. 올바른 상태 코드를 고르는 것만큼, 같은 요청이 두 번 와도 안전한 API를 만드는 것이 중요합니다.
