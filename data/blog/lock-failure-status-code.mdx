## 들어가며

포인트 차감 API에 분산 락을 걸었습니다. 사용자가 버튼을 빠르게 두 번 누르자 첫 번째 요청이 락을 잡고 처리를 시작했고, 거의 동시에 들어온 두 번째 요청은 락을 얻지 못했습니다.

락 대기 시간이 초과됐으니 408을 반환해야 할까요? 서버가 요청을 처리하지 못했으니 503이 맞을까요? 자원이 잠겨 있으니 423을 써야 할까요?

상태 코드 이름만 보면 모두 그럴듯합니다. 하지만 어떤 코드가 맞는지는 "락 획득에 실패했다"는 결과보다 실패가 어디에서 발생했고, 얼마나 넓은 범위에 영향을 주는지를 봐야 판단할 수 있습니다.

## 코드 이름보다 실패한 위치부터 보기

상태 코드를 고르기 전에 세 가지를 확인해 봅니다.

1. 서버가 클라이언트의 요청을 끝까지 받았는가?
2. 서버 전체가 요청을 처리할 수 없는 상태인가?
3. 특정 자원의 현재 상태 때문에 이 요청만 처리할 수 없는가?

지금 상황에서 요청 B는 서버에 정상적으로 도착했습니다. 서버와 다른 API도 동작하고 있고, 특정 포인트 계정만 요청 A에 의해 처리 중입니다.

즉 클라이언트의 전송이 늦어진 것도, 서버 전체가 멈춘 것도 아닙니다. 특정 자원의 현재 상태와 요청 B가 충돌한 상황에 가깝습니다.

## 후보 상태 코드 비교하기

| 코드                    | 의미                                                         | 현재 상황과의 관계                             |
| ----------------------- | ------------------------------------------------------------ | ---------------------------------------------- |
| 408 Request Timeout     | 서버가 완전한 요청 메시지를 받지 못한 채 기다리다 시간 초과  | 요청이 이미 도착했으므로 맞지 않음             |
| 409 Conflict            | 요청이 대상 자원의 현재 상태와 충돌                          | 특정 자원이 다른 요청에 점유된 상황과 잘 맞음  |
| 423 Locked              | 요청의 출발지나 목적지 자원이 잠겨 있음                      | 의미는 직접적이지만 WebDAV에서 정의된 코드     |
| 503 Service Unavailable | 과부하나 점검 등으로 서버가 일시적으로 요청을 처리할 수 없음 | 락 저장소 장애처럼 영향이 서버 전반이라면 가능 |
| 504 Gateway Timeout     | 게이트웨이나 프록시가 상위 서버의 응답을 제때 받지 못함      | 애플리케이션 내부의 락 획득 실패와는 다름      |
| 412 Precondition Failed | 요청 헤더에 담긴 전제 조건이 현재 상태와 맞지 않음           | `If-Match`를 사용한 낙관적 동시성 제어에 적합  |

[RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)은 408을 서버가 완전한 요청 메시지를 받지 못한 경우로, 409를 대상 자원의 현재 상태와 충돌한 경우로 정의합니다. 503과 504도 각각 서버의 일시적인 처리 불가와 게이트웨이의 상위 서버 응답 지연을 가리킵니다.

따라서 이름에 Timeout이 들어간다는 이유만으로 락 대기 시간 초과에 408을 쓰기는 어렵습니다. 반대로 분산 락 저장소가 중단돼 모든 요청을 처리할 수 없다면 503이 더 자연스러울 수 있습니다. 같은 락 실패라도 발생 범위에 따라 답이 달라집니다.

## 이 상황에서는 409가 가장 설명하기 쉽다

이 글의 요청 B는 서버에 정상적으로 도착했습니다. 서버 전체가 멈춘 것도 아니고, 특정 포인트 계정이 요청 A에 의해 처리 중이라 지금은 같은 작업을 진행할 수 없는 상태입니다.

따라서 요청과 대상 자원의 현재 상태가 충돌했다는 의미의 409가 가장 설명하기 쉽습니다.

요청 B가 일정 시간 기다리다 실패했는지, 락을 기다리지 않고 바로 실패했는지는 이 판단을 바꾸지 않습니다. 둘 다 특정 자원을 지금 사용할 수 없다는 충돌이고, 차이는 응답 본문의 에러 코드로 전달할 수 있습니다.

![요청 B가 도착하면 처리 방식에 따라 두 흐름으로 나뉜다. 요청 A가 락을 획득해 포인트 차감을 처리하는 동안 요청 B가 도착한다. 대기 방식의 요청 B는 락이 풀리길 기다리다 시간 초과로 409 LOCK_TIMEOUT을 받고, 즉시 실패 방식의 요청 B는 락 획득을 즉시 거절당해 409 RESOURCE_LOCKED를 받는다.](/static/images/lock-failure-status-code/lock-contention-v3.png)

| 상황                    | 에러 코드         |
| ----------------------- | ----------------- |
| 락을 기다리다 시간 초과 | `LOCK_TIMEOUT`    |
| 락을 즉시 얻지 못함     | `RESOURCE_LOCKED` |

## 상태 코드만큼 응답 본문도 중요하다

409만 반환하면 클라이언트는 충돌의 원인과 다시 시도해도 되는지 알기 어렵습니다. [Problem Details for HTTP APIs](https://www.rfc-editor.org/rfc/rfc9457.html) 형식에 도메인 에러 코드와 재시도 가능 여부를 함께 담을 수 있습니다.

```http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json
Retry-After: 1

{
  "type": "https://api.example.com/errors/resource-locked",
  "title": "Resource is locked",
  "status": 409,
  "code": "RESOURCE_LOCKED",
  "retryable": true,
  "detail": "다른 요청이 이 주문을 처리 중입니다."
}
```

서버가 적절한 재시도 시점을 알고 있다면 `Retry-After`로 기다릴 시간을 제안할 수 있습니다. 다만 모든 HTTP 클라이언트가 409의 `Retry-After`를 자동으로 처리하는 것은 아니므로, 재시도 정책은 API 문서에도 명확히 적어야 합니다.

즉시 실패와 짧게 기다린 뒤 실패하는 방식 중 무엇을 쓸지는 상태 코드와 별개의 정책입니다. 같은 사용자의 중복 요청이라면 즉시 실패가 단순할 수 있고, 여러 사용자가 같은 재고를 두고 경쟁한다면 짧게 기다리는 편이 나을 수도 있습니다.

## 423 Locked도 선택할 수 있을까?

[423 Locked](https://www.rfc-editor.org/rfc/rfc4918.html#section-11.3)는 WebDAV에서 출발지나 목적지 자원이 잠긴 상태를 표현하기 위해 정의됐습니다. 이름만 보면 분산 락 획득 실패를 가장 직접적으로 설명합니다.

팀의 API 규칙에서 잠긴 자원을 423으로 표현하고 클라이언트도 이를 이해한다면 사용할 수 있습니다. 반면 이미 자원 상태 충돌을 409로 처리하고 있거나 범용적인 오류 분류를 유지하려면 409가 더 일관된 선택일 수 있습니다.

중요한 것은 409와 423 중 하나가 언제나 정답이라는 결론이 아닙니다. API 전체에서 같은 종류의 충돌을 일관되게 표현하고, 응답 본문으로 클라이언트의 다음 행동을 알려주는 것이 더 중요합니다.

## 낙관적 동시성 제어라면 412

락을 먼저 획득하는 대신 ETag와 `If-Match`로 버전을 비교하는 API라면 상황이 다릅니다.

클라이언트가 보낸 `If-Match` 조건이 현재 버전과 맞지 않을 때는 412 Precondition Failed가 해당 실패를 직접 표현합니다. "다른 요청이 자원을 점유하고 있다"가 아니라 "네가 본 자원 버전이 더 이상 최신이 아니다"라는 뜻입니다.

이 경우 클라이언트는 최신 자원을 다시 읽고 변경 내용을 반영한 뒤 요청을 다시 만들어야 합니다. 잠시 기다렸다가 같은 요청을 그대로 보내는 락 경합과 복구 방법도 다릅니다.

## 락은 중복 실행을 막아주지 않는다

409를 선택했다고 중복 실행 문제가 해결되는 것은 아닙니다. 락은 동시에 실행되는 요청을 줄 세울 뿐, 두 요청이 같은 작업인지 판단하지 않습니다.

대기 방식에서는 다음 일이 생길 수 있습니다.

1. 요청 A가 락을 잡고 포인트를 차감합니다.
2. 요청 B가 같은 락을 기다립니다.
3. A가 끝나고 락을 해제합니다.
4. B가 락을 얻어 포인트를 한 번 더 차감합니다.

같은 논리적 요청의 중복 실행까지 막으려면 멱등 키나 이미 처리된 요청인지 확인하는 별도의 장치가 필요합니다.

```http
POST /points/deduct
Idempotency-Key: "8e03978e-40d5-43e8-bc93-6894a57f9324"
```

서버는 키별 처리 상태와 결과를 저장합니다. 같은 키의 요청이 아직 처리 중이라면 충돌을 반환하고, 처리가 끝났다면 새로 실행하지 않고 첫 번째 결과를 돌려줄 수 있습니다.

[토스페이먼츠](https://docs.tosspayments.com/reference/using-api/authorization)는 이전 멱등 요청이 처리 중일 때 409와 `IDEMPOTENT_REQUEST_PROCESSING`을 반환하고, [Stripe](https://docs.stripe.com/api/idempotent_requests)는 같은 키로 다시 들어온 요청에 처음 저장한 결과를 반환합니다. 세부 정책은 다르지만 목적은 같은 작업이 두 번 실행되지 않게 하는 것입니다.

## 마치며

락 획득 실패라는 이름만으로 상태 코드를 정할 수는 없습니다. 요청이 정상적으로 도착했는지, 서버 전체의 문제인지, 특정 자원의 현재 상태와 충돌한 것인지 먼저 구분해야 합니다.

이 글의 따닥 요청처럼 특정 자원에서 발생한 일시적인 충돌이라면 409가 설명하기 쉬운 선택입니다. 423을 사용하는 API라면 그 규칙을 일관되게 적용할 수도 있습니다. 세부 원인과 재시도 가능 여부는 응답 본문으로 전달합니다.

상태 코드를 잘 고르는 것만으로 중복 실행이 해결되지는 않습니다. 같은 요청을 식별할 수 있는 멱등성 설계까지 함께 있어야 클라이언트가 안전하게 다시 시도할 수 있습니다.
